## 0. 먼저 — 현재 코드의 계산이 얼마나 틀렸는가

v2 §4.2는 "한국 마켓의 `salePrice`는 부가세 포함가인데 초판 산식은 수수료에만 ×1.1을 하고 매출에는 안 했다"고 지적했습니다. **그 오류는 문서만의 것이 아니라 실제 코드에 있습니다.**

[src/Tetragon.Domain/Pricing/MarginHealth.cs](../../src/Tetragon.Domain/Pricing/MarginHealth.cs) 실제 계산:

```csharp
var fee        = sale * (marketFeePct / 100m);
var netRevenue = sale - fee;                    // ← sale은 부가세 포함가
var totalCost  = costKrw + supplierShippingFee; // ← 매입세액 공제 미고려
var profit     = netRevenue - totalCost;
var marginPct  = profit / sale * 100m;
BreakEvenPrice = totalCost / (1m - marketFeePct / 100m);
```

세 가지가 빠져 있습니다.

| # | 빠진 것 | 방향 |
|---|---|---|
| 1 | 매출에서 부가세 제거 (`sale / 1.1`) | 이익 **과대** |
| 2 | 수수료에 붙는 부가세 (`× 1.1`) | 이익 **과대** |
| 3 | 반품·교환 비용 | 이익 **과대** |

세 오류가 **전부 같은 방향**입니다. 상쇄되지 않고 누적됩니다.

### 0.1 숫자로

도매꾹 상품, 원가 10,000원(KRW), 판매가 15,900원, 수수료율 13%, 공급처 배송비 0원.

| | 현재 코드 | 정정 후 (세금계산서 미수취) | 정정 후 (수취) |
|---|---|---|---|
| 매출 | 15,900 | 14,455 (=15,900/1.1) | 14,455 |
| 매입원가 | 10,000 | 10,000 | 9,091 (=10,000/1.1) |
| 수수료 | 2,067 | 2,274 (=15,900×0.13×1.1) | 2,274 |
| **순이익** | **3,833** | **2,181** | **3,090** |
| **마진율** | **24.1%** | **15.1%** | **21.4%** |

**9.0%p 과대계상.** v2 §4.2가 예측한 그 값입니다.

손익분기는 더 심각합니다.

```
현재:   BreakEven = 10,000 / (1 − 0.13)                  = 11,494원
정정:   BreakEven = 10,000 / (1/1.1 − 1.1×0.13)          = 13,053원
```

**1,559원 차이.** 12,000원에 파는 상품을 현재 코드는 "마진 정상"이라 하고, 실제로는 개당 약 1,000원 손해입니다.
`MarginHealth`는 [LinkPreviewService](../../src/Tetragon.Application/Services/LinkPreview.cs)(등록 전 미리보기), [StockAudit](../../src/Tetragon.Application/Services/StockAudit.cs), [PurchaseOrderSheetBuilder](../../src/Tetragon.Application/Services/PurchaseOrderSheet.cs)에서 쓰입니다 — **소싱 판단·발주 판단이 전부 이 숫자 위에 서 있습니다.**

> 그래서 이 문서는 §2(계산식 정정)를 먼저 하고 §3~§5(대사)로 갑니다.
> 다만 **정정된 계수(수수료율·반품률·세금계산서 수취율)를 실측으로 얻는 곳이 대사**이므로 둘은 한 묶음입니다.

## 1. `Order.EstimatedMargin`도 같은 문제

[Order.cs](../../src/Tetragon.Domain/Ordering/Order.cs):

```csharp
public decimal? EstimatedMargin =>
    SupplierPaidAmount is { } paid ? PaidAmount.Amount - paid.Amount
  : SupplierUnitCost  is { } unit ? PaidAmount.Amount - unit.Amount * Quantity
  : null;
```

판매금액 − 공급처 지불액. **마켓 수수료가 아예 없습니다.** 13% 수수료 상품이면 이 값은 실제 이익의 두 배 가까이 됩니다.

이 속성은 `[NotMapped]`로 무시되고([TetragonDbContext](../../src/Tetragon.Infrastructure/Persistence/TetragonDbContext.cs) `b.Ignore(o => o.EstimatedMargin)`) 화면·발주서에서 읽힙니다.

**처리**: 삭제하지 않고 이름을 바꿉니다 — `GrossSpread`(판매금액과 매입금액의 차이). 실제로 그 값이 맞고, 이익이라고 부르지만 않으면 유용합니다. 이익은 `order_pnl`이 답합니다.

## 2. `MarginModel` — 계산식 정정

### 2.1 왜 `MarginHealth`를 수정하지 않고 새로 만드는가

`MarginHealth.Assess`는 세 곳에서 호출되고, 반환 타입 `MarginAssessment`는 API DTO로 그대로 나갑니다(프론트 `LinkPreview` 응답). 시그니처를 바꾸면 화면 세 개가 동시에 깨집니다.

**병행 구간을 둡니다** — v2 §8이 "이벤트 버스 삭제는 all-or-nothing으로 하지 말라"고 한 것과 같은 이유입니다.

```
src/Tetragon.Domain/Pricing/MarginModel.cs      신규 — 정정된 산식
src/Tetragon.Domain/Pricing/MarginHealth.cs     유지 — 내부적으로 MarginModel 위임 + [Obsolete]
```

`MarginHealth.Assess`는 새 파라미터 기본값(`returnRatePct=0`, `taxInvoiceReceived=false`, `vatPct=10`)으로 `MarginModel`을 호출하고 결과를 기존 `MarginAssessment`에 매핑합니다. **호출부를 하나도 수정하지 않아도 숫자가 즉시 정상이 됩니다.** 화면 문구·필드 추가는 그다음에 순차로.

### 2.2 산식

```csharp
// src/Tetragon.Domain/Pricing/MarginModel.cs
public static MarginBreakdown Compute(MarginInput x)
{
    var sale        = x.SalePriceKrw;                       // 부가세 포함 판매가
    var vat         = 1m + x.VatPct / 100m;

    var netSales    = sale / vat;                           // 공급가액 매출
    var costKrw     = x.SourceCost.Currency == "KRW"
                        ? x.SourceCost.Amount
                        : x.SourceCost.Amount * x.ExchangeRate;
    var netCost     = x.TaxInvoiceReceived                  // 매입세액 공제 가능 여부
                        ? costKrw / vat
                        : costKrw;                          // 위탁 공급처는 미수취가 흔하다
    var fee         = sale * (x.MarketFeePct / 100m) * vat; // 수수료에도 부가세
    var returnCost  = (x.ReturnRatePct / 100m) * x.RoundTripShippingKrw;

    var profit      = netSales - netCost - x.SupplierShippingKrw - fee - returnCost;
    var marginPct   = netSales > 0 ? profit / netSales * 100m : 0m;   // ★ 분모 = 공급가액매출

    // 손익분기: profit = 0 이 되는 sale
    //   sale/vat − netCost − shipping − sale×feeRate×vat − returnCost = 0
    //   sale × (1/vat − feeRate×vat) = netCost + shipping + returnCost
    var denom       = 1m / vat - (x.MarketFeePct / 100m) * vat;
    var breakEven   = denom > 0
                        ? (netCost + x.SupplierShippingKrw + returnCost) / denom
                        : decimal.MaxValue;                 // 수수료가 구조적으로 불가능한 수준

    return new MarginBreakdown { /* … 위 값 전부 + Level + Message */ };
}
```

**`marginPct`의 분모를 `netSales`로 명시합니다** — v2 §4.2가 "초판은 분모를 정의하지 않았다"고 지적한 부분입니다. 판매가로 나누면 부가세만큼 낮게 나와 또 다른 혼선이 생깁니다.

### 2.3 광고비는 넣지 않습니다

v2 §4.2 결론 그대로: ROAS 350%면 광고비가 매출의 28.6%인데, 모든 상품에서 이를 빼고 10%를 요구하면 전 카탈로그가 탈락합니다. 광고비는 `order_pnl.ad_cost`에 **정산 데이터로 귀속된 만큼만** 들어가고, 기본 마진 판정에는 쓰지 않습니다.

### 2.4 기본 계수와 그 출처

| 계수 | 초기값 | 출처 | 언제 교정되나 |
|---|---|---|---|
| `VatPct` | 10 | 법정 | — |
| `MarketFeePct` | 정책값(기본 13) | `PricingPolicy`의 `market-fee` Rule | §5.1 실측 |
| `TaxInvoiceReceived` | **false** | 보수적 기본값 | 공급처별 설정 + §5.3 |
| `ReturnRatePct` | **0** | 데이터 없음 | §5.2 실측 |
| `RoundTripShippingKrw` | `ConsignmentLogistics.ReturnFee × 2` (없으면 6,000) | 공급처 속성 | — |

`ReturnRatePct` 기본값을 0으로 둔 것은 의도적입니다. **없는 데이터를 상수로 채워 넣지 않습니다** — v2 §4.2의 "실측 없는 상수로 카탈로그의 운명을 결정하지 말라". 대신 화면에 "반품률 미반영"을 명시합니다.

## 3. 정산 데이터 모델

```sql
CREATE TABLE settlement_imports (
  id                 TEXT PRIMARY KEY,
  channel            TEXT NOT NULL,
  account_id         TEXT NOT NULL DEFAULT 'default',
  period_from        TEXT NOT NULL,        -- KST
  period_to          TEXT NOT NULL,
  file_name          TEXT NOT NULL,
  profile_id         TEXT NOT NULL,        -- 08 §3.2 헤더 지문
  declared_total     REAL,                 -- 파일이 명시한 정산총액 (검증용)
  computed_total     REAL NOT NULL,

  imported_at        INTEGER NOT NULL
);

CREATE TABLE settlement_lines (
  id               TEXT PRIMARY KEY,
  import_id        TEXT NOT NULL,

  option_id        TEXT,
  seq              INTEGER NOT NULL,       -- 같은 주문의 여러 라인 구분

  order_id         TEXT,                   -- 매칭된 우리 Order (NULL = 미매칭)

);
CREATE UNIQUE INDEX ux_settle_line
  ON settlement_lines(channel, account_id, settle_date, market_order_id, line_type, seq);
CREATE INDEX ix_settle_order ON settlement_lines(order_id);
CREATE INDEX ix_settle_match ON settlement_lines(match_state);

CREATE TABLE order_pnl (
  order_id          TEXT PRIMARY KEY,

  market_fee        REAL NOT NULL DEFAULT 0,
  coupon_share      REAL NOT NULL DEFAULT 0,
  return_cost       REAL NOT NULL DEFAULT 0,
  ad_cost           REAL NOT NULL DEFAULT 0,
  other_adjust      REAL NOT NULL DEFAULT 0,
  vat_payable       REAL NOT NULL DEFAULT 0,
  profit            REAL NOT NULL,
  margin_pct        REAL NOT NULL,

);

CREATE TABLE tax_ledger (            -- 부가세 신고 준비용 (계산만, 신고는 세무 영역)
  period        TEXT PRIMARY KEY,    -- 'YYYY-Q1' 또는 'YYYY-MM'
  sales_vat     REAL NOT NULL,
  purchase_vat  REAL NOT NULL,       -- 세금계산서 수취분만

  note          TEXT
);
```

### 3.1 부호 규약 — 이걸 안 정하면 대사가 망가집니다

```
gross : 판매 +, 반품/취소 −
fee   : 항상 ≤ 0 (차감)
net   : 실제 입금(+)/차감(−). 파일에 있으면 그대로, 없으면 gross + fee + vat
검증  : Σ net == settlement_imports.declared_total  (±1원 허용)
```

**불일치하면 임포트 전체를 거부합니다.** 부분 적재된 정산 데이터는 틀린 이익을 확신 있게 보여주는데, 그건 데이터가 없는 것보다 나쁩니다(08 §3.3).

## 4. 대사 알고리즘

### 4.1 3단계 매칭

```
1단 · 정확 매칭
     settlement_lines.market_order_id == Orders.MarketOrderId  (+ channel 일치)
     → matched, confidence = 1.0
     ★ IOrderRepository.FindByMarketOrderAsync가 이미 있습니다 (Ports.cs)
       Orders에 (MarketCode, MarketOrderId) 유니크 인덱스도 이미 있습니다

2단 · 분할 매칭
     묶음배송·부분취소로 주문번호에 접미가 붙는 경우 (예: "2600123456-1")
     → 접미 제거 후 재조회 + market_item_id 일치 + 금액 근접(±10%) + 날짜 근접(±14일)
     → 조건 전부 만족: matched, confidence = 0.8
     → 일부만 만족:   ambiguous  ← 자동 반영하지 않고 사람에게

3단 · 미매칭
     → unmatched + attention_item('settle.unmatched', impact = |net|)
```

### 4.2 미매칭을 무시하지 않는 이유

미매칭 라인은 세 종류이고 **셋 다 돈입니다.**

| 유형 | 의미 | impact |
|---|---|---|
| 우리가 모르는 주문 | 주문 수집이 빠뜨린 매출 | `net` (양수) — 자동화가 놓친 주문 |
| 우리가 모르는 차감 | 페널티·정산 조정 | `\|net\|` (음수) — **가장 위험** |
| 광고비 라인 | 상품 귀속 불가 | 채널 단위로 집계 |

두 번째가 특히 중요합니다. 마켓 페널티는 조용히 차감되고, 정산서를 보지 않으면 영원히 모릅니다.

### 4.3 `order_pnl` 계산

```
settle.match 완료
  → 주문별로 라인을 모아 order_pnl(basis='settled') UPSERT
      net_sales     = Σ(sale 라인 gross) / 1.1
      market_fee    = |Σ(commission 라인)|
      coupon_share  = |Σ(coupon 라인)|
      return_cost   = |Σ(return 라인)| + 왕복배송비
      supplier_cost = Order.SupplierPaidAmount ?? SupplierUnitCost × Quantity
      profit        = net_sales − supplier_cost(세금계산서 반영) − supplier_shipping
                      − market_fee − coupon_share − return_cost − ad_cost + other_adjust
  → basis='estimated' 행이 있으면 덮어쓰지 않고 둘 다 보관 (§4.4)
```

주문이 아직 정산 전이면 `basis='estimated'`를 `MarginModel`로 계산해 채웁니다. **`settled`가 도착하면 `estimated`는 지우지 않고 남깁니다** — 둘의 차이가 §5의 교정 신호입니다.

### 4.4 추정과 확정을 절대 섞지 않습니다

```
┌ 2026년 7월 ─────────────────────────────────────────┐
│ 확정 이익   2,140,300원   (정산 완료 주문 612건)      │
│ 추정 이익   3,208,700원   (같은 주문의 등록 시점 추정) │
│ 차이        −1,068,400원  (−33.3%)   ← 교정 신호      │
│                                                      │
│ 차이의 출처                                           │
│   수수료 실측 14.8% vs 정책 13.0%      −412,000원     │
│   쿠폰 분담 (정책에 없음)               −287,000원     │
│   반품 41건 (반품률 6.7%)               −301,400원     │
│   기타 조정                              −68,000원     │
└──────────────────────────────────────────────────────┘
```

이 화면 하나가 v2가 "실측으로 마진 모델 보정"이라 부른 작업의 전부입니다.

## 5. 실측 → 계수 교정 루프

### 5.1 수수료율

```sql
-- 채널 × 공급처 카테고리 × 최근 90일
SELECT SUM(ABS(fee_lines.net)) / SUM(sale_lines.gross) AS effective_fee_rate
```

실측이 정책값과 **1.0%p 이상 다르면** `attention_item('policy.fee_drift')`로 제안합니다.
**자동 반영하지 않습니다** — `PricingPolicy` 수정은 이미 등록된 상품의 재계산 여부까지 판단해야 하는 일입니다.
제안 카드에서 [정책 수정] 버튼이 기존 `PUT /api/v1/pricing-policies/{id}` 화면으로 보냅니다.

### 5.2 반품률

```sql
-- 카테고리 × 최근 180일
반품률 = COUNT(return 라인 있는 주문) / COUNT(sale 주문)
```

표본이 카테고리당 30건 미만이면 **산출하지 않습니다** (`NULL`). 5건 중 1건 반품을 20%로 확정하면 그 카테고리가 통째로 사장됩니다.
표본이 모이면 `MarginModel.ReturnRatePct`의 기본값으로 카테고리별 주입.

### 5.3 세금계산서 수취율

공급처별 설정값입니다(`supplier_settings.tax_invoice = true|false|unknown`).
`unknown`이면 **false로 계산하고 화면에 "매입세액 공제 미반영 — 공급처 확인 필요"를 표기**합니다. 보수적 기본값이 맞습니다 — 이익을 낮게 잡으면 손해를 안 봅니다.

### 5.4 교정의 도달점

이 세 계수가 실측으로 채워지면 v2가 미뤄 둔 **Score 게이트의 입력이 완성됩니다.**

```
v2 §4.2:  성과 데이터 확보 → 실측으로 마진 모델 보정 → 그 다음에 Score 게이트
            └ 09           └ 10 §5                    └ 11 §3 (소싱 스코어)
```

Score 게이트는 [11 소싱](11-소싱-인텔리전스.md)에서 **탈락 장치가 아니라 정렬 장치**로 구현합니다. 계수가 실측이어도 여전히 사람이 최종 결정합니다.

## 8. 테스트

```
□ 부호 규약    — 반품 라인이 음수로 적재되고 Σnet이 declared_total과 일치
□ 합계 불일치  — declared_total과 어긋나는 파일이 전량 거부되고 0행 적재
□ 임포트 멱등  — 같은 파일 2회 → 행 수·값 불변
□ 1단 매칭     — 정확 일치 주문 100건 전부 confidence 1.0
□ 2단 매칭     — 접미 붙은 분할 주문이 matched, 금액 불일치 건은 ambiguous
□ 미매칭 회계  — unmatched 라인의 net 합계가 pnl 어디에도 흡수되지 않음
□ MarginModel  — §0.1의 세 시나리오가 표의 값과 일치 (골든 테스트)
□ 손익분기     — Compute(BreakEven 가격) 의 profit == 0 (±1원)
□ 위임 호환    — MarginHealth.Assess 기존 호출부 3곳이 컴파일·동작
□ basis 분리   — settled 계산 후에도 estimated 행이 남아 있음
```

`MarginModel`의 골든 테스트는 **이 문서 §0.1 표를 그대로 케이스로** 넣으십시오. 산식이 다시 흔들리면 즉시 잡힙니다.

## 9. 이 설계가 틀릴 수 있는 지점

1. **수수료 부가세 처리(`× 1.1`)를 1차 출처로 확인하지 못했습니다.** 마켓이 수수료를 부가세 포함으로 청구하는지 별도 청구하는지에 따라 계수가 달라집니다. **§5.1의 실측이 정답이고, §2의 계수는 실측이 도착하기 전의 잠정값입니다.** 첫 정산 임포트 후 즉시 대조하십시오.
2. **정산 CSV의 실제 컬럼·라인 유형을 확인하지 못했습니다.** `line_type` 7종은 추정입니다. 08 §3.2의 헤더 지문 방식을 택한 이유이고, 첫 임포트가 "새 양식입니다"로 실패하는 것은 **정상 동작**입니다.
3. **`market_order_id`가 마켓 간·계정 간에 유일하지 않을 수 있습니다.** 유니크 인덱스에 `channel`과 `account_id`를 넣었지만, 같은 채널 안에서 주문번호가 재사용되는 사례가 있으면 2단 매칭이 오매칭할 수 있습니다. 그래서 2단은 금액·날짜 근접까지 요구합니다.
4. **부가세 신고는 이 시스템의 영역이 아닙니다.** `tax_ledger`는 계산 참고값이지 신고 자료가 아닙니다. 화면에 그렇게 명시하십시오.
5. **`MarginHealth` 위임 전환은 숫자를 즉시 바꿉니다.** 배포 전에 기존 DB로 새·구 산식을 동시에 돌려 차이 분포를 확인하십시오 — v2 §8이 요구한 병행 운영입니다.
