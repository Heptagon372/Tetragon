## 0. 지금의 소싱 = 무차별

코드상 상품이 시스템에 들어오는 경로는 넷입니다([ProductEndpoints](../src/Tetragon.Api/Endpoints/ProductEndpoints.cs), [CategoryEndpoints](../src/Tetragon.Api/Endpoints/CategoryEndpoints.cs), [ExcelEndpoints](../src/Tetragon.Api/Endpoints/ExcelEndpoints.cs)).

| 경로 | 선별 기준 |
|---|---|
| `POST /products/collect` (URL 붙여넣기) | 사람이 링크를 고른 것이 유일한 기준 |
| `POST /products/quick-list` | 위와 동일 |
| `POST /categories/{supplier}/collect` | **없음.** `MaxProducts`(기본 100)까지 등록일 역순으로 전부 |
| 엑셀 카테고리 임포트 | 사람이 `Y` 표시한 행 |

카테고리 수집([CategoryCrawlHandler.cs](../src/Tetragon.Application/Pipeline/CategoryCrawlHandler.cs))이 하는 유일한 선별은 **중복 제거**입니다 — `ExistingSourceIdsAsync`로 이미 수집한 상품을 건너뜁니다. 팔릴지 여부는 보지 않습니다.

그 결과가 v2 README의 진단입니다: 등록 슬롯이 아니라 **1인 운영자의 시간**이 구속 제약인데, 안 팔릴 상품을 수백 개 등록하면 그 시간이 재고 동기화·CS·정산 대사로 전부 새어 나갑니다.

---

## 1. 이 문서가 만들지 않는 것 — 먼저 못 박습니다

v2 §4.2의 경고를 그대로 받습니다.

> **Score 게이트를 지금 만들지 마십시오.** 반품률과 광고비는 지금 실측이 없는 상수입니다.
> 실측 없는 상수로 카탈로그의 운명을 결정하는 장치가 됩니다.

그래서 이 설계의 스코어는 **게이트가 아니라 정렬**입니다.

| 하지 않는 것 | 하는 것 |
|---|---|
| 점수 미달 후보를 자동 탈락 | 점수 순으로 줄 세워 보여주기 |
| 자동으로 수집·등록 큐에 투입 | 사람이 체크박스로 일괄 승인 |
| 데이터 없는 축을 기본값으로 채우기 | **그 축을 `null`로 두고 "미측정"을 화면에 표시** |
| 점수 하나로 요약 | 축별 점수 + **차단 사유는 점수가 아니라 사실 목록으로** |

마지막 항목이 중요합니다. "브랜드가 없어 쿠팡에 등록할 수 없다"는 −15점이 아닙니다. **사실**입니다. 점수에 녹이면 다른 축이 높을 때 가려집니다.

## 3. 스코어 — 축별 출처와 그 한계

### 3.1 수요 (`demand_score`) — 가장 약한 축

| 신호 | 출처 | 확보 여부 |
|---|---|---|
| 마켓 검색량 | 네이버 검색광고 API / 쿠팡 | **미확보.** 별도 계정·심사 필요 |
| 공급처 판매량·조회수 | 도매꾹 `getItemView` 응답 | **미확인.** 응답에 판매량 필드가 있는지 실측 필요 |
| **우리 성과** | `listing_perf` (09) | ✅ 확보 |

지금 확실한 것은 세 번째뿐입니다. 그래서 수요 축은 이렇게 계산합니다.

```
우리가 이미 파는 유사 상품(같은 공급처 카테고리)의 최근 90일
  주문 있는 리스팅 비율 × 100  →  demand_score
표본이 10건 미만이면 demand_score = NULL
```

**카테고리 단위의 조잡한 신호입니다.** 그렇게 표시합니다 — `score_basis_json`에
`"같은 카테고리 리스팅 34개 중 7개가 최근 90일 주문 있음 (20.6%)"`.

`winback` 모드(§4.3)에서는 이 축이 훨씬 강해집니다 — 실제로 팔린 상품의 이웃을 찾는 것이므로.

### 3.2 경쟁 (`competition_score`)

```
공급측 경쟁: 도매꾹 getItemList 응답의 header.numberOfItems
             ← 같은 키워드로 몇 개의 도매 상품이 있는가
자기 중복  : DuplicateAudit 재사용 — 우리가 이미 같은 (공급처, 원본ID)를 파는가
```

`numberOfItems`는 [DomeggookSupplierPlugin.CrawlAsync](../src/Tetragon.Plugins.Suppliers/DomeggookSupplierPlugin.cs)가 이미 파싱해 `CategoryCrawlPage.TotalCount`로 반환합니다. **추가 호출 없이 얻는 신호입니다.**

> ⚠️ **이건 공급 측 경쟁이지 판매 측 경쟁이 아닙니다.** 도매꾹에 같은 상품이 200개 있다는 것과
> 쿠팡에서 200명이 그걸 판다는 것은 다릅니다. 상관은 있겠지만 같지 않습니다.
> 화면에 "도매 공급 경쟁"이라고 정확히 쓰고, 쿠팡 검색결과 수를 얻는 방법이 생기기 전까지는 대체 신호로만 씁니다.

`DuplicateAudit`([DuplicateAudit.cs](../src/Tetragon.Application/Services/DuplicateAudit.cs), 171줄)에는 **미사용 생성자 매개변수 `listings`(빌드 경고 CS9113)**가 있습니다. 소싱에서 "우리가 이미 이 상품을 어느 마켓에 팔고 있는가"를 물으면서 **그 매개변수를 실제로 쓰게 됩니다** — 경고 하나가 자연스럽게 없어집니다.

### 3.3 마진 (`margin_score`) — 가장 강한 축

```
MarginModel.Compute (10 §2 정정된 산식)
  입력: cost_krw = CrawledProductRef.Price
        salePrice = 기본 PricingPolicy를 적용한 예상 판매가
        feeRate   = 10 §5.1 실측 (없으면 정책값)
        returnRate = 10 §5.2 실측 (없으면 0 + "미반영" 표시)
→ margin_score = clamp(순마진율 / 25 × 100, 0, 100)
→ est_monthly_profit = 순이익 × 카테고리 평균 월 판매수량(09 데이터, 없으면 NULL)
```

**이 축만 10의 실측과 직접 연결됩니다.** 08 §4가 소싱(8번)을 정산 대사(2·3번) 뒤에 배치한 이유입니다.

목록 조회(`CrawledProductRef`)에는 가격만 있고 배송비·MOQ가 없습니다. 그래서 `margin_score`는 **목록 단계에서는 잠정치**이고, 상세 수집 뒤 정확해집니다. 화면에 "잠정"으로 표시하고, 승인 직전에 상위 N건만 `LinkPreviewService`로 정밀 재계산하는 옵션을 둡니다(§4.4).

### 3.4 차단 사유 (`blockers`) — 점수가 아니라 사실

```json
[
  {"code":"NO_BRAND",    "channel":"coupang", "severity":"block",
   "message":"브랜드·모델번호 없음 — 2026-08-01부터 쿠팡 등록 불가"},
  {"code":"MOQ",         "severity":"warn",  "message":"최소구매수량 5개 — 1개 주문 시 발주 불가"},
  {"code":"NO_LICENSE",  "severity":"warn",  "message":"상세이미지 사용 미허용 — 콘텐츠 생성 필요(12)"},
  {"code":"KC_REQUIRED", "severity":"block", "message":"전기용품 카테고리 — KC 인증 확인 필요"},
  {"code":"STOCK_STUB",  "severity":"block", "message":"타오바오 — CheckInventoryAsync가 스텁이라 재고 신뢰도 0"}
]
```

출처:

| code | 판정 근거 |
|---|---|
| `NO_BRAND` | 12 `AttributeExtract` 결과 또는 공급처 속성. 없으면 "미확인"(block 아님) |
| `MOQ` | `LogisticsKeys.MinOrderQty` — v2 §5가 "감지해야 하는데 지금 못 하는 것"으로 든 항목 |
| `NO_LICENSE` | `LogisticsKeys.DetailImageLicense != "Y"` — v2 §7.5 "기본값 = 사용 금지" |
| `KC_REQUIRED` | `sourcing_blocklist`의 카테고리 패턴. v2 §7.5가 **warn이 아니라 block**을 요구 |
| `STOCK_STUB` | 공급처 코드가 `taobao`·`amazon` — v2 README의 "정리 권고" |

**`severity='block'`이 하나라도 있으면 총점을 계산하지 않고 `total_score = NULL`, `decision`을 `pending`으로 두되 목록 하단에 별도 섹션으로 분리합니다.** 점수와 섞으면 "점수 높은데 왜 못 팔지"가 됩니다.

### 3.5 총점 — 축 수를 함께 보여줍니다

```
total_score  = NULL이 아닌 축들의 가중평균
               가중치: margin 0.5, demand 0.3, competition 0.2 (정규화)
scored_axes  = NULL이 아닌 축의 개수 (1~3)
```

화면에는 `72점 (2/3축)`처럼 **항상 축 수를 붙입니다.** 1축짜리 72점과 3축짜리 72점은 다른 숫자입니다. 이 표기가 가짜 정밀도를 막습니다.

## 4. 수집 모드 3종

### 4.1 기존 계약을 거의 그대로 씁니다

`ICategoryCrawler`([CategoryCrawling.cs](../src/Tetragon.Plugin.Abstractions/CategoryCrawling.cs))의 `CategoryCrawlRequest`에는 **이미 `Keyword`, `MinPrice`, `MaxPrice`가 있습니다.** 검색 인터페이스를 새로 만들 필요가 없습니다.

부족한 것은 정렬 하나뿐입니다. 도매꾹 구현이 `so=rd`(등록일 역순)를 하드코딩하고 있습니다.

```csharp
// CategoryCrawlRequest에 추가 — init 전용 optional 속성이라 기존 구현체는 무수정
public CrawlSort Sort { get; init; } = CrawlSort.Newest;

public enum CrawlSort { Newest, PriceAsc, PriceDesc, Popular }
```

플러그인은 지원하지 않는 값을 받으면 `Newest`로 폴백합니다.
⚠️ **도매꾹 `so` 파라미터의 실제 허용값을 확인하지 못했습니다.** `Popular`가 없으면 `Newest`로 폴백되고, 그 사실이 `sourcing_runs.seed_json`에 기록됩니다.

### 4.2 `category` / `keyword`

기존 카테고리 수집과의 결정적 차이: **수집 전에 스코어링합니다.**

```
현재:  크롤 → 전부 ScrapeJob 생성 → 수집(외부 호출 N회) → 등록
신규:  크롤 → 목록 정보만으로 스코어 → 사람이 선별 → 선별분만 ScrapeJob 생성
```

목록 API 1회로 100건의 후보를 얻고, 그중 10건만 상세 수집합니다. **외부 호출이 100회에서 10회로 줄어듭니다** — v2 §4.3이 계산한 도매꾹 호출량 문제(레이트리밋 미확인)를 직접 완화합니다.

### 4.3 `winback` — 루프를 닫는 모드

**우리 성과 데이터를 소싱 조건으로 역이용합니다.**

```
입력: 최근 90일 주문이 있었던 리스팅 상위 N개 (09 listing_perf)
  → 각각의 Product.SourceCategory 와 Attributes[LogisticsKeys.SearchKeywords]
     ★ 도매꾹은 basis.keywords.kw로 검색어를 주고, 이미 파싱해 저장하고 있습니다
       (DomeggookSupplierPlugin.cs:754)
  → 그 카테고리·키워드로 CrawlAsync
  → 이미 가진 상품 제외 (ExistingSourceIdsAsync 재사용)
  → demand_score를 "원본 리스팅의 실제 주문 수"로 계산 ← ★ 이 모드에서만 강한 신호
```

이것이 08 §0 다이어그램의 `F1 → F3` 화살표입니다. **"팔린 것의 이웃을 더 찾는다"** — 시스템이 자기 실적으로 다음 소싱을 결정하는 유일한 경로입니다.

`winback`은 다른 두 모드보다 나중에 만드십시오. `listing_perf`에 최소 90일치가 쌓여야 의미가 있습니다.

### 4.4 승인 → 기존 파이프라인

```
사람이 체크박스로 후보 선택 → [수집 큐에 넣기]
  → sourcing_candidates.decision = 'promoted'
  → CollectProductsUseCase.ExecuteAsync(urls, policyId, ct)   ★ 기존 유스케이스
     또는 QuickListUseCase (마켓까지 자동 등록할 때)
  → 반환된 jobId를 candidate에 연결
```

**새 파이프라인을 만들지 않습니다.** v2 §8의 "기존 자산은 유지한다. 다시 만들지 않는다"를 지킵니다.

옵션 `[정밀 재계산]`: 승인 전 상위 N건을 `LinkPreviewService`로 실제 수집해 마진을 확정합니다.
`LinkPreviewService`는 **DB에 쓰지 않고** 수집→정규화→가격계산→`MarginHealth.Assess`까지 하는 기존 서비스입니다([LinkPreview.cs](../src/Tetragon.Application/Services/LinkPreview.cs), 293줄). 그대로 재사용합니다.

## 5. work_item 흐름

```
POST /api/v1/sourcing/runs
  → sourcing_runs(state='running')
  → work_item(kind='source.harvest', payload={runId})

source.harvest       동시성 2, 채널 리미터 경유(v2 §2.5)
  → ICategoryCrawler.CrawlAsync 페이지 순회 (페이지 간 600ms — 기존 CategoryCrawlHandler와 동일)
  → ExistingSourceIdsAsync로 중복 제거 → sourcing_candidates INSERT
  → 상한 MaxCandidates(기본 200) 또는 HasMore=false
  → work_item(kind='source.score', payload={runId})

source.score         동시성 4
  → 축별 계산 (외부 호출 없음 — 전부 우리 DB + 이미 받은 목록 데이터)
  → blockers 판정
  → sourcing_runs(state='scored')
  → attention_item('source.candidate',
       impact = Σ est_monthly_profit(상위 20건),
       title  = "소싱 후보 143건 — 승인 대기")
```

`source.score`가 **외부 호출을 하지 않는 것**이 설계상 중요합니다. 점수 재계산이 공짜여야 가중치를 실험할 수 있습니다.

## 9. 이 설계가 틀릴 수 있는 지점

1. **수요 축이 근본적으로 약합니다.** 검색량 데이터 없이 "같은 카테고리에서 우리가 뭘 팔았나"로 대신하는 것은 순환적입니다 — 우리가 등록한 것만 보므로 등록한 적 없는 좋은 카테고리는 영원히 0점입니다. **완화**: `demand_score`의 가중치를 0.3으로 낮게 두고, 표본 10건 미만이면 아예 NULL. **해소**: 네이버 검색광고 API 키를 확보하면 그때 축을 교체합니다.
2. **`numberOfItems`는 공급 경쟁이지 판매 경쟁이 아닙니다** (§3.2). 이름을 정확히 붙이는 것 외에 지금 할 수 있는 게 없습니다.
3. **목록 단계의 마진은 배송비·MOQ를 모릅니다.** 잠정치임을 표시하고 정밀 재계산 경로를 뒀지만, 대량 승인 시 사람이 그 단계를 건너뛸 것입니다. **완화**: 승인 시 `est_margin_pct < 15%`인 건이 섞여 있으면 확인 다이얼로그.
4. **`KC_REQUIRED` 판정이 카테고리 패턴 매칭입니다.** 오탐(멀쩡한 상품 차단)과 미탐(위험 상품 통과)이 둘 다 납니다. v2 §7.5가 "위반 시 형사처벌 가능성"이라 한 영역이므로 **미탐 쪽을 두려워하는 방향**으로, 즉 넓게 잡고 사람이 푸는 방식으로 설정하십시오.
5. **이 기능은 등록량을 줄이는 기능입니다.** 지금까지 100건 등록하던 자리에서 10건을 등록하게 됩니다. 매출이 단기적으로 떨어질 수 있고, 그게 정상입니다 — 목표 함수가 등록 건수에서 슬롯당 기대이익으로 바뀐 결과입니다. **이 사실을 미리 각오하지 않으면 기능을 끄게 됩니다.**
