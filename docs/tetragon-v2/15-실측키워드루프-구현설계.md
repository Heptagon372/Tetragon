## 0. 왜 이 설계인가 / 무엇이 지금 없는가

### 0.1 13은 09 위에 서 있는데, 09는 미구현이다

13이 09의 산출물을 전제하는 지점은 넷입니다: `θ_c`의 분모(상품 30일 총 유입, §F-07) · 등록 실험 지표 `INFLOW_PER_PRODUCT`(§7.1) · `keyword_score.revenue_sum` · 리포트 파이프라인 1~3단계(§8.4).

`TetragonDbContext`의 DbSet 18개([TetragonDbContext.cs:24-41](../../src/Tetragon.Infrastructure/Persistence/TetragonDbContext.cs))에 `listing_perf`도 `settlement_lines`도 없습니다. 09가 남긴 것은 **소비자 없는 프레임**뿐입니다.

```csharp
// src/Tetragon.Domain/Imports/ImportProfile.cs:55-63
public static class ImportPurposes
{
    /// <summary>마켓 판매자센터의 상품별 성과 (노출·클릭·주문) → 09 <c>listing_perf</c>.</summary>
    public const string Performance = "perf";
    /// <summary>정산 내역 → 10 <c>settlement_lines</c>.</summary>
    public const string Settlement = "settlement";

    public static bool IsKnown(string purpose) => purpose is Performance or Settlement;
}
```

`ImportFieldCatalog.Performance`는 8필드가 별칭까지 완성돼 있고([ImportFields.cs:25-43](../../src/Tetragon.Application/Services/Import/ImportFields.cs)), 파서도 완성돼 있습니다(`CsvImporter.ParseAsync(channel, purpose, byte[] content, ct)`, [CsvImporter.cs:60](../../src/Tetragon.Application/Services/Import/CsvImporter.cs)).

**그런데 `ParseAsync`의 호출처는 리포지토리 전체에서 한 곳입니다** — [ImportEndpoints.cs:95](../../src/Tetragon.Api/Endpoints/ImportEndpoints.cs). 응답은 `preview = parsed.Rows.Take(PreviewRows)`(:102-106)뿐이고 `CsvParsed`는 버려집니다. `ImportRow.Integer/Number/Date`(CsvImporter.cs:351-361)는 **어디서도 호출되지 않습니다.** 코드가 스스로 그렇게 말합니다:

> "이 프레임이 하는 일은 **"이 파일을 읽어도 되는가"**까지다. 실제 적재(`listing_perf`·`settlement_lines`)는 09·10이 붙인다." — [ImportEndpoints.cs:10-11](../../src/Tetragon.Api/Endpoints/ImportEndpoints.cs)

09는 **파일을 검증하는 데까지 와서 멈춰 있습니다.** 적재 계층이 통째로 비어 있습니다.

### 0.2 선택 — (c) 09의 최소 부분집합을 먼저 구현한다

| | 내용 | 판단 |
|---|---|---|
| (a) | 09 전체를 선행 | **기각.** 키워드 루프는 `IRepriceRule`·`listing_tier`·`listing_winner`를 한 줄도 쓰지 않습니다. 그런데 09 문서에는 공수 추정이 한 줄도 없어 "언제까지 기다리면 되는가"조차 산정할 수 없습니다 — 기한을 셀 수 없는 선행은 그 자체로 기각 사유입니다 |
| (b) | 자체 성과 테이블(`product_traffic_fact`)을 갖고 나중에 09와 합류 | **기각.** 13의 `product_traffic_fact`와 09의 `listing_perf`는 **같은 리포트에서 나오는 같은 표**입니다 — (상품 × 날짜 × 노출·클릭·주문·매출). 둘을 만들면 같은 축에서 다른 숫자를 말하는 테이블이 둘 생기고 어느 쪽이 진실인지 답할 수 없게 됩니다. "나중에 합류"는 실제로는 "나중에 하나를 버린다"입니다 |
| **(c)** | **09의 최소 부분집합을 먼저. 그 부분집합은 정확히 `listing_perf` 적재다** | **채택** |

**(c)를 고른 이유는 부분집합이 이미 절반 명세돼 있기 때문입니다.** `ImportPurposes.Performance`, 8필드 카탈로그, `CsvImporter`, `ImportProfileStore`, `ImportEndpoints`가 전부 존재합니다. 없는 것은 **엔티티 하나와 로더 하나**이고, 그 비용은 K-5 3인일로 특정됩니다(§11.1).

> **결정 1.** `product_traffic_fact`를 만들지 않습니다. 09의 `listing_perf`에 `traffic_type` 컬럼 하나를 더해 겸용합니다. 09가 나중에 티어링·리프라이싱을 얹을 때 이 테이블을 그대로 씁니다.

**컬럼을 더하는 것만으로는 안 됩니다 — 값을 채우는 주체가 필요합니다.** `ImportFieldCatalog.Performance`의 8필드에는 유입 유형 컬럼이 없고([ImportFields.cs:25-43](../../src/Tetragon.Application/Services/Import/ImportFields.cs)), 09의 `listing_perf` DDL에도 `traffic_type`이 없습니다 — 파일 안에서 얻을 수 없는 값입니다. 따라서 **perf 임포트에도 §3.2의 규칙을 적용해 `traffic_type`을 업로드 파라미터로 받고, `perf` 로더가 그 값을 행마다 기록합니다**(K-5). 이걸 안 정하고 상수 `MIXED`를 넣으면 §5.3의 `θ_c` 분모(ORGANIC 유입 합)와 §10.3의 실험 지표(ORGANIC 클릭 합)가 **영구히 0**이 됩니다 — 컬럼은 있는데 아무도 채우지 않는 테이블이 이 결정의 실패 모드입니다. 09에는 이 컬럼의 선점을 함께 제안합니다 — `DbSeeder`는 컬럼 추가만 되고 타입·제약 변경은 못 하므로(§13-3) 나중에 09가 다른 모양으로 만들면 되돌릴 수 없습니다.

**부분집합의 정확한 정의** — 09에서 가져오는 것은 셋뿐입니다. 티어링·리프라이싱 4규칙·위너 감시·생존 확인은 손대지 않습니다.

| # | 가져오는 것 | 무엇을 위해 |
|---|---|---|
| 1 | `listing_perf` 엔티티 + `traffic_type` 컬럼 | `θ_c`의 분모, 등록 실험의 측정 지표 |
| 2 | `HasIndex(l => new { l.MarketCode, l.MarketItemId })` (09 §2.1) | 리포트 상품 매칭. 지금은 `(ProductId, MarketCode)` 유니크만 있고([TetragonDbContext.cs:161](../../src/Tetragon.Infrastructure/Persistence/TetragonDbContext.cs)) `MarketItemId` 인덱스가 없어 한 줄마다 테이블 스캔입니다 |
| 3 | 임포트 적재 계층 | `perf`·`keyword`가 함께 쓰고 10도 나중에 같은 자리를 씁니다(§3.4) |

09 §2.4의 규약도 가져옵니다 — `gross_sales`는 **수요 신호**로만, 이익은 10의 `order_pnl`만이 답합니다. 키워드 루프에서는 더 강합니다: `keyword_fact.revenue`는 **키워드 우선순위를 정하는 데만** 쓰고 마진·리프라이싱 판단에 넣지 않습니다.

### 0.3 이 설계가 고정하는 가정

| 13의 항목 | 결정 | 근거 |
|---|---|---|

## 1. 최우선 결손 — 등록 시점의 상품명·태그가 남지 않는다

13 §2.4는 "이 조건이 충족되지 않으면 본 기능은 한 줄도 동작하지 않습니다"라고 씁니다. Tetragon에서 그 조건은 **채널 상품ID가 아니라 투입 원장**입니다. 상품ID는 이미 있고(§1.4), 투입 원장은 없습니다.

### 1.1 상품명은 in-place로 덮어써지고, 태그는 파생값이다

상품명이 최종 확정되는 지점은 한 줄입니다.

```csharp
// src/Tetragon.Application/Pipeline/Handlers.cs:182-183 (EnrichmentHandler)
if (seo.Success && seo.Texts.Count > 0 && !string.IsNullOrWhiteSpace(seo.Texts[0]))
    product.SetTranslatedName("ko-KR", seo.Texts[0]);
```

그 위 :159에서 번역 결과가 같은 자리에 들어가고 SEO가 성공하면 :183이 덮어씁니다(Provider가 없으면 :185-188의 `catch`가 번역문을 유지). 덮어쓰기의 실체는 `Product.SetTranslatedName`(Product.cs:78-82) → `LocalizedText.With`([ValueObjects.cs:48-52](../../src/Tetragon.SharedKernel/ValueObjects.cs)) — **`ko-KR` 키 하나에 계속 새 값이 들어갑니다.** 1차 번역명은 SEO가 성공하는 순간 사라지고, 사람이 `EditManually`(Product.cs:112-117)로 고치면 SEO 결과가 사라집니다.

태그는 더 나쁩니다. `Product`에도 `ListingPayload`에도 태그 필드가 없고, 유일한 통로는 `Attributes["검색어"]`([Supplier.cs:80](../../src/Tetragon.Plugin.Abstractions/Supplier.cs), 채우는 곳은 도매꾹 하나 — [DomeggookSupplierPlugin.cs:766](../../src/Tetragon.Plugins.Suppliers/DomeggookSupplierPlugin.cs))입니다. 실제로 나가는 태그는 **등록 요청을 조립할 때마다 다시 계산됩니다.**

```csharp
// src/Tetragon.Plugins.Markets/CoupangCategory.cs:369-390 (발췌)
private static string[] BuildSearchTags(ListingPayload payload)
{
    var tags = new List<string>();
    if (payload.Attributes.GetValueOrDefault(LogisticsKeys.SearchKeywords) is { Length: > 0 } supplied)
        tags.AddRange(supplied.Split(',', ...));                          // ① 공급처
    if (payload.Attributes.GetValueOrDefault("브랜드") is { Length: > 1 } brand && ...)
        tags.Add(brand);                                                   // ② 브랜드
    if (tags.Count < MinSearchTags)                                        // ③ 상품명에서 보충
        tags.AddRange(payload.Name.Split([' ','/','[',']','(',')',',','-','_'], ...));
    ...
}
```

**③이 상품명에 의존합니다.** 상품명을 바꾸면 과거에 나간 `searchTags`를 원리적으로 복원할 수 없습니다. 호출 지점은 `searchTags = BuildSearchTags(payload)`([CoupangAdapter.cs:289](../../src/Tetragon.Plugins.Markets/CoupangAdapter.cs)) — **인자가 `v`(변형)가 아니라 `payload`(상품)이므로 모든 아이템에 같은 배열이 실립니다.** 이 사실이 §1.2의 입도 결정을 바꿉니다.

`Listing`에도 이력이 없습니다. 전 필드는 `TenantId, ProductId, MarketCode, Status, MarketItemId, LastError, ListedPrice, CreatedAt, UpdatedAt, SyncLogs`([Listing.cs:8-18](../../src/Tetragon.Domain/Listing/Listing.cs))이고, `MarkRegistered(string marketItemId, Money price)`(:25-32)는 상품번호와 가격만 저장합니다. 호출부([Handlers.cs:427](../../src/Tetragon.Application/Pipeline/Handlers.cs))는 바로 위 :370에서 만든 `payload`를 쥐고 있으면서 `payload.Name`을 넘기지 않습니다. `SyncLogs`도 원장이 못 됩니다 — `if (SyncLogs.Count > 50) SyncLogs.RemoveAt(0);`(:56), **50건 상한 FIFO**입니다.

### 1.2 설계 — `listing_snapshot` (리비전이 아니라 스냅샷)

13 §5.3은 `valid_from`/`valid_to` + `EXCLUDE USING gist`의 `listing_title_revision`을 제안합니다.

> **결정 2.** 구간(리비전)이 아니라 **시점(스냅샷)**으로 만듭니다.

근거 셋: ① **수정 경로가 존재하지 않습니다** — `IMarketplaceAdapter.UpdateAsync`의 호출자가 리포지토리 전체에서 **0개**(`grep -rn "\.UpdateAsync("` 결과 정의 외 히트 없음)이므로 "언제부터 언제까지 유효했나"라는 질문 자체가 아직 성립하지 않고, 구간을 만들면 `valid_to`가 영원히 NULL인 행만 쌓입니다. ② **SQLite에 `EXCLUDE USING gist`가 없어** 기간 중첩 금지를 DB로 강제할 수 없고, 강제되지 않는 불변식은 첫 배치 임포트에서 깨집니다. ③ 팩트 조인은 "`TakenAt <= statDate`인 것 중 최신 하나"면 구간 테이블과 결과가 같고, 인덱스 하나로 답합니다.

```csharp
// src/Tetragon.Domain/Keywords/ListingSnapshot.cs
/// <summary>
/// 등록·수정 시점에 <b>실제로 마켓에 나간 문자열</b>을 통째로 얼린다.
/// 상품명은 Product.Name의 ko-KR 키 하나를 계속 덮어쓰고(Product.cs:78-82), 태그는
/// 저장조차 되지 않고 등록 요청마다 상품명에서 다시 계산된다(CoupangCategory.cs:369-398).
/// 갭 분석(§5)의 투입 집합 L(p)가 통째로 이 테이블 위에 선다.
/// </summary>

    public List<string> Tags;                       // 실제로 나간 검색어. 슬롯 없는 채널이면 빈 목록
    public string Source;                           // SnapshotSources — injected_by 판정의 유일한 근거
    public DateTimeOffset TakenAt;

    public static ListingSnapshot Take(Guid listingId, Guid productId, string marketCode,
        string title, IReadOnlyList<string> tags, string source) => new() { /* … */ };

public static class SnapshotSources

    /// <summary>파이프라인이 마켓에 등록하며 찍었다 — 유일하게 "실제로 나갔다"가 보장되는 값.</summary>
    public const string Registered = "REGISTERED";

    /// DeadVerdict가 이 소스를 즉시 보류로 돌린다(§3.7 ③) — DISCOVERED·VERIFIED에만 쓰인다.</summary>
    public const string Backfilled = "BACKFILLED";

```

**`BACKFILLED`는 두되 격리합니다.** 13 §11 P0-5의 한계 — "백필로 얻는 것은 **현재 상품명**이지 등록 당시 원문이 아니며, 과거 상품의 투입 원장은 복원 불가" — 는 그대로 유효하고, 그래서 초안은 백필을 통째로 잘랐습니다. 그런데 그 결정은 더 나쁜 결과를 만듭니다: `REGISTERED` 스냅샷은 신규 등록 경로(Handlers.cs:427)에서만 생기고, `UpdateAsync` 호출자가 0개이며, `(ProductId, MarketCode)` 유니크(TetragonDbContext.cs:161) 때문에 재등록도 불가능하므로 **기존 리스팅 전부가 영구 `UNKNOWN`이 되어 인수 시점 산출물이 0건**입니다 — 인일을 써서 인도하는 화면이 "보류 3,000건"입니다. 백필의 위험(등록 당시 원문이 아닌 값으로 `DEAD` 오판)은 값을 안 만드는 것이 아니라 **소스 격리**로 막습니다: `DeadVerdict.Evaluate`가 `Source != REGISTERED`면 즉시 보류를 돌려주므로(§3.7 ③) `BACKFILLED` 스냅샷은 `DISCOVERED`·`VERIFIED`의 `covered` 판정에만 쓰입니다. 그 판정에는 현재 상품명이 정확히 맞는 입력입니다 — "지금 상품명에 있는가"를 묻는 질문이기 때문입니다. 회수 경로는 쿠팡의 경우 이미 있습니다 — `GET seller-products/{id}` 호출이 가격·재고 갱신 경로에 존재하고([CoupangAdapter.cs:382-383](../../src/Tetragon.Plugins.Markets/CoupangAdapter.cs)), 지금은 응답에서 `vendorItemId`만 읽으므로(:388-394) 같은 응답에서 상품명·태그 필드를 읽는 파싱을 더하는 일입니다(그 필드가 실제 응답에 실리는지는 K-0에서 확인). 티켓은 K-2b 3인일입니다(§11.1).

**입도는 상품(Listing) 레벨입니다.** 13 §5.4-F는 `map_level ∈ {PRODUCT, ITEM}`을 요구하지만, 태그가 아이템 단위로 갈라지지 않으므로(§1.1 — `BuildSearchTags(payload)`) 상품 레벨 스냅샷은 **손실이 아니라 정확한 표현**입니다.

> **결정 5.** 백필(K-2b) 후에도 스냅샷이 없는 리스팅 — ESM 등록분, `MarketItemId = "unknown"`, 채널 조회 실패 — 에는 **어떤 gap_class도 배정하지 않습니다.** `UNKNOWN`으로 두고 화면에 "등록 원장 없음"이라고 씁니다.

### 2.2 SQLite 관용구 — 반드시 지킬 일곱

이 리포는 **EF Core Migrations를 쓰지 않습니다.** `Migrations` 폴더가 없고 `.config/dotnet-tools.json`이 없고 `Tetragon.Infrastructure.csproj:15`에 `Microsoft.EntityFrameworkCore.Sqlite 8.0.11`만 있고 `.Design`/`.Tools`가 없어 `dotnet ef` 명령 자체가 실행되지 않습니다. 스키마는 기동 시 1회 동기화됩니다: [Program.cs:103-107](../../src/Tetragon.Api/Program.cs) → `DbSeeder.InitializeAsync`(DbSeeder.cs:12) → `EnsureCreatedAsync`(:14) → `SyncSchemaAsync`(:40) → `PRAGMA journal_mode=WAL`(:16).

**① decimal은 TEXT로 매핑돼 정렬·합산이 안 된다**

```csharp
// TetragonDbContext.cs:210-212
// SQLite는 decimal을 ORDER BY에 쓸 수 없다. 목록의 정렬 기준이 바로 이 값이므로
// REAL로 저장한다 (08 §1.2 스키마도 impact_krw를 REAL로 둔다).
b.Property(a => a.ImpactKrw).HasConversion<double>();
```

→ `keyword_fact.Revenue`·`AdCost`, `keyword_score.RevenueSum` 등은 전부 `HasConversion<double>()`.

**② `DateTimeOffset`은 전역 변환이 이미 걸려 있다** — `ConfigureConventions`(:49-53)의 `DateTimeOffsetToBinaryConverter`가 새 엔티티에 자동 적용됩니다.

**③ `DateOnly`는 명시 변환이 관습이다** — `AutomationPolicy.SpentDate`(:199-202)가 유일한 선례입니다. `"yyyy-MM-dd"` 문자열은 **사전순 정렬이 날짜순과 일치**해 `WHERE StatDate >= @from` 범위 질의가 그대로 됩니다. 이게 이 형식을 쓰는 진짜 이유입니다.

**④ 유니크 인덱스는 테이블 최초 생성 시점에만 안전하다**

```csharp
// DbSeeder.cs:59-66

catch (Microsoft.Data.Sqlite.SqliteException) { /* 이미 존재하는 스키마 요소 — 무시하고 계속 */ }
```

데이터가 있는 테이블에 유니크 인덱스를 나중에 붙이면 중복 행 때문에 실패하는데, 이 `catch`가 조용히 삼켜 **인덱스 없이 계속 돕니다.** 유일키가 중복 합산 방어의 전부인 팩트 테이블에서는 치명적입니다.

> **결정 6.** `keyword_fact`의 유니크 인덱스는 **테이블을 처음 만들 때 함께** 넣습니다. 이후 유일키 변경은 "테이블을 지우고 다시 임포트"로만 합니다. 그리고 K-9에 `PRAGMA index_list("KeywordFacts")` 확인을 넣습니다 — 인덱스가 실제로 있는지 코드가 확인하지 않으면 아무도 모릅니다.

**⑤ `UNIQUE NULLS NOT DISTINCT`가 없다 — 센티널로 대체한다**

13의 `uq_fact`는 `product_channel_map_id`가 NULL(STORE grain)인 행들을 같은 것으로 취급해야 합니다. SQLite는 NULL을 서로 다른 값으로 봐서 **중복 행이 무제한으로 쌓입니다.**

> **결정 7.** `keyword_fact.ListingId`를 nullable로 두지 않습니다. `Guid` 비-nullable에 **`Guid.Empty`를 "상품에 붙지 않은 행"의 센티널**로 씁니다. 의미는 `Grain` 컬럼이 말합니다.

생성 컬럼(`COALESCE(x,0)`)이 아니라 센티널인 이유: `DbSeeder`가 `GenerateCreateScript()`를 재작성해 실행하므로(DbSeeder.cs:46-56) **EF 모델이 표현할 수 있는 것만 스키마가 됩니다.** 센티널은 EF가 그냥 컬럼 하나로 봅니다.

**⑥ 관계형 내비게이션을 만들지 않는다** — `HasOne`/`WithMany`/`HasForeignKey`가 리포 전체에서 0건입니다. FK 대신 `Guid` 컬럼 + `HasIndex`. 안 그러면 `GenerateCreateScript`의 테이블 생성 순서 문제가 생깁니다.

**⑦ NOT NULL 컬럼을 나중에 추가하면 빈 값이 들어간다** — `BackfillNullsAsync`(:119-128)가 숫자면 `0`, 아니면 `''`를 넣습니다. → **나중에 추가할 가능성이 있는 지표 컬럼은 전부 nullable로 둡니다.** 이건 §2.4의 "NULL은 미제공"과 우연히 같은 방향입니다.

**`ReportImport`** — 리포트 파일 한 부의 적재 이력.
`TenantId, ChannelCode, ReportType,` **`Grain, TrafficType, CoverageScope, PeriodType, TopN?, RevenueBasis, AttributionDays?`**(← `ReportType`에서 복사)`, PeriodStart, PeriodEnd, FileName, FileHash, HeaderFingerprint, EncodingName, RowTotal, RowLoaded, RowUnmatched, RowReplaced, Status('LOADED'|'REVERTED'), Note?, ImportedAt`

`FileHash`는 `CsvParsed.Checksum`([CsvImporter.cs:365](../../src/Tetragon.Application/Services/Import/CsvImporter.cs))입니다 — :154의 정적 헬퍼 `Checksum(byte[])`이 계산해 :119에서 레코드에 싣습니다. 지금은 응답 JSON에만 나가고 저장되지 않습니다(ImportEndpoints.cs:100). **여기가 그 소비처입니다.** 다만 재업로드 차단으로서의 실효는 제한적입니다 — 재다운로드한 파일은 해시가 거의 항상 다릅니다(13 §5.4-A). 이 유니크가 막는 것은 "같은 파일을 실수로 두 번"이고, 기간 겹침의 실질 방어는 §3.6의 키 단위 대체입니다.

**튜플을 복사해 저장하는 이유**: `ReportTypes` 카탈로그는 코드 상수이고 실계정 확인에 따라 값이 바뀝니다. 그때 **이미 적재된 팩트의 판정 근거가 소급해서 바뀌면 안 됩니다** — 어제까지 `DEAD`가 아니던 것이 오늘 `DEAD`가 되고 아무도 이유를 설명할 수 없습니다. 복사본이 그 시점의 진실입니다. `RevenueBasis`(부가세 포함 여부)·`AttributionDays`(광고 전환 기여 기간)도 같은 이유로 복사합니다 — 13 §5.4-I가 "이걸 모르고 합산하면 매출 비교가 무의미해진다"고 못박은 두 값이고(C-7·C-19), §6.2의 근거 문장이 이 값을 인용합니다.

**`ReportCoverage`** — `TenantId, ChannelCode, StatDate, TrafficType, CoverageScope, ImportId, CreatedAt`
"이 채널의 이 날짜에 이런 종류의 관측이 있었다"의 한 행. **§9.1 커버리지 카드와 "지금 무엇을 판정할 수 있는가" 안내문의 근거**입니다. 단, `DEAD`의 관측 근거로는 쓰지 않습니다 — 그건 아래 `ReportListingDay`의 일입니다.

**`ReportListingDay`** — `TenantId, ChannelCode, ListingId, StatDate, TrafficType, CoverageScope, ImportId, CreatedAt`
"그 날 그 임포트에 **이 리스팅의 행이 1건이라도 있었다**"의 한 행 — **§3.7의 급소**입니다. 초안은 커버리지를 채널 축으로만 두고 "FULL 리포트에 없는 상품 = 그 날 유입 0"이라고 추론했는데, 그 전제("FULL = 유입 있던 상품 전부 수록")는 C-2와 같은 **미확인 가정**이고 셀러가 상품·카테고리·기간을 필터해 내려받는 순간 깨집니다 — 상품 3개만 담긴 "전량" 리포트 17일치가 나머지 리스팅 전부의 `covered` 키워드를 `DEAD`로 만듭니다(13 §13 하드 요구 위반). 그래서 **`DEAD`의 관측일은 채널 커버리지가 아니라 이 테이블로 정의합니다**: "그 날 이 리스팅이 리포트에 실렸는가." 귀결 — 리포트에 한 번도 안 실린 리스팅(유입 0 상품)은 `DEAD`가 나오지 않습니다. 안전한 방향의 손실입니다. §2.5의 "지표 전부 0/NULL 행 스킵" 최적화보다 **먼저**, 스킵 전 행에서 (리스팅, 날짜)를 뽑아 기록합니다 — 스킵과 관측이 분리돼야 스킵이 판정을 오염시키지 않습니다.

**`ChannelListingKey`** — `TenantId, ChannelCode, ListingKey, ListingId, CreatedAt`
미매칭 행을 사람이 연결한(§8 `unmatched/link`) 결과의 기억. 이게 없으면 다음 임포트에서 같은 `listingKey`가 또 미매칭이 됩니다 — 13 F-04의 수동 해결은 지속성을 전제합니다. `MatchListing`의 2.5단이 여기를 봅니다(§3.6).

**`PeriodType='WEEK'` 리포트는 커버리지도 관측일도 만들지 않습니다** — 주간을 7일로 전개하면 관측하지 않은 6일에 대해 관측했다고 주장하게 됩니다. ESM은 어차피 `TOP_N`이라 `DEAD`에 못 쓰므로 손해도 없습니다.

**`ReportImport`의 해시만 유니크가 아닌 이유**를 따로 적어 둡니다. 같은 파일 재업로드 차단은 필요하지만 그것을 **DB 제약으로 걸면 §3.4의 되돌리기가 죽습니다** — 되돌린 임포트의 행은 `Status='REVERTED'`로 남으므로, 같은 파일을 다시 올리는 순간 새 `ReportImport` INSERT가 유니크에 걸려 SQLite Error 19가 납니다. `force`는 §3.6 의사코드의 앱 레벨 검사만 건너뛸 뿐 DB 제약은 못 뚫습니다. 유니크에 `Status`를 넣어 살리는 방법도 있지만, 그러면 "되돌리지 않은 같은 파일"이 두 번 들어오는 것만 막고 세 번째부터는 다시 뚫립니다 — 제약이 표현하려는 사실이 애초에 유일성이 아닙니다. 그래서 **차단은 앱 레벨 하나로 통일합니다**: 인덱스는 조회용 일반 인덱스로 두고, `Status='LOADED'`인 같은 해시가 있으면 409, `force=true`면 통과(§3.6). 이 제약이 막으려던 것(기간 겹침 중복 합산)의 실질 방어는 어차피 §3.6의 키 단위 대체입니다.

보존은 09의 규약을 따릅니다: `keyword_fact` 25개월(전년 동월 비교, ESM 4주 롤링은 우리가 안 지우면 어디에도 없다) · `report_coverage`·`report_listing_day` **팩트와 같이 25개월**(팩트만 남고 관측 기록이 없으면 과거 판정을 재현할 수 없다) · `report_import` 무기한(메타만) · **`listing_snapshot`·`listing_keyword` 무기한**(이게 해자다) · `keyword_score` 갱신형. 13 §5.4-J의 `raw_row`는 만들지 않습니다 — 재처리는 "되돌리고 다시 올린다"(§3.4)로 대신하고, 부수 효과로 **검색어에 혼입된 개인정보가 원문 그대로 남는 표면(13 R14)이 아예 안 생깁니다.**

행 수 추정: 리스팅 3,000 × 유입 키워드 평균 8 × 90일 ≈ 216만 행 + `report_listing_day` 3,000 × 관측일(분기 최대 27만 행). 09가 이미 `listing_perf` 750만 행을 예고했으므로 **둘을 합치면 PostgreSQL 전환 트리거에 먼저 닿습니다.** 완화책도 09와 같습니다 — **지표가 전부 0이거나 NULL인 행은 적재하지 않습니다.** 그래도 "안 실렸다"와 "0이다"의 구분은 유지됩니다. 그 구분은 `keyword_fact`가 아니라 `report_listing_day`·`report_coverage`가 하기 때문입니다(§3.7). 이게 §2.3의 설계가 벌어 주는 두 번째 이익입니다.

숨은 비용 하나를 적어 둡니다: `DbSeeder.BackfillNullsAsync`(DbSeeder.cs:119-128)는 **기동할 때마다** 모든 NOT NULL 컬럼에 `UPDATE … WHERE col IS NULL` 전량 스캔을 돕니다. 216만 행 팩트 테이블에서는 그 비용이 앱 기동 시간에 그대로 붙습니다 — 팩트 테이블의 비-nullable 컬럼을 최소로 두는(§2.3 — 지표 전부 nullable) 또 하나의 이유입니다.

③ **탭 구분 감지** — `ParseCsv`(:222)가 쉼표만 처리해 `.tsv`가 안 읽힙니다.

이 셋 밖의 프레임 — `CsvImporter`의 검증·프로파일·지문, `ImportProfileStore`, `ImportProfileRepository`, DI, DbSet — 은 그대로입니다: 전부 `purpose`를 문자열로만 다루고 `import_profiles.Purpose`는 TEXT입니다.

### 3.2 CSV 컬럼과 업로드 파라미터의 경계

> **행마다 달라지는 값은 CSV 컬럼, 파일 전체에 공통인 값은 업로드 파라미터.**

| 값 | 어디서 | 왜 |
|---|---|---|
| `keyword` `listingKey` `date` 지표 7종 | CSV 컬럼 | 행마다 다르다 |
| `channel` | 업로드 파라미터 | 파일이 어느 채널 것인지 파일 안에 안 적혀 있다 |
| `reportType` | **업로드 파라미터 (사람이 고른다)** | 아래 |
| `grain` `trafficType` `coverageScope` `periodType` `topN` `revenueBasis` `attributionDays` `rowFilter` | `reportType`에서 **유도** | §3.3 |
| `periodStart` `periodEnd` | 업로드 파라미터 (기본 = 파일 안 날짜의 min/max) | 주간 리포트는 행에 날짜가 없다 |

**위 표는 `keyword` 목적의 것입니다.** `perf` 목적에는 `reportType` 카탈로그가 없으므로(§3.3의 4종은 전부 키워드 리포트다) 유도할 원천도 없습니다 — 결정 1의 `trafficType`은 **`perf` 업로드 파라미터로 직접 받습니다**(`ORGANIC`|`AD`|`MIXED`, 기본값 없음 — 고르지 않으면 400). 원칙은 같습니다(파일 전체 공통값은 파라미터). 다른 것은 경유지뿐입니다: `keyword`는 `reportType`을 거치고 `perf`는 직행합니다. K-5는 이 파라미터를 받아 행마다 기록하는 것까지가 범위입니다.

**`coverageScope`를 CSV에서 추정하지 않는 이유**: 리포트 파일 안에는 "이게 상위 5개만이다"라는 정보가 없습니다. ESM 키워드 분석 파일은 그냥 5행짜리 표이고, 전량 리포트에 마침 키워드가 5개인 것과 파일만 봐서는 구분되지 않습니다. **사람이 어느 메뉴에서 내려받았는지가 유일한 근거**이고, 그건 `reportType`을 고르는 행위로만 표현됩니다.

### 3.4 적재 계층 — 지금 없는 것을 만든다

> **결정 8.** 목적별 전용 라우트가 아니라 **공통 커밋 + 로더 디스패치**로 갑니다.

```csharp
private static decimal? DecOrNull(ImportRow r, string f) => r.Text(f) is null ? null : r.Number(f);
```

### 3.6 재적재·겹침·중복 — 키 단위 대체와 단일 트랜잭션

```
  spec = ReportTypes.Find(options["reportType"])          없으면 400
```

**왜 DELETE→INSERT가 아닌가.** 초안은 (채널·grain·기간유형·유형·날짜범위)로 기존 팩트를 `DELETE`하고 새로 넣는 설계였는데, 두 가지가 동시에 틀립니다. ① 같은 4튜플의 **부분 리포트가 서로를 지웁니다** — 쿠팡 광고를 캠페인 A·B 두 파일로 나눠 올리면 두 번째 커밋의 DELETE가 첫 파일의 팩트를 전부 지우고, `loaded`는 정상으로 보이고, 살아남은 커버리지 행이 사라진 키워드들을 "관측했는데 안 나왔다"로 바꿔 `DEAD`의 근거를 만듭니다. ② `ExecuteSqlRaw`의 DELETE는 자동 커밋이라 그 뒤 `SaveChangesAsync`가 실패하면(위 유니크 충돌이 정확히 그 경우) **기존 데이터만 소실**됩니다 — 초안이 선례로 든 `WalletRepository.SaveAsync`([Repositories.cs:81-85](../../src/Tetragon.Infrastructure/Persistence/Repositories.cs))는 `SaveChanges` 한 번의 원자성일 뿐 선행 raw DELETE를 덮지 못합니다. 키 단위 대체는 둘 다 피합니다: **파일에 없는 키는 건드리지 않고, 모든 쓰기가 한 트랜잭션입니다.** `BeginTransaction`은 리포 전체에서 히트 0건 — 이 로더가 첫 명시 트랜잭션이고, 커버리지·관측일 기록에 `INSERT OR IGNORE` 원시 SQL 대신 차집합 Add를 쓰는 이유도 트랜잭션 밖 쓰기를 만들지 않기 위해서입니다. 수만 행의 변경 추적 비용은 **배치 동안 `ChangeTracker.AutoDetectChangesEnabled = false`**로 눌러줍니다.

**대체 의미론의 한계 하나를 기록합니다.** 같은 키가 **서로 다른 부분 파일에 걸치면**(캠페인 A·B 둘 다 같은 키워드·아이템·날짜를 담으면) 나중 파일이 앞 파일의 그 키를 대체합니다. 합산으로 바꾸면 정정 재다운로드를 올릴 때 2배가 되므로 합산은 답이 아닙니다 — 대체가 정정 재업로드(주 용도)에 맞는 의미론입니다. 응답의 `replaced > 0`이 부분 파일 신호이고, 화면은 그 노트를 그대로 보여줍니다: "기존 행 n건을 대체했습니다 — 파일을 나눠 받았다면 전체 기준으로 다시 내려받아 올리세요"(§13-13).

**상품 매칭 `MatchListing` 폴백**

| 순서 | 근거 | 조건 |
|---|---|---|
| 1 | `externalSku` → `Product.Variants[].VariantId` | ITEM grain(쿠팡). `Variants`가 JSON 컬럼(TetragonDbContext.cs:69)이라 역인덱스가 없으므로 **커밋 시작 시 전체를 메모리 사전으로 한 번** 만든다 |
| 2 | `listingKey` → `Listing(MarketCode, MarketItemId)` | §0.2 #2의 인덱스. **파일의 모든 `listingKey`를 모아 한 번에 로드**해 사전을 만든다(09 §2.1과 같은 방식) |
| 2.5 | `listingKey` → `channel_listing_key` | 과거에 사람이 연결한 키(§2.3). 13 F-04의 수동 해결은 지속성을 전제한다 |
| 3 | 실패 | `Guid.Empty` + `unmatched++`. 화면에서 수동 연결 → `channel_listing_key`에 기록 |

수동 연결(§8 `unmatched/link`)이 기존 `Guid.Empty` 행을 실제 리스팅으로 바꿀 때, 같은 uq_fact 키의 매칭된 행이 이미 있으면 **§4.5 3단계와 같은 합산·삭제 절차를 재사용합니다** — 절차 없이 재지정하면 유니크 위반으로 `SQLite Error 19`만 남습니다.

상품명 유사도 매칭(13 §F-04 3단)은 **하지 않습니다** — 스냅샷 이전 리스팅에는 대조할 원문이 없고(§1.5), 있는 리스팅은 1·2·2.5단에서 잡힙니다.

### 3.7 ★ "판정 보류"를 코드에서 어떻게 표현하는가

13 §16 결함 ③이 지적한 오작동(관측 부재를 유입 0으로 읽어 잘 팔리는 키워드를 제거)을 막는 장치를 **네 층**으로 겁니다. 한 층이 뚫려도 나머지가 막습니다.

**① 자료구조 — 팩트의 부재는 아무 뜻도 없다**

```
"이 키워드가 이 상품에 안 들어왔다" 라고 말하려면:
   ① report_listing_day 에 (channel, listing, d, ORGANIC, FULL) 행이 있어야 하고
                                          ← 그 날 이 리스팅이 실제로 리포트에 실렸다
   ② 그 d 가 등록(REGISTERED) 스냅샷 이후여야 하고
                                          ← 상품이 존재하기 전을 관측했다고 세지 않는다
   ③ 그 d 에 keyword_fact 에 (listing, keyword) 행이 없어야 한다   ← 안 나왔다
   ①·② 없이 ③은 아무 의미가 없다.
```

`keyword_fact`는 **있었던 것만** 담고, 없었던 것의 의미는 `report_listing_day`(리스팅 축)와 `report_coverage`(채널 축, 화면용)가 정합니다. 이 분리 덕에 §2.5의 "0행 스킵" 같은 최적화가 판정을 오염시키지 않습니다.

**② 열거형의 기본값 — 판정하지 않으면 자동으로 보류**

`KeywordScore.GapClass`의 초기값이 `UNKNOWN`입니다. 배치가 분기를 하나 빠뜨리면 그 행은 `DEAD`가 아니라 `UNKNOWN`이 됩니다. **실수의 방향이 안전한 쪽입니다.**

**③ 타입 — `DEAD`를 만드는 경로를 하나로 좁힌다**

```csharp
// src/Tetragon.Application/Services/Keywords/DeadVerdict.cs
/// <summary>
/// DEAD 판정을 만들 수 있는 유일한 경로 (13 §F-07 "유효 음성 관측").
///
/// DEAD는 셀러가 상품명에서 키워드를 지우게 만드는 판정이고 오판하면
/// 매출에 직접 손해를 입힌다(13 §16 결함 ③). 그래서 배정 지점을 한 군데로 좁힌다 —
/// GapClasses.Dead 문자열이 이 파일 밖에 나타나면 코드 리뷰에서 잡는다(§12.3).
/// </summary>
public readonly record struct DeadVerdict
{
    public bool IsDead { get; }  public int OrganicFullDays { get; }  public string Basis { get; }

    public static DeadVerdict Evaluate(
        bool covered,
        string snapshotSource,                           // SnapshotSources — REGISTERED만 통과 (§1.2)
        DateOnly snapshotDate,                           // 등록 스냅샷의 날짜
        IReadOnlyCollection<DateOnly> organicFullDays,   // report_listing_day에서 온, 이 리스팅이 실린 날짜들
        IReadOnlyCollection<DateOnly> observedDays,      // 그 창 안에서 키워드가 등장한 날짜들
        int keywordCharLength, int requiredDays = 14)
    {
        if (!covered) return new(false, 0, "상품명·태그에 없는 키워드는 DEAD 대상이 아닙니다.");
        if (snapshotSource != SnapshotSources.Registered) return new(false, 0,
            "등록 원장이 아니라 백필 스냅샷입니다 — 등록 시점을 모르므로 죽었다고 판정하지 않습니다.");
        // ★ 등록보다 앞선 관측일은 버린다. 채널에 FULL 21일이 쌓여 있어도 이 리스팅이
        //   어제 등록됐으면 n=1이다 — 등록 전에는 이 상품이 존재하지도 않았으므로
        //   "관측했는데 안 나왔다"가 성립하지 않는다 (13 §16 결함 ②, §F-07 "t는 팩트의 stat_date").
        var n = organicFullDays.Count(d => d >= snapshotDate);
        if (n < requiredDays) return new(false, n,
            $"등록 후 이 상품이 실린 오가닉 전량 관측이 {n}일치뿐입니다({requiredDays}일 이상 필요). 판정을 보류합니다.");
        var seen = observedDays.Count(d => d >= snapshotDate);
        if (seen > 0) return new(false, n,
            $"등록 후 오가닉 전량 관측 {n}일 중 {seen}일에 유입이 있었습니다.");
        return new(true, n,
            $"등록 후 오가닉 전량 관측 {n}일 중 한 번도 등장하지 않았습니다. 상품명에서 {keywordCharLength}자를 차지하고 있습니다.");
    }
}
```

`organicFullDays`가 어떻게 채워지는지가 가드의 전부입니다.

```csharp
// KeywordAnalyzer 내부 — 이 질의가 AD_ONLY·TOP_N·미수록 리스팅을 구조적으로 배제한다
var organicFull = await listingDays.DaysAsync(channelCode, listingId,   // ★ 리스팅 축 (§2.3)
    today.AddDays(-21), today,                //   리포트에 이 리스팅이 없던 날은 아예 안 나온다
    trafficType:   TrafficTypes.Organic,      // ← 광고 리포트는 여기서 탈락
    coverageScope: CoverageScopes.Full, ct);  // ← 상위 N 리포트는 여기서 탈락
```

**쿠팡 광고 보고서만 올린 상태에서 `organicFull`은 빈 목록이 됩니다.** `n = 0 < 14` → `IsDead = false`, 근거 문장에 "오가닉 전량 리포트가 0일치뿐입니다"가 남습니다. 13 §13이 "목표가 아니라 하드 요구"라고 한 **"AD_ONLY 리포트만 있을 때 DEAD 0건"이 조건문이 아니라 데이터 흐름에서 성립합니다.**

**④ `Confirmed=false` 리포트는 어떤 판정도 만들지 않는다**

```
if (!spec.Confirmed)
    → GapClass = UNKNOWN
      GapBasis = "이 리포트의 커버리지 범위가 실계정으로 확인되지 않았습니다 (13 §14 C-2)."
```

13 §8.1의 "확인 전까지 해당 리포트로는 `UNKNOWN` 분류만 생성합니다"를 코드 상수 하나로 옮긴 것입니다. C-2가 확인되면 `Confirmed: true` 한 글자를 고칩니다.

**판단 근거**: ③만 있어도 오늘의 요구는 충족됩니다. 그런데 ③은 사람이 고칠 수 있는 코드이고 ①은 데이터가 없으면 답이 안 나오는 구조입니다. **가드는 고치기 어려운 층에 둘수록 오래 삽니다.**

```csharp
/// 같은 개념이 서로 다른 norm_key로 갈라졌다.
/// </summary>
public static NormalizedKeyword Normalize(string raw)
{
    var text = CollapseSpaces(ToHalfWidth(raw.Normalize(NormalizationForm.FormC))
        .ToLowerInvariant().Trim());                     // ①NFC ②전각→반각 ③소문자 ④공백 축약
    // ⑤ 어절 목록을 구분자 제거 전에 뽑는다. 이게 없으면 "무선 마우스 패드"가
    //    "무선마우스패드"가 되어 경계를 가로지르는 매칭을 걸러낼 수 없다(§5.2).
    var segments = text.Split([' ', '-', '_', '.', '/'], RemoveEmptyEntries)
        .Select(KeepAllowedChars)                        // ⑦ 화이트리스트: 한글·영문·숫자
        .Where(s => s.Length > 0).ToList();
    return new NormalizedKeyword(raw.Trim(), string.Concat(segments), segments);  // ⑥ 구분자 제거
}

/// <param name="Segments">구분자로 나뉜 어절. 토크나이저의 입력이자 경계의 근거.</param>
public sealed record NormalizedKeyword(string CanonText, string NormKey, IReadOnlyList<string> Segments);
```

**분절** — 어절마다 사전 최장일치.

```
tokenize(segments, dict):
    tokens = []
    for seg in segments:
        i = 0
        while i < len(seg):
            matched = null
            for L in range(min(MaxTermLength, len(seg) - i), 1, -1):     # 긴 표제어부터
                if seg[i : i+L] in dict: matched = seg[i : i+L]; break
            if matched: tokens.append(matched); i += len(matched)
            else:
                # 사전에 없다. 남은 어절 전체를 한 토큰으로 두고 끝낸다 —
                # 한 글자씩 쪼개면 아무 상품명에나 부분집합이 성립한다
                tokens.append(seg[i:]); break
    return distinct(tokens)
```

`dict`는 `HashSet<string>` + `MaxTermLength`면 충분합니다(후보 수가 어절 길이 × 최대 표제어 길이로 묶입니다).

**13의 반례 검증**

| 입력 | 결과 |
|---|---|
| L(p) = `캠핑 롤탑 테이블 우드 접이식` | segments 전부가 사전 표제어(그 상품명 자체가 사전의 출처) → tokens 동일 |
| k = `우드테이블` | 사전에 `우드테이블`이 없고 `우드`가 있음 → `우드` 매칭 후 남은 `테이블` 매칭 → `{우드, 테이블}` |
| 판정 | `{우드, 테이블} ⊆ {캠핑, 롤탑, 테이블, 우드, 접이식}` → **covered ✅** |

n-gram이 실패하는 지점을 사전 최장일치가 통과합니다. 사전에 `우드`와 `테이블`이 있는 이유는 **그 상품명 자체가 사전에 기여했기 때문**입니다 — 이 순환이 성립하는 것이 (d)를 고른 근거입니다.

## 5. 갭 분석 엔진

### 5.1 투입 집합 `L(p, t)`

```
L(p, t) = ⋃ tokens(lk.Keyword)   for lk in listing_keyword  where lk.SnapshotId = snapshot(p,t).Id

snapshot(p, t) = ListingSnapshots
    .Where(s => s.ListingId == p
             && s.Source is SnapshotSources.Registered or SnapshotSources.Backfilled
             && s.TakenAt <= t)
    .OrderByDescending(s => s.TakenAt).FirstOrDefault()
  → null 이면 이 (상품, 날짜)의 모든 판정은 UNKNOWN (§1.5)
```

**`t`는 하나가 아닙니다 — 팩트는 자기 `stat_date`의 스냅샷과 조인합니다**(13 §F-07: "`t`는 팩트의 `stat_date`"). 스냅샷 기계를 만들어 놓고 알고리즘이 `t = today` 하나로만 부르면 기계가 무의미해집니다 — 상품명을 바꾼 다음 날, 바꾸기 전의 유입이 "지금 넣은 키워드의 유입"으로 소급되거나(Phase C에서 제안을 적용하면 다음 날 "방금 넣은 키워드가 죽었다"가 나오는 경로) 그 반대가 됩니다. §5.3의 어느 판정이 어느 시점의 스냅샷을 쓰는지가 그 절에 명시돼 있습니다.

`BACKFILLED`가 투입 집합에 들어가는 이유: 그것은 **현재 마켓에 실제로 걸려 있는 문자열**이라 `covered`("지금 상품명에 있는가")의 근거로 정확합니다. `DEAD`로는 못 갑니다 — `DeadVerdict`의 소스 가드가 막습니다(§3.7 ③).

**슬롯을 구분하지 않고 합칩니다** — 13 §F-07의 정정 그대로입니다. `TITLE`만 보면 `slot='TAG'` 키워드가 판정에서 통째로 탈락해 태그 키워드가 영원히 `DISCOVERED`로 오분류됩니다. 슬롯은 판정이 아니라 **제안**에서만 씁니다.

**`Source='MANUAL'` 스냅샷은 투입 집합의 근거가 되지 않습니다.** `UpdateAsync` 호출자가 0개라 사람이 상품명을 고쳐도 마켓에 반영되지 않고, 반영되지 않은 상품명의 토큰을 "투입했다"고 세면 **실제로 마켓에 없는 키워드가 `DEAD`로 판정됩니다.**

### 5.2 커버리지 판정

```
covered(k, p, t)  ⟺  tokens(k) ⊆ L(p, t)
```

`tokens(k)`는 `Keyword.Tokens`에 저장돼 있고 `L(p,t)`는 스냅샷당 한 번 계산해 캐시합니다.

**보조 신호는 단독 근거가 아니다** — `AhoCorasickMatcher`로 `snapshot.Title`에서 `keyword.NormKey`를 찾을 수 있지만, 이건 토큰 분절이 실패했을 때의 보정으로만 씁니다.

```
if (!covered && matcher.Match(normalizedTitle).Contains(keyword.NormKey))
    → covered = true, confidence = LOW, GapBasis 에 "문자열 일치로만 확인" 을 남긴다
```

13 §F-07이 경고한 어절 경계 오탐은 이 보조 경로에서만 일어납니다. `NormalizedKeyword.Segments`(§4.3 ⑤)로 경계를 알고 있으므로 **매칭 구간이 두 어절에 걸치면 이 보정을 적용하지 않습니다.**

### 5.3 분류 알고리즘

```
Analyze(listing, channel, window = 90d, today):

    snap = snapshot(listing, today)                     # REGISTERED 또는 BACKFILLED (§5.1)
    if snap == null:
        for k in observed(listing, window):
            emit(k, UNKNOWN, "등록 원장이 없습니다.")
        return

    L           = tokens_of(snap)                                        # §5.1
    snapDate    = date(snap.TakenAt)
    organicFull = listingDays.Days(channel, listing, today-21, today, ORGANIC, FULL)
                                                        # ★ 리스팅 축 관측 (§2.3, §3.7 ③)
    totalInflow30d = perf.InflowSum(listing, today-30, today, ORGANIC)   # 09 listing_perf
    θ_c            = max(3, 0.005 * totalInflow30d)
    candidates     = facts.Keywords(listing, channel, today-window, today)
                     ∪ listing_keyword.Keywords(snap.Id)                 # 회수 ∪ 투입

    for k in candidates:
      for tt in [ORGANIC, AD]:                          # ★ 3차원: (p, k, traffic_type)
        spec = importSpecOf(k, listing, tt)

        # ⓪ 미확인 리포트에서 온 것은 판정하지 않는다 (§3.7 ④)
        if spec != null and not spec.Confirmed:
            emit(k, tt, UNKNOWN, "리포트 커버리지 미확인 (13 §14 C-2)"); continue

        rows    = facts(k, listing, tt, today-window, today)    # NULL 지표 행은 합산·분모 제외
        clicks  = Σ rows.Clicks;  orders = Σ rows.Orders;  revenue = Σ rows.Revenue
        cov     = covered(k, snap)                              # 현재 스냅샷 기준
        # ★ 팩트는 자기 stat_date의 스냅샷과 조인한다(§5.1). 지금 커버됐다고 과거 유입까지
        #   소급해 "의도한 유입"이 되지 않고, 방금 넣은 키워드가 과거 구간 때문에
        #   DISCOVERED로 남지도 않는다. window 안에 스냅샷 구간이 여러 개면
        #   그 사실을 GapBasis에 남긴다 ("스냅샷 2개 구간에 걸친 판정입니다").
        uncovClicks = Σ (rows where not covered(k, snapshot(listing, row.StatDate))).Clicks

        if cov and orders >= 1:                                          # ① VERIFIED
            emit(k, tt, VERIFIED, "{window}일간 클릭 {clicks}회 · 주문 {orders}건 · 매출 {revenue}원"); continue
        if not cov and uncovClicks >= θ_c:                               # ② DISCOVERED
            if matcher.Match(k.NormKey).Count > 0:                       #   금칙어·브랜드 게이트 (§5.6)
                emit(k, tt, DISCOVERED_BLOCKED,
                     "유입은 실측이지만 상표 확인이 필요한 키워드입니다 (14 §5.2.2)"); continue
            emit(k, tt, DISCOVERED,
                 "상품명·태그에 없는데 {window}일간 클릭 {uncovClicks}회가 들어왔습니다 (임계 {θ_c})"); continue
        if cov and clicks >= 30 and orders == 0:                         # ③ WATCH
            emit(k, tt, WATCH, "클릭 {clicks}회에 주문 0건 — 키워드가 아니라 가격·썸네일 문제입니다"); continue

        # ④ DEAD — 유일한 경로. 광고 유입에는 적용하지 않는다
        if tt == ORGANIC:
            observedDays = facts.Days(k, listing, ORGANIC, organicFull)
            v = DeadVerdict.Evaluate(cov, snap.Source, snapDate,
                                     organicFull, observedDays, k.CharLength)
            emit(k, tt, v.IsDead ? DEAD : UNKNOWN, v.Basis)   # 보류여도 Basis를 남긴다
            continue

        emit(k, tt, UNKNOWN, "판정에 필요한 관측이 부족합니다.")         # ⑤ 나머지 전부 보류
```

**`facts.Sum`의 NULL 처리**: `Clicks`가 NULL인 행은 합산에서 제외하고 **분모(관측 일수)에서도 제외**합니다. NULL을 0으로 더하면 "채널이 클릭을 안 준다"가 "클릭이 0이다"가 되어 ②·③의 임계 비교가 무너집니다.

**`θ_c`의 분모가 09에서 옵니다.** `listing_perf`가 비어 있으면 `θ_c = 3`으로 떨어집니다 — 13 v1.0의 고정값과 같아지지만 **틀린 값이 아니라 보수적인 값**이라 안전합니다.

### 5.5 VKS와 빼는 것

```
CVR_smoothed = min(1.0, (orders + α·CVR_prior) / (clicks + α))
               α = 20, CVR_prior는 traffic_type별로 따로.
               min(1.0): 광고 전환 기여 기간(AttributionDays) 때문에 orders > clicks인
               날이 실제로 있다(13 §9.1 "orders > clicks 방어"). 클리핑 없이는 백분위와
               전환율 표기가 깨진다 — 기여기간 시프트 정렬은 하지 않으므로 이게 방어의 전부다.
Recency      = 0.5 ^ (days_since_last_click / 30)         클릭 이력 없으면 0
VKS          = 100 · Recency · (0.30·P(clicks) + 0.40·P(CVR_smoothed) + 0.30·P(revenue))

P(x)의 모집단 = (CategoryCode × 채널 × traffic_type)      CategoryCode는 KeywordScore에 있다(§2.3)
  n < 30 이면 (채널 × traffic_type) → 그래도 n < 30 이면 채널 전체로 폴백 (13 §5.4-G)
```

> **결정 11.** `expected_gain`(13 §9.2 — `clicks × uplift_factor(0.3) × confidence`)을 **구현하지 않습니다.**
> 근거: 13 스스로 "상수뿐 아니라 함수 형태도 미검증"이라고 적었고, `AttentionScan`의 규약과 정면 충돌합니다 — "**실측이 없는 항목의 영향 금액은 0으로 두고 그 사실을 근거 문장에 적는다.** 상수를 지어내면 그 상수가 목록의 순서를 정하게 되고, 순서가 곧 운영자의 하루가 된다"([AttentionScan.cs:19-21](../../src/Tetragon.Application/Services/AttentionScan.cs)). `uplift_factor = 0.3`이 정확히 그 지어낸 상수입니다. 대신 §6.2에서 **이미 실측된 매출**을 영향 금액으로 씁니다.

`VKS`는 목록 정렬에만 쓰고 원장에는 넣지 않습니다 — 백분위 기반이라 원(₩) 단위가 아니고, `ImpactKrw`는 원 단위여야 다른 kind와 같은 줄에 설 수 있습니다.

### 5.6 발굴 키워드의 금칙어 게이트 — `DISCOVERED_BLOCKED`

실측 유입 상위에는 **구조적으로 타사 브랜드가 섞입니다** — "다이슨 청소기"를 검색하고 우리 무명 청소기를 산 사람은 늘 있습니다. 거르는 장치 없이 그 키워드를 §9.2에 "넣지 않았는데 들어온 검색어"로 보여주고 §6.2에서 매출 원장 카드로 승격시키면, **도구가 상표권 침해를 권장하는 모양**이 됩니다. 13 R9가 이것을 🔴(상표권 + 채널 제재)로 두고 금칙어 필터를 필수(P1-12)로 못박았고, 14 §5.2.2는 상품명 상표권 침해를 계정 정지 1순위 위험(위험도 16 🔴, R1-2a — "브랜드명·○○st·○○풍 표기")으로 둡니다. 초안은 "사전·매처가 이미 있다"며 이 공수를 0으로 지웠는데, 있는 것은 부품이지 **키워드 경로에 연결된 필터가 아닙니다.**

게이트는 그 부품으로 만듭니다 — `ComplianceRule.Keyword` 사전(시드 16건, ComplianceEngine.cs:61-79)을 `AhoCorasickMatcher`([Compliance.cs:39-102](../../src/Tetragon.Domain/Compliance/Compliance.cs), `Match(string)` :89)로 통과시켜, 걸리면 `DISCOVERED` 대신 **`DISCOVERED_BLOCKED`**를 냅니다(§5.3 ②). 근거 문장: "유입은 실측이지만 상표 확인이 필요한 키워드입니다 — 확인 없이 상품명에 넣으면 계정 정지 사유가 될 수 있습니다(14 §5.2.2)." `DISCOVERED_BLOCKED`는 **원장(§6.1)에 올라가지 않고** §9.2 진단 화면에 ⚠ 배지로만 나옵니다. KIPRIS 확인은 사람의 일이고 도구가 대신할 수 없습니다 — 14의 면책 고지가 그은 선입니다. 시드 16건은 시작점일 뿐이라 사전 확장은 운영 절차입니다(§13-14).

### 6.2 `ImpactKrw` 산식과 근거 문장

| kind | `ImpactKrw` | `ImpactBasis` |
|---|---|---|
| `keyword.discovered` | **그 상품의 발굴 키워드가 최근 30일간 실제로 만든 매출의 합** | "상품명·태그에 없는 검색어 7개로 최근 30일간 클릭 214회·주문 9건·매출 271,000원이 들어왔습니다. 상품명에 넣으면 늘어난다는 보장은 없지만, 지금 이만큼이 이름 밖에서 오고 있습니다." |
| `keyword.discovered` (매출 0) | **0** | "…클릭 62회가 들어왔지만 주문은 0건입니다. 금액으로 환산할 근거가 없어 0으로 둡니다." |
| `keyword.dead` | **0** | "상품명에 있는 검색어 3개가 오가닉 전량 리포트 17일 중 한 번도 등장하지 않았습니다. 제거로 회수되는 것은 상품명 24자입니다 — 금액으로 환산할 근거가 없어 0으로 둡니다." |

**`discovered`의 금액이 "얻을 금액"이 아니라 "이미 이 키워드에 걸려 있는 금액"인 것이 요점입니다.** 상품명에 넣으면 얼마가 늘어나는지 우리는 모릅니다. 아는 것은 지금 이 검색어가 이만큼을 만들고 있고 그게 **우리 의도 없이** 만들어지고 있다는 사실입니다. 그 숫자가 크면 손볼 가치가 크다 — 이건 실측입니다.

**`dead`가 항상 0인 것이 옳습니다.** 죽은 키워드를 지워서 버는 돈은 없고 글자수가 회수될 뿐입니다. 결과적으로 `dead` 항목은 목록 맨 아래에 깔립니다 — **그게 정확한 우선순위입니다.**

합산 하나에 주석이 필요합니다. `discovered`의 금액은 채널·traffic이 섞인 원화 합인데, 쿠팡 광고 전환 매출(기여기간 n일)과 네이버 오가닉 매출은 같은 원이 아닙니다 — 그리고 이 합이 정렬 순서, 즉 `OpenManyAsync`가 영향 금액 내림차순으로 상한을 배분하는 그 순서(:81-87)를 정합니다. 그래서 **`Detail`에 traffic_type별 분해를 싣고, 광고 매출이 섞이면 근거 문장에 "광고 전환 매출은 기여 기간 {n}일 기준"을 덧붙입니다**(`ReportImport.AttributionDays`, §2.3). 완전한 해결(기준 통일)은 불가능하고, 무엇이 섞였는지 문장에 남기는 것이 할 수 있는 전부입니다.

### 6.3 `DedupKey` — 상품 단위로 묶는다

```
keyword.discovered → "kw.disc:{marketCode}:{listingId}"      SubjectType = "listing"
keyword.dead       → "kw.dead:{marketCode}:{listingId}"      SubjectId   = listingId
```

키워드 단위가 아닌 이유 둘. ① **조치의 단위가 상품입니다** — 운영자가 하는 일은 "상품명 한 번 고치기"이지 "키워드 하나 넣기"가 아닙니다. 항목이 조치와 1:1이 아니면 목록이 할 일 목록이 아니라 사실 목록이 됩니다. ② **상한 때문입니다** — 상품 하나에 발굴 키워드가 20개면 항목 20건이고, 리스팅 3,000개면 첫 스캔에서 수만 건이 나와 대부분이 접힙니다. 그리고 **접힌 항목에서 개별 항목으로 내려가는 경로가 없습니다**(`FoldAsync`가 `Detail`에 `foldedKind`와 `count`만 남깁니다, [AttentionLedger.cs:228-231](../../src/Tetragon.Application/Services/AttentionLedger.cs)).

개별 키워드는 `Detail`에 실어 보냅니다 — `listingId`, `marketCode`, `keywordCount`, `topKeywords`(상위 5개), `clicks30d`, `orders30d`.

**`busy_timeout`이 어디에도 없습니다** — `DbSeeder`가 켜는 것은 WAL뿐입니다(DbSeeder.cs:16). 임포트 커밋은 이제 쓰기 트랜잭션이므로(§3.6) 시간당 스윕과 겹치면 `SQLITE_BUSY`가 납니다. WAL을 켜는 그 자리에 `PRAGMA busy_timeout = 5000`을 한 줄 더하고, K-9에 "임포트 커밋 중 스윕이 돌아도 BUSY가 안 난다"를 넣습니다(§11.3).

### 7.3 레이트리밋과 자격증명

13은 3 QPS 준수를 요구합니다. 리포에서 조절기가 있는 유일한 선례는 쿠팡입니다.

`NaverSearchAdThrottle`은 이 구조를 복사하고 `MinInterval`도 **350ms 그대로** 씁니다 — 3 QPS는 334ms이므로 350ms면 안전측이고, 두 조절기가 같은 상수를 갖는 편이 나중에 공통화하기 쉽습니다. `MaxConcurrent`는 1로 낮춥니다(등록과 달리 리포트 폴링은 급하지 않습니다).

자격증명은 `market:{code}` 관용구 그대로 `credentials.GetAsync("market:naver-searchad", ct)`([Handlers.cs:394](../../src/Tetragon.Application/Pipeline/Handlers.cs))입니다. `market:smartstore`와 분리하는 이유: 검색광고 계정과 커머스 계정은 별개이고 하나를 지우면 다른 하나가 죽으면 안 됩니다. **필요한 값은 `api_key`/`secret_key`/`customer_id`뿐이고 판매자 ID/PW는 요구하지 않습니다** — `CredentialEntry.SecretsJson`이 평문 저장이고([TetragonDbContext.cs:297-304](../../src/Tetragon.Infrastructure/Persistence/TetragonDbContext.cs) 주석: "프로덕션에선 KMS/Envelope 암호화로 교체"), 13 §2.5 결정 2가 이를 아키텍처 제약으로 못박았습니다(§12).

### 7.4 `AD_ONLY`는 코드에 박는다

`ReportType`이 프로퍼티이고 호출자가 정할 수 없습니다. `ReportTypes.NaverSaKeyword`의 스펙이 `AdOnly`·`Ad`이므로(§3.3) 이 소스가 만든 팩트는 **`DEAD` 판정 질의에서 구조적으로 탈락합니다**(§3.7 ③). 요청 파라미터로 받으면 언젠가 잘못된 값이 들어옵니다.

### 7.5 상품ID 매핑 — 이번에는 풀지 않는다

13 §11 P3-2가 남긴 문제입니다: 검색광고 API의 상품ID와 커머스API의 `originProductNo`(우리가 `Listing.MarketItemId`에 저장하는 값, SmartStoreAdapter.cs:114-117)가 매핑되지 않습니다.

> **결정 14.** 매핑을 시도하지 않습니다. 검색광고 API 팩트는 **`Grain='STORE'`, `ListingId = Guid.Empty`로 적재**합니다.
> 근거: 13이 제시한 해결책 중 "NV_MID 대조"는 13 §2.5 결정 3(타 셀러 데이터 미수집)과 충돌하고, 나머지는 C-16 확인에 달려 있습니다. **확인되지 않은 매핑으로 상품에 팩트를 붙이면 엉뚱한 상품의 진단이 오염됩니다.** 스토어 스코프로 두면 §9.1의 스토어 목록에는 나오고 상품별 진단에는 안 나옵니다 — 정확히 우리가 아는 만큼입니다.

C-16이 확인되면 소스가 `RawKeywordRow.ChannelProductNo`를 채우고 로더의 2단 매칭(§3.6)이 그대로 받습니다. **계약을 바꿀 필요가 없습니다** — 이게 `ChannelProductNo`를 nullable로 둔 이유입니다.

**적재만 되고 아무도 못 보는 데이터를 만들면 안 됩니다.** `ListingId = Guid.Empty` 팩트는 리스팅 루프(§5.3)에 잡히지 않으므로, 배치 ③b(§6.5)가 **(채널 × 키워드 × traffic_type) 단위로 별도 집계**해 `KeywordScore`에 `ListingId = Guid.Empty` 행으로 Upsert합니다 — `covered`가 정의되지 않으므로 gap_class는 전부 `UNKNOWN`이고, 매출·클릭 정렬용 지표만 실립니다. 소비처는 §9.1의 "스토어 단위" 섹션과 `GET /api/v1/keywords?scope=store`(§8)입니다. 13 §9.1의 "STORE grain은 별도 모집단으로 계산하고 S-3에 절대 섞지 않는다"가 이 분리입니다 — 상품별 진단(§9.2)에는 나오지 않습니다.

```csharp
/// ★ string.GetHashCode()를 쓰면 안 된다 — .NET Core 3.0부터 문자열 해시가
///   프로세스마다 랜덤화되어, 앱을 재시작하면 같은 상품이 다른 Arm으로 간다.
///   그러면 배정이 무작위가 아니라 "재시작할 때마다 바뀌는 것"이 되고 실험이 무의미해진다.
/// </summary>
public static int AssignArm(string salt, Guid productId, int armCount)
{
    var hash = SHA1.HashData(Encoding.UTF8.GetBytes($"{salt}:{productId:N}"));
    return (int)(BinaryPrimitives.ReadUInt32BigEndian(hash.AsSpan(0, 4)) % (uint)armCount);
}

/// <summary>
/// 층 키 — 가격 구간 × 공급처. 층 안에서만 해시로 나눈다.
/// 층화하지 않으면 비싼 상품이 한쪽 Arm에 몰려 유입 차이가 상품명이 아니라 가격에서 온다.
/// </summary>
public static string Stratum(Product product) =>
    $"{PriceBand(product.BasePrice.Amount)}|{product.Source.SupplierCode}";
```

`Product.Source.SupplierCode`는 `SourceRef`([ValueObjects.cs:56](../../src/Tetragon.SharedKernel/ValueObjects.cs))에서 옵니다.

### 10.3 측정

```
metric(assign) = Σ listing_perf.Clicks
                 where TrafficType = 'ORGANIC'
                   and StatDate in [assign.WindowFrom , assign.WindowTo]

WindowFrom = date(등록 스냅샷.TakenAt) + BurnInDays(7)      ★ 상품별 등록일 기준
WindowTo   = WindowFrom + ObserveDays(14)                   등록 성공 시점에 Assign에 기록
```

**창은 실험 시작일이 아니라 상품별 등록일에 겁니다.** 배정은 `ListingRequested`마다 일어나므로 상품은 실험 기간 내내 계속 등록됩니다 — 실험 시작일 고정 창(`[started+7d, started+21d]`)을 쓰면 늦게 등록된 상품의 유효 관측일이 0이 되어 metric이 0으로 집계되고, **Arm 평균이 "상품명 패턴"이 아니라 "언제 등록됐나"의 함수**가 됩니다. burn-in을 두는 근거(초기 노출 부스트는 등록 시점의 함수)와 정확히 같은 이유로, 측정 창도 등록 시점의 함수여야 합니다. 앵커는 `ListingSnapshot.TakenAt`입니다 — `Listing`에는 등록 시각 컬럼이 없습니다(§1.1의 전 필드 목록). **창이 아직 닫히지 않은 상품은 표본에서 제외합니다.**

burn-in 7일을 판정에서 제외하는 이유: 신규 등록 상품은 초기 노출 부스트를 받는 것으로 알려져 있고, 그 구간의 유입은 상품명이 아니라 등록 시점의 함수입니다.

> **결정 15.** 등록 실험은 **네이버 전용**입니다. 오가닉 유입을 상품 단위로 주는 리포트가 네이버뿐이고, 쿠팡은 광고 유입만 확보돼 있습니다. 광고 유입으로 상품명 효과를 측정하면 **입찰가의 함수를 상품명의 함수로 오독합니다.** 따라서 등록 실험은 **C-2가 확인되기 전까지 켤 수 없습니다.**

### 10.4 통계 — Arm 2개로 제한한다

> **결정 16.** Arm은 **2개까지**만 허용합니다.
> 근거: 13 §7.3의 확정 절차(Kruskal-Wallis → Dunn → Holm-Bonferroni → HL + 부트스트랩)를 .NET에서 쓰려면 직접 구현해야 하는데(통계 라이브러리 의존성이 없습니다) **리포에 테스트 프로젝트가 없습니다.** 검증할 수 없는 다중비교 보정은 잘못된 p값을 자신 있게 보여줍니다 — 데이터가 없는 것보다 나쁩니다. Arm 2개면 Mann-Whitney U 하나로 끝나고 보정 자체가 필요 없습니다.

```
U 검정 (동점 보정 포함):
  1. 두 Arm의 metric을 합쳐 순위 매김 (동점은 평균 순위)
  2. U1 = R1 − n1(n1+1)/2,   U = min(U1, U2)
  3. μ = n1·n2/2
     σ² = n1·n2/12 · [ (N+1) − Σ(tᵢ³−tᵢ)/(N(N−1)) ]      ← 동점 보정
     z = (U − μ)/σ
  4. p = 2·(1 − Φ(|z|))       Φ는 표준정규 CDF (erf 근사 30줄)
  5. 효과크기: Hodges-Lehmann = median{ x − y : x∈A, y∈B }, CI는 부트스트랩 2,000회
```

**동점 보정이 필수인 이유: 유입수 분포는 0이 압도적으로 많습니다.** 보정 없이 쓰면 σ가 과대평가되어 p값이 보수적으로 나오고 실제 차이를 놓칩니다.

**평가 시점은 고정 날짜가 아닙니다** — **두 Arm 모두 "창이 닫힌 표본"(§10.3)이 `MinArmSize`에 도달한 시점**입니다. 고정 날짜(`StartedAt + 21d`)를 쓰면 그날까지 창이 안 닫힌 상품을 버리거나 0으로 세는 것 중 하나를 강요당합니다. 도달 전에는 p값을 응답에 넣지 않습니다 — API가 `null`을 돌려주고 화면은 Arm별 "닫힌 표본 n / 필요 50"만 보여줍니다. 13 v1.0이 18일차에 p값을 노출해 optional stopping을 유발한 것을 그대로 피합니다. 등록 유량이 적어 영영 도달하지 못하면 실험을 `EXPIRED`로 닫고 "결론 없음"을 그대로 표기합니다. `MinArmSize` 기본값은 **50**이고 화면에 `(추정)`을 붙입니다(MDE 근거가 없다고 13이 자백했습니다). **표기는 평균이 아니라 중앙값 + IQR + HL 위치이동 + CI**입니다 — 유입 분포는 극단적 롱테일이라 평균이 상위 1개 상품에 끌려갑니다.

## 12. 배제 결정 — 자동 로그인 스크래핑

### 12.1 왜 지금 못박는가

13 §2.5가 "마케팅 문구가 아니라 아키텍처 제약"으로 못박은 첫째가 "채널 어드민 자동 로그인·스크래핑 코드를 리포지토리에 넣지 않는다"입니다. **이 리포에서 그 유혹이 특히 강한 이유는 도구가 이미 있기 때문입니다.**

```csharp
// src/Tetragon.Plugin.Abstractions/BrowserFetch.cs:20-27
public interface IBrowserFetcher
{
    bool IsAvailable { get; }
    Task<BrowserFetchResult> FetchAsync(BrowserFetchRequest request, CancellationToken ct);
}
```

`BrowserFetchRequest`는 `CookieHeader`(:50), `SessionKey`(:46), `BehaviorProfile.Human`(:60), `AllowCaptchaSolve`(:44)를 이미 갖고 있습니다. 구현체는 DI에 등록돼 있고([HttpBrowserFetcher.cs:18](../../src/Tetragon.Infrastructure/External/HttpBrowserFetcher.cs), [DependencyInjection.cs:106](../../src/Tetragon.Infrastructure/DependencyInjection.cs)) Playwright 사이드카가 리포 안에 있습니다(`tetragon-fetch/`). 즉 **"판매자센터도 이걸로 긁으면 리포트 업로드가 필요 없지 않나"가 반드시 나옵니다.** 그때 근거가 문서에만 있으면 집니다.

### 12.2 코드 수준 경계 4개

**① 이 기능의 코드는 `IBrowserFetcher`를 주입받지 않는다.** `Tetragon.Application.Services.Keywords.*`, `Tetragon.Application.Services.Import.*`, `Tetragon.Domain.Keywords.*`, `Tetragon.Plugins.Markets.*KeywordSource`의 어떤 타입도 생성자에 `IBrowserFetcher`를 갖지 않습니다.

**② 판별의 근거를 스키마가 아니라 소비처에 둔다** — 초안은 "`MarketCredential`에 판매자 ID/PW 필드를 추가하지 않는다. 필드가 없으면 저장할 자리도 없다"고 썼는데, **그 집행은 성립하지 않습니다.** `MarketCredential`에는 타입 필드가 아예 없습니다 — 전체 정의가 `public sealed record MarketCredential { public Dictionary<string,string> Secrets { get; init; } = []; … }`([Marketplace.cs:278-285](../../src/Tetragon.Plugin.Abstractions/Marketplace.cs))인 자유형 key/value 가방이고, 저장도 `CredentialEntry.SecretsJson` TEXT JSON 블롭(TetragonDbContext.cs:302)이라 `Secrets["seller_pw"]`로 아무 키나 들어갑니다. `Order`에 개인통관고유부호 필드가 없어 보관 자체가 불가능한 것과는 구조가 다릅니다 — 그쪽은 스키마가 집행하고, 이쪽은 스키마가 집행할 수 없습니다. 그래서 경계는 두 겹으로 다시 긋습니다: (a) §7.1의 "공식 API + 발급된 API 키로만 동작한다"를 계약 주석에 박고, (b) 이 기능의 코드는 `api_key`/`secret_key`/`customer_id` **세 키만 읽습니다**(§7.3) — 다른 키는 읽는 코드가 없으므로 넣어도 죽은 값이고, §12.3 체크리스트는 "필드가 추가됐는가"(볼 수 없는 것) 대신 **자격증명을 읽고 쓰는 코드의 키 이름 문자열**(볼 수 있는 것)을 봅니다.

**③ 자격증명 스코프에 로그인 정보를 넣지 않는다** — `market:naver-searchad`가 담는 것은 `api_key`/`secret_key`/`customer_id`뿐입니다(§7.3). `SecretsJson`이 평문이므로 여기에 판매자 비밀번호를 넣는 것은 개인정보보호법 「안전성 확보조치 기준」의 일방향 암호화 원칙과 정면 충돌합니다. **평문 저장이라는 현재 상태가 이 경계를 더 절박하게 만듭니다.**

**④ 업로드 경로를 유일한 오가닉 확보 수단으로 둔다** — `coverage_scope='FULL'` 팩트가 들어오는 경로는 **CSV 업로드 하나뿐**입니다. API 소스는 `AD_ONLY`로 고정돼 있고 그 고정이 프로퍼티라 호출자가 못 바꿉니다(§7.4). 누군가 스크래핑을 붙이려면 `ReportTypeSpec`을 새로 만들고 `Confirmed: true`를 손으로 켜야 합니다 — **리뷰에서 반드시 보이는 변경입니다.**

### 12.3 경계선의 정의와 리뷰 체크리스트

`IBrowserFetcher`는 계속 씁니다. 잘라내지 않습니다. 차이는 하나입니다.

| | 공급처 수집 (계속 쓴다) | 판매자센터 (쓰지 않는다) |
|---|---|---|
| 대상 | 1688·타오바오·쿠팡 **상품 페이지** | 판매자센터·WING·ESMPLUS **어드민** |
| 인증 | 비로그인 공개 페이지 | **로그인 뒤 우리 계정 화면** |
| 약관 | 비회원에게 적용 안 되는 영역 | 판매자 본인이 **명시 동의한 회원 약관** |
| 기술적 보호조치 | Akamai (봇 일반) | 로그인 + 2FA + 채널이 공지로 명시한 차단 |
| 대체 경로 | **없다** | **있다** — 셀러가 직접 내려받아 올리면 된다 |

**마지막 줄이 결정적입니다.** 공급처 수집은 대체 경로가 없어 기술적 우회가 기능의 전제입니다. 판매자센터는 대체 경로가 있고 그 경로가 이 설계의 §3 전체입니다. **대체 경로가 있는데 우회하는 것은 필요가 아니라 편의입니다.** 그리고 13의 실사가 이를 지지합니다 — 네이버는 2024-03-27부터 스마트스토어센터의 기계적 접근을 시스템으로 차단하고 대안으로 커머스API를 지정했고, 쿠팡은 2026-03-19부터 판매자 2FA를 SMS로 일원화했습니다(SMS 2FA는 자동화가 구조적으로 불가능합니다). 소송보다 먼저 오는 것은 IP·계정 차단이고, 셀러 계정이 정지되면 클레임은 우리에게 옵니다.


세 번째부터 다섯 번째는 스크래핑과 무관해 보이지만 같은 이유로 여기 있습니다 — **DEAD 판정과 커버리지 확정은 매출에 직접 손해를 입힐 수 있는 지점**이고, 그 경로는 좁을수록 좋습니다.

## 13. 이 설계가 틀릴 수 있는 지점

1. **카탈로그 사전 최장일치(§4.3)의 오탐률을 모릅니다.** `우드테이블` 반례는 통과하지만 사전이 자기 카탈로그에서 자라므로 **처음 보는 키워드에 취약합니다.** 사전에 없는 어절은 통째로 한 토큰이 되고 `covered`가 false가 되어 `DISCOVERED`로 잡힙니다. 즉 **오탐의 방향이 "이미 있는 걸 또 넣으세요"입니다** — 13 R18이 n-gram 폴백에 대해 경고한 것과 같은 오류를 다른 경로로 낼 수 있습니다. K-0의 실파일로 첫 100건을 손으로 검증하기 전까지 `DISCOVERED` 자동 제안을 켜지 마십시오.

2. **13 §F-07이 "어절 경계 오탐"이라 부른 것은 폴백의 결함이 아니라 부분집합 판정의 성질입니다.** `무선마우스` → `{무선, 마우스} ⊆ {무선, 마우스, 패드}`는 형태소 분석기를 써도 성립합니다. §5.2의 보조 신호 강등은 문자열 매칭 경로만 막을 뿐 토큰 경로는 못 막습니다. **이 오탐은 이 설계에 남아 있습니다.** 완화책(핵어 일치 요구)을 검토했지만 한국어 상품명은 어순이 뒤죽박죽이라 핵어 추출을 신뢰할 수 없어 넣지 않았습니다.

3. **`listing_perf`를 `product_traffic_fact` 대신 쓰기로 한 결정 1은 09가 아직 없어 검증되지 않았습니다.** 09가 나중에 이 테이블에 리프라이싱용 컬럼을 더하며 스키마를 바꾸면, `DbSeeder`는 컬럼 추가만 되고 타입·제약 변경은 못 합니다(DbSeeder.cs:37-38). 09를 쓰는 사람이 이 문서를 안 읽으면 충돌합니다.

4. **`θ_c`의 분모가 비어 있는 상태로 오래 갈 수 있습니다.** `listing_perf`가 채워지려면 셀러가 성과 리포트를 따로 올려야 하는데, 키워드 리포트만 올리고 성과 리포트는 안 올릴 가능성이 큽니다. 그러면 `θ_c = 3` 고정이고 트래픽이 큰 상품에서 노이즈 키워드가 대량으로 `DISCOVERED`가 됩니다.

5. **`WATCH`의 임계값 30(§5.3)과 `DeadVerdict`의 21일/14일에 근거가 없습니다.** 13에서 그대로 가져왔고 13도 근거를 대지 않았습니다. 특히 리포트를 매일 올리는 셀러는 없으므로 실제로는 `n ≥ 14`가 거의 안 나올 가능성이 큽니다 — 그리고 관측일이 리스팅 축이 되면서(§2.3) 조건은 더 엄격해졌습니다: 유입이 적은 상품은 리포트에 실리는 날 자체가 적어 `n`이 잘 안 찹니다. 그러면 `DEAD`는 이론상 존재하지만 실무에서 한 번도 안 나오는 기능이 됩니다. 안전한 방향이긴 하나 **기능을 만든 인일이 낭비였다는 뜻**이 될 수 있습니다.

6. **스냅샷 입도를 상품 레벨로 정한 근거(§1.2)는 `searchTags = BuildSearchTags(payload)` 한 줄에 걸려 있습니다**([CoupangAdapter.cs:289](../../src/Tetragon.Plugins.Markets/CoupangAdapter.cs)). 누군가 이걸 `BuildSearchTags(payload, v)`로 바꿔 아이템별 태그를 만들면 스냅샷이 조용히 손실 있는 표현이 됩니다. 주석은 달았지만 강제 수단이 없습니다.

7. **`InjectedBy.Supplier` vs `Pipeline` 판별(§2.3)이 `BuildSearchTags`의 내부 순서에 의존합니다.** 공급처 값 → 브랜드 → 상품명 보충 순서(CoupangCategory.cs:373-390)가 바뀌면 판별이 틀립니다. 그리고 이 판별로 내는 통계가 13 §13이 "이 기능이 존재할 이유의 유일한 증명"이라고 한 숫자입니다.

8. **`ExternalSku` 기반 쿠팡 ITEM 매칭(§3.6 1단)이 실제로 되는지 모릅니다.** 우리가 `externalVendorSku = v.VariantId`를 보내는 것은 확인했지만(CoupangAdapter.cs:276) **광고 보고서에 그 컬럼이 실려 나오는지는 K-0에서만 확인됩니다.** 안 실리면 쿠팡 광고 팩트가 전부 미매칭이 되고, MVP의 유일한 확실한 데이터 소스가 상품에 붙지 않습니다. **이 설계에서 가장 큰 단일 위험입니다.**

9. **`AttentionPolicy.DailyOpenCap = 30`이 kind별 고정이고 설정으로 뺄 수 없습니다**(`AddSingleton<AttentionPolicy>()`에 configuration 바인딩이 없습니다, DependencyInjection.cs:48). 상품 단위로 묶어 항목 수를 줄였지만(§6.3) 리스팅 3,000개 중 발굴 키워드가 있는 것이 500개면 여전히 470건이 접히고, **접힌 항목에서 개별 항목으로 내려가는 경로가 없습니다.**

10. **`decimal?`에 `HasConversion<double>()`이 실제로 동작하는지 확인하지 않았습니다**(§2.4). 리포에 nullable decimal을 REAL로 저장하는 선례가 없습니다. 안 되면 프로퍼티 타입을 `double?`로 바꿔야 하고, 그러면 도메인 타입이 저장소 사정에 오염됩니다.

11. **배치를 워커 인스턴스 필드로 게이트한 결정 13은 프로세스가 자주 재시작되면 무너집니다.** 재시작할 때마다 전 리스팅 갭 분석이 다시 돌고, 그동안 시간당 스윕이 밀립니다.

12. **C-2가 확인되지 않으면 이 설계의 절반이 실행되지 않습니다.** `DEAD`도, 등록 실험도(결정 15), 오가닉 `DISCOVERED`도 오가닉 전량 리포트를 전제합니다. 확인 결과가 "네이버는 검색 채널까지만 주고 키워드 원문은 안 준다"이면 남는 것은 **광고 키워드 기준 `DISCOVERED`와 `VERIFIED`**뿐입니다. 여전히 가치는 있지만 13이 약속한 것의 절반입니다. **K-0을 첫 티켓으로 올린 이유가 이것입니다.**

13. **부분 파일 대체 의미론(§3.6)은 셀러가 응답 노트를 읽는다는 데 기댑니다.** 같은 키가 걸친 부분 파일을 나눠 올리면 나중 파일이 앞 파일의 그 키를 대체하고, `replaced > 0`이 화면에 나오지만 노트를 읽지 않으면 조용한 손실과 구분이 안 됩니다. 합산으로 바꾸면 정정 재업로드가 2배가 되므로 이 방향을 골랐지만, 실사용에서 캠페인별 부분 다운로드가 일반적이라는 것이 K-0에서 확인되면 uq_fact에 축을 하나 더하는 재설계가 필요합니다.
