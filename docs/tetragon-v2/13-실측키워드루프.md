## 0. 한 장 요약

**하려던 것**: 아이템스카우트 같은 툴이 주는 *이론적 추정 검색량* 대신, 대량등록으로 실제 판매가 일어난 상품의 *실측 유입 키워드*를 확인한다.

**실사 결과**: 방향은 맞습니다. 국내 서드파티 키워드 툴 중 **셀러 본인 계정의 실측 유입 키워드를 연동 분석해 주는 사례는 확인되지 않았고**, 시장 전체가 네이버 검색광고 API 추정치 위에 서 있습니다. 공백은 실재합니다.

**다만 최초 가정 하나를 수정해야 합니다.** "통계 데이터를 프로그램이 자동으로 긁어오면 된다"는 전제는 성립하지 않습니다.

- 네이버 커머스API에 **상품별 유입 검색어 API가 없습니다.** 유사 기능인 `API데이터솔루션(통계)`는 브랜드스토어 전용이며 2026-03-17부터 신규 구독이 중지되어 리뉴얼 대기 중입니다.
- 쿠팡 오픈API에는 **통계·검색어 엔드포인트가 0개**입니다(11개 API 패밀리 전수 확인).
- 11번가·ESM 어느 쪽도 **통계/키워드 API를 제공하지 않습니다.**
- 네이버는 **2024-03-27부터 스마트스토어센터에 대한 기계적 접근을 시스템적으로 차단**하고 있고, 쿠팡은 **2026-03-19부터 판매자 2단계 인증을 SMS로 일원화**했습니다. 어드민 자동 로그인 스크래핑은 기술적으로 막히는 중이며, 법적으로도 정보통신망법 제48조·부정경쟁방지법 제2조 제1호 카목 4호(형사)에 정면으로 노출됩니다.

**따라서 채택 구조는 "업로드 퍼스트(Upload-First)"입니다.** 셀러가 각 채널에서 직접 내려받은 리포트 파일을 드래그&드롭하면 파싱·정규화하고, 여기에 자동화가 합법적으로 가능한 **네이버 검색광고 API**를 붙입니다. 자동 로그인은 아키텍처에서 배제합니다.

**그리고 진짜 해자는 키워드 데이터 자체가 아닙니다.**

키워드 데이터만 놓고 보면 우리는 기껏해야 "셀러가 볼 수 있는 화면을 예쁘게 다시 보여주는 툴"입니다. 하지만 **대량등록 프로그램은 그 상품을 어떤 상품명·태그로 등록했는지 알고 있는 유일한 주체**입니다. 아이템스카우트는 셀러 계정을 연동해도 이걸 모릅니다.

> **투입(내가 넣은 키워드) × 회수(실제로 들어온 키워드) 조인 = 대량등록 툴만 계산할 수 있는 지표**

여기서 세 가지가 나옵니다.

| 분류 | 정의 | 액션 |
|---|---|---|
| **발굴 키워드** | 내가 안 넣었는데 유입·전환된 키워드 | 상품명/태그에 명시 삽입 → 순위 상승 |
| **죽은 키워드** | 상품명에 넣었는데 유입 0 | 제거 → 글자수 예산 회수 |
| **검증 키워드** | 넣었고 전환도 난 키워드 | 유지 + 동일 카테고리 신규 상품에 확산 |

> **⚠️ "죽은 키워드"는 조건부 기능입니다.** 광고 전용 리포트(쿠팡 광고, 네이버 검색광고 API)나 상위 N 절단 리포트(ESM 상위 5개)에서는 **"안 들어왔다"와 "리포트에 안 실렸다"를 구분할 수 없습니다.** 이걸 구분하지 않으면 오가닉으로 잘 팔리는 키워드를 셀러가 지우게 됩니다. 그래서 오가닉 전량 리포트가 확보된 경우에만 판정하고, 나머지는 `판정 보류`로 둡니다(§F-07). **C-2가 이 기능의 사활을 가릅니다(§14).**

여기에 대량등록의 구조적 이점이 하나 더 붙습니다. **수백~수천 개를 한 번에 올린다는 것은 곧 A/B 테스트 모수가 공짜로 생긴다는 뜻**입니다(§7 등록 실험).

**최종 그림 — 폐루프**

```
   대량등록 ──▶ 실제 판매 발생 ──▶ 채널 리포트 다운로드
       ▲                                    │
       │                                    ▼
   상품명/태그 재생성 ◀── 갭 분석 ◀── 업로드·파싱·정규화
   (검증 키워드 주입)      (투입×회수)      (실측 팩트 적재)
```

**개발 규모**: Phase 0 선행 27d → Phase 1 MVP 53d → Phase 2 58d = **138인일 ≈ 28주(1인 기준)**. Phase 3은 별도 34d ≈ 7주. v1.0의 "총 15주"는 티켓별 공수 합계(Phase 1만 46d)와 맞지 않아 전면 재산정했습니다(§11).

**착수 전 반드시 결정할 것 2가지**

1. **배포 형태** — 로컬 데스크톱형인가 서버 SaaS형인가(§5.1). 스키마·배치·인증·알림이 전부 여기서 갈립니다.
2. **C-2** — 네이버 통계가 **키워드 원문을 상품 단위로 주는가**(§14). 아니라면 Phase 1 MVP의 목표 자체를 다시 써야 합니다(§11 의사결정 게이트).

## 1. 배경과 문제 정의

### 1.1 기존 키워드 발굴 방식의 구조적 한계

현재 위탁판매 셀러의 표준 워크플로는 이렇습니다.

```
아이템스카우트/판다랭크에서 키워드 검색
  → 월간 추정 검색량·경쟁강도 확인
  → "이 키워드가 좋아 보인다" 판단
  → 상품명에 조합해서 대량등록
  → ??? (여기서 피드백이 끊깁니다)
```

문제는 마지막 화살표입니다. **등록 이후 실제로 어떤 키워드가 작동했는지를 확인하는 경로가 없습니다.** 그래서 다음 등록 배치도 다시 추정치에서 출발합니다. 100번을 등록해도 학습이 누적되지 않습니다.

이론 키워드의 구체적 한계는 다음과 같습니다.

| # | 한계 | 설명 |
|---|---|---|
| L1 | **추정치다** | 네이버 검색광고 API의 `monthlyPcQcCnt`/`monthlyMobileQcCnt`는 광고 노출 기반 추정이며, 검색량 10 미만은 숫자가 아니라 문자열 `"< 10"`으로 반환됩니다. 경쟁정도(`compIdx`)도 `높음/중간/낮음` 3단 구간값입니다. |
| L2 | **시장 평균이지 내 상품이 아니다** | "이 키워드로 월 5만 명이 검색한다"와 "내 상품이 그 키워드로 노출·클릭된다"는 완전히 다른 명제입니다. 노출 순위, 가격 경쟁력, 리뷰 수가 그 사이를 가릅니다. |
| L3 | **전환을 모른다** | 유입은 많은데 안 팔리는 키워드와, 유입은 적은데 확실히 팔리는 키워드를 구분할 수 없습니다. 위탁판매는 마진이 얇아 후자가 훨씬 중요합니다. |
| L4 | **모두가 같은 데이터를 본다** | 경쟁 셀러 전원이 동일한 툴에서 동일한 추정치를 봅니다. 그 키워드는 이미 레드오션입니다. |
| L5 | **롱테일이 안 보인다** | 실제 매출의 상당 부분은 검색량이 낮아 툴에서 필터링되어 사라지는 롱테일 조합어에서 발생합니다. |

### 1.2 실측 데이터가 메우는 지점

| 한계 | 실측 데이터의 답 |
|---|---|
| L1 추정치 | 채널이 집계한 실제 유입수·클릭수 |
| L2 시장 평균 | **내 상품에 실제로 들어온** 검색어 |
| L3 전환 미상 | 유입 대비 전환수·전환매출 |
| L4 공용 데이터 | 내 계정에서만 나오는 **비공개 1st-party 데이터** |
| L5 롱테일 | 실제 유입 로그에는 롱테일이 그대로 남습니다 |

특히 **L5는 위탁판매에서 결정적**입니다. 대량등록은 애초에 롱테일 전략이고, 실측 리포트는 롱테일 조합어를 있는 그대로 보여줍니다.

### 1.3 경쟁 지형 — 공백은 실재하나 이유가 있다

| 툴 | 데이터 소스 | 셀러 실측 연동 |
|---|---|---|
| 아이템스카우트 | 네이버쇼핑 크롤링 + 검색광고 API 추정 | 없음 |
| 판다랭크 | 네이버 계열 (소스 비공개) | 확인 안 됨 |
| 키워드사운드 | 네이버 검색광고 API (명시) | 없음 |
| 셀러라이프(셀록홈즈) | 쿠팡 공개 데이터 기반 AI 추정 (자체 고지 오차 10~20%) | 없음 |
| 셀링샷 | 네이버쇼핑 비공개 엔드포인트 추정 — **타인 스토어** 조회 구조 | 아니오 |
| 대량등록 계열(플레이오토·사방넷·샵링커·이지어드민) | 주문/재고/정산 API | 키워드 기능 자체 없음 |
| *(참고)* 지그재그 인사이트 | **플랫폼 1st-party** | **있음 — 단, 플랫폼이 직접 제공** |

두 가지를 읽어야 합니다.

1. **서드파티 중에는 없습니다.** 공백은 진짜입니다.
2. **지그재그는 플랫폼 본인이 '마이샵 키워드'(본인 스토어 유입 키워드 + 클릭수 추이)를 유료 상품으로 팔고 있습니다.** 이 데이터의 상업적 가치는 이미 검증됐다는 뜻이자, **데이터 소유자만이 안전하게 이 기능을 제공하고 있다**는 뜻이기도 합니다.

> **판단**: 차별성 = 높음. 지속가능성 = 수집 방식 선택에 전적으로 달림. 이 기획안의 나머지 전부가 그 선택에 대한 것입니다.

### 1.4 그런데 진짜 해자는 따로 있다

실측 키워드를 보여주는 것만으로는 부족합니다. 언젠가 네이버가 API를 열면 누구나 할 수 있고, 지그재그처럼 플랫폼이 직접 하면 우리는 밀려납니다.

**대량등록 프로그램만 가진 것은 "등록 원장"입니다.**

우리는 상품 A를 등록할 때 상품명에 `[무선 블루투스 이어폰 노이즈캔슬링 게이밍 저지연]`이라고 넣었다는 사실을 **DB에 갖고 있습니다.** 외부 키워드 툴은 셀러 계정을 100% 연동해도 이걸 모릅니다 — 채널 리포트에는 "무엇이 들어왔는가"만 있고 "무엇을 넣었는가"는 없기 때문입니다.

이 둘을 조인하는 순간 다른 누구도 계산할 수 없는 지표가 나옵니다.

```
투입 집합 L(p) = 등록 시 상품명·태그에 넣은 키워드
회수 집합 A(p) = 실제로 유입된 키워드

발굴(Discovered) = A(p) \ L(p)   ← 안 넣었는데 들어왔다. 명시하면 더 온다.
죽음(Dead)       = L(p) \ A(p)   ← 넣었는데 안 들어왔다. 글자수만 낭비 중.
검증(Verified)   = A(p) ∩ L(p)   ← 작동 확인. 다른 상품으로 확산.
보류(Unknown)                     ← 판정할 데이터가 없음. 실무에서는 이게 가장 많습니다.
```

**이것이 이 기능의 핵심이며, 모든 설계는 이 조인을 성립시키기 위해 존재합니다.**

### 2.2 이 표에서 나오는 설계 결론 5가지

**결론 ①  통계 API는 어느 채널에도 없다.**
네이버 검색광고 API 하나만 예외이며, 그마저 **광고 유입에 한정**됩니다. 오가닉 유입 키워드를 API로 받는 경로는 2026-08 현재 존재하지 않습니다.

**결론 ②  오가닉과 광고는 반드시 분리 저장해야 한다.**
광고 리포트(쿠팡 키워드 전환, ESM 파워클릭, 네이버 검색광고 API)는 **광고 유입만** 담습니다. 이걸 오가닉 데이터와 섞으면 "이 키워드가 잘 된다"는 결론이 사실은 "이 키워드에 돈을 썼다"가 됩니다. 팩트 테이블에 `traffic_type` 컬럼을 두고 UI에서도 배지로 구분합니다.

**결론 ③  채널마다 해상도가 다르므로 단일 스키마로 뭉개면 안 된다.**
ESM 키워드 분석은 **스토어 단위 / 주간 / 최근 4주 / 상위 5개**입니다. 이걸 "상품별 유입 키워드" 스키마에 억지로 넣으면 화면에서 거짓말을 하게 됩니다. `grain`(PRODUCT/STORE) 컬럼을 두고, 통합 뷰에서 해상도 배지를 강제 노출합니다.

**결론 ④  ESM은 4주 롤링이므로 스냅샷 누적이 곧 자산이다.**
ESM은 최근 4주치만 보여주고 지나간 데이터는 사라집니다. **주 1회 업로드를 습관화시키면 우리 DB에만 존재하는 장기 시계열이 쌓입니다.** 이건 채널도 안 갖고 있는 우리만의 데이터가 됩니다. 리마인더 기능(§6 F-11)이 여기서 나옵니다.

**결론 ⑤  리포트 컬럼 구조를 우리는 아직 모른다.**
실계정이 없어 엑셀 파일의 실제 컬럼명·헤더 위치·인코딩을 확인하지 못했습니다. **파서를 코드에 하드코딩하면 반드시 터집니다.** 컬럼 매핑을 외부 프로파일(JSON)로 빼고, 자동 감지 실패 시 수동 매핑 UI로 폴백하며, 그 매핑을 새 프로파일로 저장하는 구조가 필수입니다(§8).

### 2.3 네이버 데이터솔루션 — 지금은 닫혀 있지만 감시할 것

커머스API에 `API데이터솔루션(통계)` 그룹이 실재하고, 그 안에 `/external/v1/bizdata-stats/channels/{channelId}/marketing/...` 계열과 검색 키워드 성과 엔드포인트가 문서화되어 있는 정황이 있습니다. 그러나 네이버 운영자 공식 답변 기준:

- 2026-03-17 **신규 구독 중지**
- **브랜드스토어 전용** — "스마트스토어 또는 API대행사는 이용 불가" (2026-06-22)
- 2026년 6월경 서비스 종료 후 **리뉴얼 예정**
- 스마트스토어 '데이터분석' 탭 API는 **"제공 준비 중, 오픈 시점 미정"** (2026-07-10)

> **액션 아이템**: 커머스API 공지사항([GitHub Discussions 공지 카테고리](https://github.com/commerce-api-naver/commerce-api/discussions/categories/%EA%B3%B5%EC%A7%80%EC%82%AC%ED%95%AD))을 **주 1회 자동 모니터링**하고, 리뉴얼 오픈 시 **스마트스토어 대상 포함 여부**를 최우선 확인. 열리는 순간 Phase 3의 API 커넥터가 즉시 붙도록 어댑터 인터페이스를 미리 설계해 둡니다(§8.5).

### 2.4 ⚠️ 선행 필수 조건 — 채널 상품ID 회수

**이 조건이 충족되지 않으면 본 기능은 한 줄도 동작하지 않습니다.**

채널 리포트는 **채널이 부여한 상품ID**(네이버 `channelProductNo`/`originProductNo`, 쿠팡 `vendorItemId`/옵션ID, ESM 상품번호)로 나옵니다. 우리 대량등록 프로그램은 **자체 SKU**로 관리합니다. 이 둘을 잇는 매핑 테이블이 없으면 리포트를 파싱해도 어느 상품인지 알 수 없습니다.

확인해야 할 것:

- [ ] 현재 대량등록 시 채널 API 응답에서 **생성된 상품번호를 회수해 저장하고 있는가?**
- [ ] 저장하고 있다면 어느 테이블 어느 컬럼인가?
- [ ] **옵션(SKU) 단위 ID도 저장하는가?** — 쿠팡 비즈니스 인사이트와 광고 보고서는 옵션 단위입니다.
- [ ] 과거에 등록한 상품들은 매핑이 있는가, 없다면 **역추적 백필**이 가능한가? (채널 상품 목록 조회 API + 상품명 대조)

미저장이라면 **Phase 0(§11)에서 이것부터 해결**해야 합니다. 백필은 채널별 상품 목록 조회 API로 전체를 받아 상품명 유사도 매칭 + 수동 확인 UI로 처리합니다.

### 2.5 자동 수집(RPA)을 배제하는 이유

기획 초기에 자연스럽게 떠오르는 선택지지만, 실사 결과 채택하지 않습니다.

**기술적으로 막히고 있습니다.**

- 네이버: **2024-03-27부터** 스마트스토어센터 기계적 접근을 시스템 차단. 차단 시 "비정상적 요청이 감지되었습니다" 노출. 네이버는 공지에서 대안으로 커머스API를 지정했습니다.
- 쿠팡: **2026-03-19부터** 판매자 2FA를 **SMS로 일원화**(한국·일본·대만·중국·미국 동시 적용). 미설정 계정에도 SMS 인증이 기본 적용됩니다. **SMS 2FA는 자동화가 구조적으로 불가능**합니다.
- 쿠팡 프론트는 봇 매니저로 자동화 브라우저(Selenium/Playwright/Puppeteer)를 강하게 차단하는 것으로 알려져 있습니다.

**법적으로 위험합니다.** (참고 정보이며 법률 자문 아님)

| 법령 | 쟁점 |
|---|---|
| 정보통신망법 §48①  | "정당한 접근권한 없이 또는 **허용된 접근권한을 넘어**" 침입 금지. 대법원 2021도1533(여기어때 무죄)은 접근권한 부여 주체를 **"계정 명의자가 아니라 서비스제공자"**로 못박았습니다. **셀러 본인 동의로는 면책되지 않습니다.** |
| 부정경쟁방지법 §2 1호 카목 **4호** | **데이터 기술적 보호조치 무력화 — 이 유형만 형사처벌.** 2FA·캡차·봇 탐지 우회 로직을 넣는 순간 "어렵게 뚫었다"가 그대로 구성요건이 됩니다. |
| 부정경쟁방지법 §2 1호 카목 **2호** | 접근권한 있는 자가 부정한 이익 목적으로 데이터를 제3자에게 제공·사용. 특히 **여러 셀러 데이터를 집계해 "업계 벤치마크"로 재판매하면 리스크가 급상승**합니다. |
| 개인정보보호법 | 「안전성 확보조치 기준」상 비밀번호는 **복호화 불가능한 일방향 암호화** 저장이 원칙인데, 자동 로그인은 **원문 재사용이 필요해 양방향 암호화가 강제**됩니다. 규범과 기능이 정면충돌합니다. |
| 쿠팡 API 연동 협약서 §3③ | **"API 제공자의 시스템을 우회하여 API 호출"** 금지 — 윙 내부 XHR 리버스 엔지니어링에 직접 적용됩니다. 같은 조항이 **"주문 데이터 관리 외의 목적으로 DB 구축"**도 금지합니다. |

**여기어때 무죄를 방패로 쓸 수 없습니다.** 그 판결의 무죄 근거 3가지를 스마트스토어센터에 대입하면 전부 뒤집힙니다.

| 여기어때 무죄 근거 | 스마트스토어센터 현실 |
|---|---|
| 기술적 보호조치 없었음 | 로그인 + 2FA + **2024-03-27 기계적 접근 차단 시스템** |
| 비회원이라 약관 적용 안 됨 | 판매자는 **약관에 명시 동의한 회원 본인** |
| 명시적 접근차단 의사 부재 | **공지로 차단 방침 명시 + 대체 경로(커머스API) 지정** |

**그리고 소송보다 먼저 오는 것은 제품 사망입니다.** IP·계정 차단으로 기능이 하루아침에 죽고, 셀러 계정이 정지되면 고객 손해에 대한 클레임이 우리에게 돌아옵니다. 위탁판매 셀러에게 계정 정지는 사업 종료와 같습니다.

> **아키텍처 결정 (되돌리지 않음)**
> 1. 채널 어드민 **자동 로그인·스크래핑 코드를 리포지토리에 넣지 않는다.**
> 2. 셀러 계정 **ID/PW를 서버에 저장하지 않는다.** (API 키·토큰만, 로컬 암호화 보관)
> 3. **타 셀러·타 스토어 데이터를 수집하지 않는다.** 코드 레벨에서 차단하고 코드 리뷰 체크리스트에 넣는다.
> 4. 크로스-셀러 집계 데이터를 **외부 판매하지 않는다.**

1~4는 마케팅 문구가 아니라 **아키텍처 제약**입니다. 특히 ③은 위반 시 잡코리아 vs 사람인(확정 4.5억), 네이버페이 vs 다윈중개(2심 8천만원) 계열의 DB제작자권 침해로 카테고리가 바뀝니다.

### 3.3 C안의 유일한 약점과 그 해소

**약점**: 셀러가 주 1회 다운로드→업로드를 해야 합니다.

**해소 설계** (§6 F-10~F-12에서 구현):

1. **업로드 마찰 최소화** — 드래그&드롭 한 번. 채널·리포트 종류·기간을 파일에서 **자동 판별**. 여러 파일 동시 드롭 지원. 중복 파일은 해시로 자동 스킵.
2. **채널 바로가기** — 각 채널 리포트 다운로드 페이지로 가는 딥링크 + 3단계 스크린샷 가이드를 업로드 화면에 붙임. (링크 제공은 자동화가 아닙니다.)
3. **리마인더** — "ESM 키워드 데이터는 4주 후 사라집니다. 지난주 데이터를 아직 안 올리셨어요" 형태의 능동 알림. **소멸 경고가 가장 강력한 업로드 동기**입니다.
4. **업로드 가치의 즉시 시각화** — 업로드 직후 "발굴 키워드 12개 / 죽은 키워드 8개 발견, 예상 개선 상품 27개"를 즉시 보여줌. 마찰 대비 보상이 즉각적이어야 습관이 됩니다.
5. **폴더 감시(선택)** — 로컬 실행형이라면 셀러의 다운로드 폴더를 감시해 리포트 파일 패턴 감지 시 **"이 파일 가져올까요?" 토스트**. 자동 로그인이 아니라 로컬 파일 감시이므로 리스크가 없습니다.

> 5번은 UX상 사실상 자동에 가까운 체감을 주면서 법적 리스크는 0인 지점입니다. **Phase 2 우선 구현 권장.**

## 5. 데이터 모델

### 5.1 배포 아키텍처 전제 ⚠️ 먼저 확정하십시오

**이 선택이 스키마·배치 실행 주체·인증·알림·형태소 분석기 패키징·백업을 전부 규정합니다. 미결 상태로 개발에 들어가면 반드시 재작업이 발생합니다.**

| | A. 로컬 데스크톱형 | B. 서버 SaaS형 |
|---|---|---|
| DB | SQLite (단일 파일) | PostgreSQL |
| 배치(§9.4) | **앱 실행 중에만 동작** — "매일 03:00"은 성립하지 않음. 앱 기동 시 밀린 배치 실행 | 스케줄러 상시 |
| 자격증명 | OS 키체인/DPAPI | 서버 암호화 저장 (§2.5 결정 2 재검토 필요) |
| 멀티테넌시 | 불필요 | **`tenant_id` 필수 — 현 DDL에 없음** |
| 형태소 분석기 | 앱에 번들 (설치 용량 증가) | 서버 상주 |
| 프로파일 갱신 | 원격 다운로드 + **서명 검증** | 서버 배포 |
| §13 지표 수집 | 텔레메트리 동의 필요 | 서버에서 직접 |
| F-12 폴더 감시 | 가능 | 불가 |

**본 문서의 DDL은 A(로컬 SQLite)와 B(서버 PostgreSQL) 양쪽에서 동작하도록 작성했으나, B를 택할 경우 아래 두 가지를 반드시 추가하십시오.**

1. **모든 셀러 스코프 테이블에 `tenant_id`** — `channel_account`, `product_channel_map`, `report_import`, `keyword_fact`, `product_traffic_fact`, `keyword_score`, `keyword_suggestion`, `listing_*`. **`keyword` / `keyword_alias`만 전역 사전으로 공유**합니다.
2. **Row Level Security 정책** — §2.5 아키텍처 결정 3·4(타 셀러 데이터 미수집, 크로스-셀러 집계 미판매)를 **스키마 레벨에서 강제**하는 유일한 수단입니다. 애플리케이션 코드에만 의존하면 언젠가 뚫립니다.

> DDL은 PostgreSQL 15+ 문법 기준입니다. SQLite로 구현할 경우 `BIGSERIAL`→`INTEGER PRIMARY KEY AUTOINCREMENT`, `JSONB`→`TEXT`, `NUMERIC`→`REAL`로 치환하고, **`UNIQUE NULLS NOT DISTINCT`는 생성 컬럼(`COALESCE(x, 0)`)으로 대체**하십시오(§5.4).

### 5.3 DDL

```sql
-- ─────────────────────────────────────────────────────────
-- 1. 채널 계정
-- ─────────────────────────────────────────────────────────
CREATE TABLE channel_account (
    id              BIGSERIAL PRIMARY KEY,
    -- tenant_id    BIGINT NOT NULL,   -- ★ 서버형이면 필수 (§5.1)
    channel_code    VARCHAR(20)  NOT NULL
                    CHECK (channel_code IN ('NAVER','COUPANG','ESM_G','ESM_A','ST11')),
    account_alias   VARCHAR(100) NOT NULL,
    seller_id_mask  VARCHAR(100),
    is_active       BOOLEAN      NOT NULL DEFAULT TRUE,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);
-- ※ ID/PW 컬럼은 의도적으로 없습니다(§2.5 아키텍처 결정 2).

-- ─────────────────────────────────────────────────────────
-- 2. 채널 상품 매핑  ★ 선행 필수 (§2.4)
--    상품 레벨 행과 옵션(ITEM) 레벨 행을 parent_id로 명시 분리 (§5.4-F)
-- ─────────────────────────────────────────────────────────
CREATE TABLE product_channel_map (
    id                  BIGSERIAL PRIMARY KEY,
    parent_id           BIGINT       REFERENCES product_channel_map(id),  -- NULL = 상품 레벨
    map_level           VARCHAR(8)   NOT NULL
                        CHECK (map_level IN ('PRODUCT','ITEM')),
    product_id          BIGINT       NOT NULL REFERENCES product(id),
    channel_account_id  BIGINT       NOT NULL REFERENCES channel_account(id),
    channel_code        VARCHAR(20)  NOT NULL,
    channel_product_no  VARCHAR(64)  NOT NULL,
    channel_origin_no   VARCHAR(64),
    channel_item_no     VARCHAR(64),          -- map_level='ITEM'일 때만 값 존재
    title_source        VARCHAR(12)  NOT NULL DEFAULT 'REGISTERED'
                        CHECK (title_source IN ('REGISTERED','BACKFILLED','MANUAL')),
    listed_at           TIMESTAMPTZ  NOT NULL,
    last_synced_at      TIMESTAMPTZ,
    status              VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE',
    -- ★ NULL 중복 방지: channel_item_no가 NULL이어도 유일성이 성립해야 함
    CONSTRAINT uq_pcm UNIQUE NULLS NOT DISTINCT
        (channel_account_id, channel_product_no, channel_item_no)
);
CREATE INDEX ix_pcm_product ON product_channel_map(product_id);
CREATE INDEX ix_pcm_lookup  ON product_channel_map(channel_code, channel_product_no);
CREATE INDEX ix_pcm_parent  ON product_channel_map(parent_id);
-- ※ listed_title은 이 테이블에 두지 않습니다. 상품명은 시간에 따라 바뀌므로
--    아래 listing_title_revision이 단일 진실 원천입니다 (§5.4-B).

-- ─────────────────────────────────────────────────────────
-- 3. 상품명 리비전  ★ 루프를 닫는 핵심 (§5.4-B)
-- ─────────────────────────────────────────────────────────
CREATE TABLE listing_title_revision (
    id                     BIGSERIAL PRIMARY KEY,
    product_channel_map_id BIGINT      NOT NULL REFERENCES product_channel_map(id),
    title                  TEXT        NOT NULL,
    title_len              INT         NOT NULL,   -- 채널 계수 규칙 적용값 (§F-09)
    title_source           VARCHAR(12) NOT NULL
                           CHECK (title_source IN ('REGISTERED','SUGGESTION','MANUAL','BACKFILLED')),
    suggestion_id          BIGINT      REFERENCES keyword_suggestion(id),
    valid_from             TIMESTAMPTZ NOT NULL,
    valid_to               TIMESTAMPTZ,            -- NULL = 현재 유효
    -- 기간 중첩 금지 (PostgreSQL btree_gist 확장 필요)
    EXCLUDE USING gist (
        product_channel_map_id WITH =,
        tstzrange(valid_from, COALESCE(valid_to,'infinity')) WITH &&
    )
);
CREATE INDEX ix_rev_current ON listing_title_revision(product_channel_map_id)
    WHERE valid_to IS NULL;

-- ─────────────────────────────────────────────────────────
-- 4. 키워드 사전 (전역 공유)
-- ─────────────────────────────────────────────────────────
CREATE TABLE keyword (
    id          BIGSERIAL PRIMARY KEY,
    canon_text  VARCHAR(200) NOT NULL,   -- 표준 표기 (char_len 기준, §5.4-H)
    norm_key    VARCHAR(200) NOT NULL,
    char_len    INT          NOT NULL,   -- canon_text 기준. 관측 순서에 의존하지 않음
    token_count INT          NOT NULL,
    tokens      JSONB        NOT NULL,   -- 형태소 토큰 배열 (§8.2)
    first_seen  DATE         NOT NULL,
    last_seen   DATE         NOT NULL,
    CONSTRAINT uq_keyword_norm UNIQUE (norm_key)
);

CREATE TABLE keyword_alias (
    id           BIGSERIAL PRIMARY KEY,
    alias_norm   VARCHAR(200) NOT NULL UNIQUE,
    keyword_id   BIGINT       NOT NULL REFERENCES keyword(id),
    source       VARCHAR(20)  NOT NULL CHECK (source IN ('AUTO','MANUAL')),
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- ─────────────────────────────────────────────────────────
-- 5. 등록 원장 — 투입 키워드  ★ 해자의 절반 (§1.4)
--    revision_id로 "그 시점에 무엇을 넣었는가"를 고정 (§5.4-B)
-- ─────────────────────────────────────────────────────────
CREATE TABLE listing_keyword (
    id                     BIGSERIAL PRIMARY KEY,
    revision_id            BIGINT      NOT NULL REFERENCES listing_title_revision(id),
    product_channel_map_id BIGINT      NOT NULL REFERENCES product_channel_map(id),
    keyword_id             BIGINT      NOT NULL REFERENCES keyword(id),
    slot                   VARCHAR(10) NOT NULL
                           CHECK (slot IN ('TITLE','TAG','AD','DETAIL')),
    position               INT,
    char_len               INT         NOT NULL,
    injected_by            VARCHAR(20) NOT NULL
                           CHECK (injected_by IN ('MANUAL','THEORY','VERIFIED','PROPAGATED')),
    created_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_lk UNIQUE (revision_id, keyword_id, slot)
);
CREATE INDEX ix_lk_kw  ON listing_keyword(keyword_id);
CREATE INDEX ix_lk_pcm ON listing_keyword(product_channel_map_id);

-- ─────────────────────────────────────────────────────────
-- 6. 리포트 업로드 이력
--    coverage_scope / is_truncated 가 DEAD 판정의 전제 (§5.4-C)
-- ─────────────────────────────────────────────────────────
CREATE TABLE report_import (
    id                 BIGSERIAL PRIMARY KEY,
    channel_account_id BIGINT       NOT NULL REFERENCES channel_account(id),
    channel_code       VARCHAR(20)  NOT NULL,
    report_type        VARCHAR(40)  NOT NULL,
    profile_id         VARCHAR(80)  NOT NULL,
    profile_version    INT          NOT NULL,
    coverage_scope     VARCHAR(12)  NOT NULL      -- ★ 절단 여부
                       CHECK (coverage_scope IN ('FULL','TOP_N','AD_ONLY')),
    top_n              INT,                        -- TOP_N일 때 N (ESM=5)
    revenue_basis      VARCHAR(20),                -- VAT_INCL|VAT_EXCL|UNKNOWN (§5.4-I)
    attribution_days   INT,                        -- 광고 전환 기여 기간 (쿠팡 등)
    file_name          TEXT         NOT NULL,
    file_hash          CHAR(64)     NOT NULL,
    period_start       DATE,
    period_end         DATE,
    row_total          INT          NOT NULL DEFAULT 0,
    row_parsed         INT          NOT NULL DEFAULT 0,
    row_unmatched      INT          NOT NULL DEFAULT 0,
    row_rejected       INT          NOT NULL DEFAULT 0,
    status             VARCHAR(20)  NOT NULL
                       CHECK (status IN ('PARSING','NEEDS_MAPPING','DONE','FAILED')),
    error_detail       JSONB,
    imported_at        TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT uq_import_hash UNIQUE (channel_account_id, file_hash)
);

-- ─────────────────────────────────────────────────────────
-- 7. 키워드 실측 팩트  ★ 핵심 테이블
--    NULL = "채널이 제공하지 않음". 0과 구분됩니다 (§5.4-C)
-- ─────────────────────────────────────────────────────────
CREATE TABLE keyword_fact (
    id                     BIGSERIAL PRIMARY KEY,
    import_id              BIGINT       NOT NULL REFERENCES report_import(id),
    channel_account_id     BIGINT       NOT NULL REFERENCES channel_account(id),
    channel_code           VARCHAR(20)  NOT NULL,
    product_channel_map_id BIGINT       REFERENCES product_channel_map(id), -- NULL = STORE grain
    keyword_id             BIGINT       NOT NULL REFERENCES keyword(id),

    stat_date              DATE         NOT NULL,
    period_type            VARCHAR(6)   NOT NULL CHECK (period_type IN ('DAY','WEEK')),
    grain                  VARCHAR(8)   NOT NULL
                           CHECK (grain IN ('STORE','PRODUCT','ITEM')),   -- ★ ITEM 추가
    traffic_type           VARCHAR(8)   NOT NULL
                           CHECK (traffic_type IN ('ORGANIC','AD','MIXED')),

    impressions            BIGINT,      -- DEFAULT 0 제거 — NULL은 "미제공"
    clicks                 BIGINT,
    orders                 BIGINT,
    order_qty              BIGINT,
    revenue                NUMERIC(16,2),
    ad_cost                NUMERIC(16,2),
    rank_in_report         INT,
    raw_row                JSONB,

    -- ★ import_id를 키에서 제외 → 기간 겹침 시 실제로 덮어써짐 (§5.4-A)
    CONSTRAINT uq_fact UNIQUE NULLS NOT DISTINCT (
        channel_account_id, channel_code, grain, period_type,
        product_channel_map_id, keyword_id, stat_date, traffic_type
    )
);
CREATE INDEX ix_fact_kw_date  ON keyword_fact(keyword_id, stat_date);
CREATE INDEX ix_fact_pcm_date ON keyword_fact(product_channel_map_id, stat_date);
CREATE INDEX ix_fact_ch_date  ON keyword_fact(channel_code, stat_date);
CREATE INDEX ix_fact_import   ON keyword_fact(import_id);   -- ★ FK 인덱스 (재처리·삭제용)

-- ─────────────────────────────────────────────────────────
-- 8. 상품 단위 트래픽 팩트  ★ 등록 실험의 측정 기반 (§5.4-E)
-- ─────────────────────────────────────────────────────────
CREATE TABLE product_traffic_fact (
    id                     BIGSERIAL PRIMARY KEY,
    import_id              BIGINT       NOT NULL REFERENCES report_import(id),
    channel_account_id     BIGINT       NOT NULL REFERENCES channel_account(id),
    product_channel_map_id BIGINT       NOT NULL REFERENCES product_channel_map(id),
    stat_date              DATE         NOT NULL,
    traffic_type           VARCHAR(8)   NOT NULL,
    impressions            BIGINT,
    clicks                 BIGINT,
    orders                 BIGINT,
    revenue                NUMERIC(16,2),

-- 9. 스코어 스냅샷
-- ─────────────────────────────────────────────────────────
CREATE TABLE keyword_score (

    keyword_id             BIGINT       NOT NULL REFERENCES keyword(id),

        window_days, traffic_type
    )

CREATE INDEX ix_score_vks ON keyword_score(vks DESC);
CREATE INDEX ix_score_cls ON keyword_score(gap_class, vks DESC);
CREATE INDEX ix_score_pcm ON keyword_score(product_channel_map_id);  -- ★ S-3 화면용

-- 10. 액션 제안 — HELD_OUT 상태로 대조군 내장 (§9.2)

);
CREATE INDEX ix_sug_status ON keyword_suggestion(status, expected_gain DESC);
-- ★ 활성 제안 중복 생성 방지 (§8.4 [8] "생성/갱신")
CREATE UNIQUE INDEX uq_sug_active ON keyword_suggestion
    (product_channel_map_id, action, target_slot,

-- ─────────────────────────────────────────────────────────

    ended_at      TIMESTAMPTZ,
    winner_arm_id BIGINT REFERENCES listing_experiment_arm(id),  -- ★ FK 추가

                  CHECK (status IN ('DRAFT','RUNNING','EVALUATED','ABORTED'))
```

### 5.4 설계 결정과 그 이유

**A · `keyword_fact` 유일키에서 `import_id`를 뺀 이유 — 중복 합산 방지**

v1.0의 유일키는 `import_id`를 포함하고 있었습니다. 그러면 임포트가 다르면 같은 (상품·키워드·날짜) 행이 **별개 행으로 들어가 합산**됩니다. 셀러가 `8/1~8/21`로 한 번, `8/15~8/28`로 한 번 받아 올리면 겹치는 8/15~8/21이 **2배로 계산**됩니다. `file_hash` UNIQUE는 바이트가 같은 파일만 막는데, 재다운로드한 리포트는 생성 시각 셀·파일명이 달라 해시가 거의 항상 다릅니다.

또한 `product_channel_map_id`가 NULL일 수 있는데(STORE grain), PostgreSQL·SQLite 모두 UNIQUE에서 **NULL끼리는 충돌하지 않으므로** ESM 스토어 데이터는 같은 임포트 안에서조차 중복 제거가 안 됐습니다. → `NULLS NOT DISTINCT`로 해결하고, 키에 `channel_account_id`·`grain`·`period_type`을 추가했습니다(계정 2개 충돌, 주간/일간 같은 날짜 충돌 방지).

**겹치는 기간 처리 절차** (§8.4 [6]에서 구현):

```
1. 파싱 완료 후, (channel_account_id, report_type, period_start ~ period_end)
   범위의 기존 keyword_fact / product_traffic_fact 를 DELETE
2. 신규 행 INSERT
3. 또는 ON CONFLICT (uq_fact) DO UPDATE SET ..., import_id = EXCLUDED.import_id
```

**B · `listing_title_revision`을 신설한 이유 — 루프가 닫히려면 필요합니다**

v1.0은 `product_channel_map.listed_title`에 "등록 당시 원문"을 두었습니다. 그런데 P2-4가 실제 상품명을 수정하는 순간 그 값은 **더 이상 살아 있는 상품명이 아니고**, 갭 분석(§F-07)이 존재하지 않는 상품명을 기준으로 계산됩니다. **제안을 적용하는 순간 분석이 틀리기 시작합니다.**

연쇄적으로 §9.2 자가 보정, R8 롤백, §13 `injected_by` 비교, S-4 "4주 뒤 효과 측정"이 전부 구현 불가였습니다. 리비전 테이블이 있으면 `stat_date`가 속한 리비전을 조인해 "그 시점의 상품명 기준"으로 계산할 수 있고, 롤백은 이전 리비전을 다시 유효화하면 됩니다.

**C · 지표 컬럼에서 `DEFAULT 0`을 제거한 이유 — "미제공"과 "0"은 다릅니다**

`keyword_fact`에는 **유입이 있었던 키워드만 행이 생깁니다.** 그리고 행이 없는 이유는 "유입 0"이 아닙니다.

- ESM 키워드 분석 = **상위 5개만** 제공 → 6위 키워드는 유입이 있어도 리포트에 없음
- 쿠팡 키워드 전환 보고서 · 네이버 검색광고 API = **광고 유입만** → 오가닉이 아무리 많아도 없음

이걸 "유입 0"으로 읽으면 **오가닉으로 잘 팔리는 키워드를 상품명에서 제거**하게 됩니다. 매출에 직접 손해를 입히는 오작동입니다. 그래서 `report_import.coverage_scope`(`FULL`/`TOP_N`/`AD_ONLY`)를 두고, **절단 리포트에서는 `DEAD`를 절대 생성하지 않도록** 코드에 가드를 겁니다(§F-07). 판정 불가는 `UNKNOWN`으로 분류합니다.

**D · `gap_class`에 `UNKNOWN` 추가** — v1.0의 4분류에는 "데이터 부족으로 판정 불가"가 없어서 모든 미관측이 `DEAD`로 흘러갔습니다.

**E · `product_traffic_fact` 신설** — §7 등록 실험의 측정 지표는 "상품당 평균 유입수"인데, `keyword_fact`를 합산하면 위 C의 절단·광고 편향이 그대로 들어옵니다. 특히 쿠팡은 광고 키워드만 있으므로 **사실상 광고비 지출량을 측정**하게 됩니다. 상품 단위 유입은 별도 팩트로 받아야 합니다(네이버 통계 › 판매분석의 상품별 유입 리포트가 소스). **그 전까지 §7 등록 실험은 네이버 전용 기능입니다.**

**F · `map_level` + `parent_id`로 옵션 레벨 분리** — 쿠팡 광고 보고서와 비즈니스 인사이트는 **옵션(SKU) 단위**입니다. v1.0은 `grain`이 `PRODUCT|STORE`뿐이라 담을 곳이 없었고, `product_channel_map`이 (상품 × 옵션) 혼합 grain이라 `keyword_fact`가 어느 행을 가리켜야 하는지 정의되지 않았습니다. → **적재는 원본 해상도(`ITEM`) 그대로, 롤업은 집계 쿼리에서만** 수행합니다. 리포트에 상품 행과 옵션 행이 함께 들어오면 `map_level`로 구분되므로 이중 합산이 발생하지 않습니다.

**G · 인덱스·제약 보강**

| 추가 | 이유 |
|---|---|
| `ix_fact_import`, `ix_ptf_import` | PostgreSQL은 FK에 인덱스를 자동 생성하지 않습니다. §8.4의 "`import_id` 기준 재처리"가 풀스캔이 됩니다. |
| `ix_score_pcm` | S-3 상품별 진단이 핵심 화면인데 `uq_score` 선두가 `keyword_id`라 커버되지 않았습니다. |
| `uq_score`에 `channel_code`·`category_code` | 없으면 **카테고리 스코프 스코어를 저장할 수 없어 §F-13 확산 자격 계산이 불가능**합니다. |
| `uq_sug_active` 부분 유니크 | 없으면 업로드할 때마다 동일 제안이 중복 생성되어 S-4의 건수가 무한히 불어납니다. |
| `winner_arm_id` FK | v1.0에 누락. |
| 열거형 CHECK 제약 | `grain`·`traffic_type`의 정확성이 §2.2 결론②③의 전제인데 DB가 잘못된 값을 막지 않고 있었습니다. |

**H · `keyword.char_len`을 `canon_text` 기준으로** — v1.0은 "최초 관측 원문" 기준이라, 같은 키워드가 `블루투스 이어폰`으로 먼저 관측되면 8, `블루투스이어폰`이면 7이 됩니다. **배낭 무게가 관측 순서에 좌우**되는 문제가 있었습니다.

**I · `revenue_basis` / `attribution_days`** — 부가세 포함 여부와 광고 전환 기여 기간이 채널마다 다릅니다. 이걸 모르고 합산하면 매출 비교가 무의미해집니다.

**J · 그 밖에 유지한 결정**

| 결정 | 이유 |
|---|---|
| `raw_row` JSONB 보존 | 파서 프로파일이 바뀌어도 원본 재처리가 가능해야 합니다. **단, 검색어에 개인정보(전화번호·이름)가 섞일 수 있으므로 보관 기간·삭제 정책 필요** — §12 R14. |

## 6. 기능 상세 정의

### F-01 · 리포트 업로드

**입력**: 파일 드래그&드롭 또는 파일 선택 (다중 지원). 허용 확장자 `.xlsx .xls .csv .tsv`.

**처리 순서**

1. SHA-256 해시 계산 → `report_import.file_hash` 조회. 중복이면 즉시 스킵하고 "이미 2026-08-16에 업로드된 파일입니다" 안내.
2. **채널·리포트 타입 자동 판별** — 헤더 행 후보(1~8행)를 순회하며 각 파서 프로파일의 `detect.required_headers` 일치도를 계산, 최고 점수 프로파일 선택. 점수 0.7 미만이면 `NEEDS_MAPPING` 상태로 전환하고 F-02 수동 매핑 UI 호출.
3. **기간 자동 추출** — 날짜 컬럼의 min/max, 없으면 파일명 패턴(`YYYYMMDD`, `YYYY-MM-DD`) 파싱, 그것도 없으면 사용자 입력.
4. 파싱 → 정규화 → 상품 매칭 → 팩트 적재(트랜잭션).
5. 결과 요약 표시.

**출력 UX** — 업로드 직후 반드시 다음을 보여줍니다(§3.3 해소 4번).

```
✅ 쿠팡 · 키워드 전환 보고서 · 2026-08-01 ~ 2026-08-21
   1,847행 파싱 · 1,791행 상품 매칭 · 56행 미매칭 [확인하기]

   🔍 발굴 키워드   12개  (안 넣었는데 전환된 키워드)
   ✅ 검증 키워드   64개
   ⚠ 주시 키워드    9개  (유입은 오는데 전환 0)
   ❔ 판정 보류    38개  (이 리포트는 광고 유입만 담고 있어
                        '죽은 키워드' 판정은 하지 않습니다)
   → 개선 제안이 생성된 상품: 27개  [바로 보기]
```

**예외**

| 상황 | 처리 |
|---|---|
| 암호화된 xlsx | "암호를 해제한 뒤 다시 올려주세요" 안내 |
| 인코딩 깨짐(CP949 CSV) | `chardet` 자동 감지 → `cp949 → utf-8` 재시도 |
| 헤더 없이 데이터만 | 수동 매핑 UI로 폴백 |
| 파일이 리포트가 아님(주문서 등) | 프로파일 미매칭 → "이 파일은 지원하는 리포트가 아닌 것 같습니다" + 지원 리포트 목록 안내 |
| 기간이 기존 적재분과 겹침 | 겹치는 날짜 구간의 기존 팩트를 **DELETE 후 재적재**(§5.4-A 절차). 단순 INSERT 시 2배 합산됩니다. 사용자에게 고지. |
| 파일이 매우 큼 | 행수·용량 상한 초과 시 거부 (§14 NFR에서 값 확정). zip bomb 방어 필수 |

### F-02 · 파서 + 수동 매핑 폴백

§2.2 결론⑤에 따라 **컬럼 매핑은 절대 코드에 하드코딩하지 않습니다.** 상세 설계는 §8.

수동 매핑 UI는 다음을 제공합니다.

- 파일 상위 20행 미리보기 (헤더 행 지정 가능)
- 좌: 우리 표준 필드 / 우: 파일 컬럼 드롭다운 — 유사도 기반 초기 자동 선택
- 필수 필드(`keyword`, `clicks` 중 하나 이상 + 날짜) 미지정 시 저장 불가
- 저장 시 **새 프로파일로 등록** → 다음부터 자동 인식
- 프로파일은 로컬에 저장하되, 셀러 동의 하에 익명 공유(컬럼명 구조만, 데이터 없이) 옵션 제공 — 채널이 리포트 양식을 바꿔도 커뮤니티가 빠르게 복구

### F-04 · 상품 매칭

리포트의 채널 상품ID를 `product_channel_map`에서 조회합니다.

**매칭 실패 시 3단 폴백**

1. `channel_item_no`(옵션 ID)로 `map_level='ITEM'` 행 조회. **찾으면 그 행에 그대로 적재하고 롤업하지 않습니다** — 리포트에 상품 행과 옵션 행이 함께 오면 롤업이 이중 합산을 만듭니다(§5.4-F). 롤업은 집계 쿼리에서만 수행합니다.
2. 리포트에 상품명이 있으면 **해당 시점의 `listing_title_revision.title`**과 정규화 후 유사도 매칭 (임계값 0.85, Jaro-Winkler 또는 토큰 자카드)
3. 그래도 실패 → `row_unmatched` 카운트, **미매칭 해결 화면**에 큐잉. 사용자가 수동으로 연결하면 매핑이 학습되어 다음부터 자동 처리.

**미매칭이 30%를 넘으면** 업로드를 `DONE`이 아니라 경고 상태로 두고 "채널 상품ID 매핑이 부족합니다. 상품 동기화를 먼저 실행하세요"를 안내합니다.

### F-07 · 투입 × 회수 갭 분석  ★ 핵심

> v1.0 대비 전면 개정. 이전 정의는 (i) `L(p)` 정의가 자기모순이었고 (ii) 미관측을 유입 0으로 읽어 **잘 팔리는 키워드를 제거**했으며 (iii) 광고와 오가닉을 섞었습니다. 아래가 확정 정의입니다.

#### 투입 집합 `L(p, t)` — 시점 `t`의 상품명 리비전 기준

```
L(p, t) = tokens( 리비전(p, t).title )  ∪  ⋃ tokens(k)  for k in 태그 키워드
          — 형태소 분석기(Kiwi / mecab-ko) 기준 토큰 집합
```

**단일 정의입니다.** v1.0은 "키워드 집합"과 "상품명 문자열 + 토큰 집합" 두 가지를 동시에 적어 놓았고, 후자를 택하면 `slot='TAG'` 키워드가 판정에서 통째로 탈락해 **태그 키워드가 영원히 DISCOVERED로 오분류**됐습니다. 이제 태그도 토큰으로 합칩니다.

`t`는 팩트의 `stat_date`입니다. **상품명은 시간에 따라 바뀌므로 항상 그 시점의 리비전을 조인**합니다(§5.4-B).

#### 커버리지 판정

```
covered(k, p, t)  ⟺  tokens(k) ⊆ L(p, t)
```

**⚠️ 형태소 분석기는 Phase 1 필수 의존성입니다.** §8.2의 n-gram 폴백으로는 이 규칙이 동작하지 않습니다. 예를 들어 상품명 `캠핑 롤탑 테이블 우드 접이식`, 유입 키워드 `우드테이블`의 경우:

| 방식 | 결과 |
|---|---|
| 문자열 부분일치 | ✗ 실패 (연속하지 않음) |
| n-gram 부분집합 | ✗ 실패 (`드테`가 상품명 n-gram에 없음) |
| **형태소 토큰 부분집합** | ✅ `{우드, 테이블} ⊆ {캠핑, 롤탑, 테이블, 우드, 접이식}` |

n-gram 폴백에서는 이미 표현 가능한 키워드가 `DISCOVERED`로 잡혀 **F-09가 상품명에 또 집어넣습니다.** 따라서 폴백 모드로 운영할 경우 **`DISCOVERED` 자동 제안을 비활성화**하고 UI에 "정확도 저하 모드" 배지를 노출하십시오.

**어절 경계 오탐 방지**: §8.2의 공백 전면 제거와 문자열 부분일치를 결합하면 `무선 마우스 패드` → `무선마우스패드`에서 `무선마우스`가 매칭되어 마우스가 아닌 상품이 VERIFIED로 잡힙니다. 공백 제거 전 **어절 경계 offset 맵을 보존**하고, 경계를 가로지르는 문자열 매칭은 **낮은 신뢰도로 강등**합니다. 문자열 부분일치는 어디까지나 보조 신호이며 **단독 판정 근거로 쓰지 않습니다.**

#### 분류 규칙 — `(상품 p, 키워드 k, traffic_type)` 3차원

**`traffic_type`을 분리하지 않으면 §2.2 결론②를 갭 분석 단계에서 위반합니다.** 광고로만 들어온 키워드가 `DISCOVERED`로 잡혀 "상품명에 넣으세요"가 나가면, 사실은 "이 키워드에 돈을 썼다"를 "이 키워드가 잘 된다"로 오독한 것입니다.

| 분류 | 조건 | 의미 · 액션 |
|---|---|---|
| `VERIFIED` | covered ∧ `orders ≥ 1` | 넣었고 팔렸다 → 유지 + 확산 |
| `DISCOVERED` | ¬covered ∧ `clicks ≥ θ_c` | 안 넣었는데 들어왔다 → **명시 삽입** |
| `WATCH` | covered ∧ `clicks ≥ 30` ∧ `orders = 0` | 유입은 오는데 전환 0 → **키워드가 아니라 가격·썸네일 문제** |
| `DEAD` | covered ∧ **유효 음성 관측** (아래) | 넣었는데 안 들어왔다 → 제거 후보 |
| `UNKNOWN` | 그 외 (판정 근거 부족) | 아무 제안도 생성하지 않음 |

**`DEAD`의 유효 음성 관측 조건 — 이 가드가 없으면 매출에 손해를 입힙니다.**

```
dead(k, p) ⟺
      해당 (채널, 상품)에 대해 traffic_type='ORGANIC' 이고
      report_import.coverage_scope = 'FULL' 인 리포트가
      최근 21일 중 14일 이상 존재하고,
      그 리포트들 어디에도 k가 등장하지 않음
```

- `coverage_scope`가 `TOP_N`(ESM 상위 5개)이거나 `AD_ONLY`(쿠팡 광고, 네이버 검색광고 API)이면 **`DEAD`를 절대 생성하지 않습니다.** 코드에 가드를 넣고 단위 테스트로 고정하십시오.
- `DEAD` 판정은 **오가닉 기준으로만** 합니다. 광고 리포트에 없다는 것은 아무 의미가 없습니다.
- 조건을 만족하지 못하면 `UNKNOWN`입니다. 제안도, S-3의 🟥 색칠도 하지 않습니다.

**임계값 `θ_c`**: 절대 클릭수 고정값(v1.0의 `3`)은 상품·채널 트래픽 규모를 무시합니다. **상품 총 유입 대비 비율 또는 채널별 분위수**로 정의하십시오.

```
θ_c(p, ch) = max( 3,  0.005 × 해당 상품의 30일 총 유입 )
```

#### `WATCH`의 진단적 가치

이 분류가 있으면 **"키워드 문제"와 "상품 자체 문제"를 분리**할 수 있습니다. 유입은 오는데 전환이 0이면 키워드를 더 넣어도 소용없습니다. UI에서 "키워드가 아니라 가격·썸네일을 보세요"라고 말해줘야 합니다. 지금 어떤 툴도 이 말을 해주지 않습니다.

### F-09 · 상품명 재작성 제안 (토큰 커버리지 최적화)

> v1.0은 이를 0/1 배낭 문제로 정식화했습니다. 그러나 **키워드 가치는 가법적이지 않습니다** — `우드`와 `테이블`이 이미 있으면 `우드테이블`을 추가로 넣어도 한계 가치가 거의 0입니다. 배낭으로 풀면 중복 토큰이 발생하고, 실제로 v1.0의 출력 예시에는 `테이블`이 3회, `이어폰`이 2회 등장했습니다. 네이버·쿠팡 상품명 정책상 중복 단어는 어뷰징 신호로 다뤄질 수 있습니다(C-15에서 확인). 아래가 확정 정식화입니다.

#### 문제 정의 — 가중 최대 커버리지 (서브모듈러)

```
U         = 대상 상품의 유입 쿼리 집합 (각 쿼리 q에 가중치 VKS(q))
후보 토큰  T = DISCOVERED 키워드들의 형태소 토큰 ∪ 기존 토큰
비용 c(τ)  = 토큰 τ의 글자수 + 구분자 1
예산 W    = 채널 상품명 한도 − 고정부(브랜드/모델/필수옵션) 길이

선택 집합 S ⊆ T 에 대해
  covered(S) = { q ∈ U : tokens(q) ⊆ S ∪ 고정부토큰 }
  maximize   Σ VKS(q)  for q ∈ covered(S)
  subject to Σ c(τ) ≤ W,  τ ∈ S
```

**이 목적함수는 서브모듈러이므로 그리디가 `(1 − 1/e) ≈ 0.63` 근사를 보장**하고, **중복 토큰이 구조적으로 발생하지 않습니다** — 이미 커버된 쿼리는 한계 이득이 0이므로 그리디가 두 번 담지 않습니다.

```python
def greedy_cover(candidates, queries, budget, fixed_tokens):
    selected, remaining = set(), budget
    while True:
        best, best_ratio = None, 0
        for tok in candidates - selected:
            if cost(tok) > remaining:
                continue
            gain = marginal_gain(selected | {tok} | fixed_tokens, queries)
            if gain / cost(tok) > best_ratio:
                best, best_ratio = tok, gain / cost(tok)
        if best is None:
            break
        selected.add(best); remaining -= cost(best)
    return selected
```

#### 하드 제약 (위반 시 REJECT — P2-1 수용 기준)

1. **중복 토큰 금지** — 최종 상품명 전체(고정부 포함)에 동일 토큰이 2회 이상 나타나면 거부.
2. **금칙어 필터** — 타사 브랜드명, 과대광고 표현(`최고`·`1위`·`정품보장` 등), 채널 정책 위반어. **선택이 아니라 필수입니다.** 실측 데이터에는 타사 브랜드로 들어온 유입이 섞여 있고, 그대로 넣으면 **상표권 문제 + 채널 제재**로 직행합니다.
3. **길이 한도** — 아래 계수 규칙 기준.
4. **`W ≤ 0` 가드** — 고정부가 이미 한도를 넘으면 제안을 생성하지 않고 "고정부가 너무 깁니다"를 안내.
5. **어순 정책** — 채널이 브랜드 선두를 요구하면 이는 선택 문제가 아니라 **배치 문제**입니다. 선택 후 채널별 배치 규칙을 적용합니다.

#### 글자수 계수 규칙 — 반드시 외부화

v1.0은 화면 예시마다 계수 기준이 달라 수치가 재현되지 않았습니다. 채널 프로파일로 확정하십시오.

```jsonc
"title_len_rule": {
  "unit": "CHAR",          // CHAR | BYTE
  "include_space": true,   // 공백 포함 여부
  "max": 100               // 채널 한도 (C-15에서 확정)
}
```

**본 문서의 모든 예시는 `unit=CHAR, include_space=true` 기준입니다.**

#### 출력 예시

```
현재 (34자 / 100자)
  캠핑 롤탑 테이블 우드 접이식 경량 야외 피크닉 알루미늄 미니

제안 (43자 / 100자)                        커버 쿼리 +9개 · 예상 유입 +31% (추정)
  캠핑 롤탑 테이블 우드 접이식 차박 감성 원목 사이드 경량

  + 추가: 차박(VKS 86, 전환 19) · 감성(79, 11) · 원목(72, 8) · 사이드(61, 3)
  − 제거: 야외(21일 오가닉 전량 리포트 무유입) · 피크닉(동일)
          알루미늄(동일) · 미니(동일)

  ⓘ 토큰 중복 없음 · 금칙어 없음 · 43/100자
  [적용]  [부분 적용]  [무시]   ⓘ 근거 보기
```

`차박테이블`이 아니라 `차박`만 넣는 이유: `테이블`이 이미 있으므로 형태소 매칭상 `차박테이블` 쿼리가 커버됩니다. 이것이 서브모듈러 그리디가 자동으로 하는 일입니다.

#### 두 개의 가치 함수를 혼동하지 마십시오

`expected_gain`(§9.2, 제안 정렬용)과 커버리지 목적함수의 `VKS(q)` 합(§F-09, 토큰 선택용)은 **서로 다른 값**입니다. UI에는 `expected_gain` 기준 하나만 노출하고, 툴팁에서 커버 쿼리 수를 보조 표기하십시오.

#### 적용은 반드시 사람이 누릅니다

자동 일괄 수정은 Phase 2 이후에도 기본 OFF입니다. 검증 이력이 쌓인 셀러에게만 옵트인으로 엽니다. **상품명 수정 자체가 채널 랭킹·재검수에 영향을 줄 수 있습니다**(§12 R15).

### F-10 · 대량등록 연동 — 검증 키워드 주입

기존 대량등록 파이프라인의 상품명 생성 단계에 후크를 겁니다.

```
[기존]  소싱 데이터 → 상품명 템플릿 적용 → 등록
[개선]  소싱 데이터 → 상품명 템플릿 적용
                    → ★ 검증 키워드 주입 (카테고리 매칭)
                    → 토큰 커버리지 최적화 + 중복 토큰 검증
                    → 금칙어 필터
                    → 등록 → ★ 채널 상품ID 회수 → listing_keyword 기록
```

마지막 줄이 중요합니다. **등록할 때마다 `listing_keyword`에 투입 원장을 남겨야 다음 사이클의 갭 분석이 가능**합니다. 루프가 닫히는 지점입니다.

주입 대상은 `keyword_score.gap_class = 'VERIFIED'` 이면서 `product_coverage ≥ 2`, `order_sum ≥ 3` 인 키워드로 제한합니다(§F-13 확산 조건과 동일).

### F-13 · 키워드 확산 (Propagation)

검증된 키워드를 **아직 등록하지 않은 신규 상품**에 시드로 공급합니다. 이것이 "이론 키워드"를 대체하는 지점입니다.

**확산 자격**

```
propagatable(k, category c) ⟺
      product_coverage(k, c) ≥ 2      -- 2개 이상 상품에서
  AND order_sum(k, c)       ≥ 3      -- 누적 3건 이상 전환
  AND cvr_smoothed(k, c)    ≥ 카테고리 중앙값
  AND k ∉ 금칙어
```

`product_coverage ≥ 2` 조건이 핵심입니다. **한 상품에서만 잘 된 키워드는 그 상품 고유의 우연일 수 있습니다.** 두 개 이상에서 재현돼야 카테고리 지식으로 승격합니다.

**확산 강도 단계**

| 단계 | 조건 | 동작 |
|---|---|---|
| 후보 | 자격 충족 | 신규 등록 시 **제안 목록**에 노출 |
| 자동 | 자격 충족 + `product_coverage ≥ 5` | 신규 등록 시 **기본 선택** 상태로 주입 |
| 승격 | 자동 + 3사이클 연속 유지 | **카테고리 템플릿**에 편입 |

## 7. 등록 실험 (Listing Experiment) — 대량등록만 가능한 것

### 7.1 왜 이게 가능한가

일반 셀러는 상품이 10~50개라 A/B 테스트 표본이 안 나옵니다. **대량등록 셀러는 한 배치에 수백~수천 개를 올립니다.** 표본이 공짜로 생깁니다. 이건 아이템스카우트가 절대 못 하는 영역입니다.

> **⚠️ 전제**: 측정 지표가 "상품당 유입수"이므로 **상품 단위 오가닉 트래픽 리포트(`product_traffic_fact`)가 있는 채널에서만** 유효합니다(§5.4-E). 키워드 팩트를 합산해 대신 쓰면 ESM은 상위 5개 절단, 쿠팡은 광고 전용이라 **사실상 광고비 지출량을 측정**하게 됩니다. **당분간 네이버 전용 기능입니다.**

### 7.2 설계

**대상**: 동일 카테고리 · 유사 가격대 · 동시 등록되는 상품 그룹

**배정 — 층화 후 안정 해시**

```python
# ⚠️ Python 내장 hash()는 문자열에 대해 프로세스마다 시드가 달라
#    "재실행 시 배정이 흔들리지 않게" 하려는 의도가 정확히 반대로 깨집니다.
import hashlib

def assign_arm(sku: str, arm_count: int, salt: str) -> int:
    h = hashlib.sha1(f"{salt}:{sku}".encode()).hexdigest()
    return int(h[:8], 16) % arm_count
```

**층화(stratification)가 필요합니다.** §7.3이 우려하는 교란(상품 품질·가격이 Arm 간에 쏠림)은 단순 해시로는 남습니다. **가격 구간 × 공급사**로 층을 나눈 뒤 **층 내에서 해시 배정**하십시오. 층 키는 `listing_experiment_assign.stratum`에 기록합니다.

**패턴 예시**

| Arm | 상품명 패턴 | 가설 |
|---|---|---|
| A | `{핵심}{용도}{브랜드}{옵션}` | 핵심어 선두가 유리 |
| B | `{브랜드}{핵심}{용도}{옵션}` | 브랜드 선두가 신뢰도↑ |
| C | `{핵심}{롱테일조합}{용도}` | 롱테일 다수 배치가 유입↑ |

**측정 지표**: 상품당 오가닉 유입수 (`INFLOW_PER_PRODUCT`, `product_traffic_fact` 기준)

### 7.3 통계 설계 — v1.0에서 가장 크게 고친 부분

v1.0은 3개 Arm을 쌍별로 `p < 0.05`에 걸어 판정했습니다. 두 가지 문제가 있었습니다.

**문제 1 · 다중비교 미보정** — 3개 Arm이면 3쌍이고, 각각 α=0.05를 쓰면 family-wise error가 **약 14%**로 부풀어 오릅니다. 실제로는 아무 차이가 없는데 "승자"가 나올 확률이 1/7입니다.

**문제 2 · 결과 훔쳐보기(peeking)** — v1.0의 S-5 화면은 `RUNNING · 18일차`에 p값을 실시간 노출하고 `[계속 관찰]` 버튼을 제공했습니다. 유의미가 나올 때까지 보다가 멈추는 전형적인 optional stopping이며, 실제 1종 오류율은 명목 α를 크게 초과합니다. 스키마에 `evaluate_at`이 이미 있는데 UI가 무시하고 있었습니다.

**확정 절차**

```
1. 옴니버스 검정   Kruskal-Wallis (Arm 3개 이상)
                   → p ≥ α 이면 "패턴 간 차이 없음"으로 종료. 사후검정 안 함.
2. 사후검정        Dunn's test
3. 다중비교 보정   Holm-Bonferroni (또는 Benjamini-Hochberg)
                   ※ 최소한 Bonferroni: α' = 0.05 / 3 = 0.0167
4. 효과크기        Hodges-Lehmann 위치 이동 추정치 + 부트스트랩 95% CI
                   ※ p값만 보고하지 않습니다.
```

**Arm 2개인 경우**에만 Mann-Whitney U를 단독으로 씁니다.

**⚠️ 지표와 검정통계량을 일치시키십시오.** v1.0의 S-5는 "상품당 유입 41.2 vs 47.9"라는 **평균**을 보여주면서 **순위 기반 검정** 결과를 붙였습니다. 유입 분포는 소수 상품이 독식하는 극단적 롱테일이므로 평균은 대표성이 없습니다. **중앙값 + Hodges-Lehmann 위치 이동 + CI**로 표기하십시오.

**관측 기간 — 하나로 확정**

```
총 기간 = burn_in_days (7일, 색인 반영 대기 · 판정에서 제외)
        + observe_days (14일, 유효 관측)
        = 21일
evaluate_at = started_at + 21일
```

**`evaluate_at` 이전에는 p값을 화면에 표시하지 않습니다.** 진행률과 Arm별 표본 수만 노출합니다. `[계속 관찰]`로 기간을 연장하는 경우 α-spending 계획을 사전에 등록하거나, 연장 후 재판정은 참고용으로만 표기하십시오.

**`min_arm_size`** — v1.0의 `30`은 근거가 없었습니다. 유입 분포에 0이 다수인 조건에서 MWU/Dunn의 검정력은 매우 낮습니다. **파일럿 데이터로 MDE(최소 검출 가능 효과)를 계산해 값을 정하십시오.** 계산 전까지는 기본값 50으로 두고 UI에 "표본 부족" 경고를 띄웁니다.

### 7.4 주의사항

- **"차이 없음"도 결과입니다.** Kruskal-Wallis가 기각되지 않으면 상품명 패턴에 더 시간 쓰지 말고 다른 변수(가격·썸네일)로 옮기라고 안내합니다. 이게 정직한 툴의 태도이고, 셀러가 신뢰하게 되는 지점입니다.
- **교란 변수를 완전히 통제하지 못합니다.** 층화 배정이 상당 부분 완화하지만 완전하지 않습니다. UI에 "참고 지표"임을 명시하고, 실험 결과를 단독 근거로 대량 수정하지 않도록 안내합니다.
- **채널 정책 위반 주의** — 동일 상품을 패턴만 바꿔 중복 등록하는 것은 어뷰징입니다. 실험은 **서로 다른 상품**에 다른 패턴을 적용하는 방식이어야 하며, 동일 상품 복제는 절대 금지입니다. 코드에 가드를 넣습니다.

### 8.2 키워드 정규화

동일 키워드가 표기 차이로 갈라지면 스코어가 흩어지고 갭 분석이 무너집니다. 정규화는 이 기능의 정확도를 좌우합니다.

```
norm_key(raw) =
  1. 유니코드 NFC 정규화            (한글 자모 결합형 통일 — 필수)
  2. 전각 → 반각 변환
  3. 소문자화 (영문)
  4. 앞뒤 공백 제거 → 연속 공백 1개로 축약
  5. 어절 경계 offset 맵 보존       ← 6번 전에. F-07 오탐 방지용
  6. 구분자 제거: 공백 · 하이픈 · 언더스코어 · 마침표를 모두 동일 처리
                                    "USB-C" == "USB C" == "usbc"
  7. 그 외 특수문자 제거 (허용: 한글 · 영문 · 숫자)
```

**v1.0의 오류 정정**: v1.0은 5번에서 "하이픈은 모델명 보존을 위해 유지", 6번에서 "모든 공백 제거"라고 했습니다. 그러면 `USB-C` → `usb-c`, `USB C` → `usbc`로 **동일 개념이 서로 다른 `norm_key`로 갈라집니다.** 하이픈을 살린 목적과 공백 제거가 충돌했습니다. → 구분자를 전부 동일하게 처리하고, 모델명은 별도 `model_token` 사전으로 보존합니다.

또한 v1.0의 문자 클래스 `[^\w가-힣]`에서 `\w`는 유니코드 모드에서 이미 한글을 포함하므로 `가-힣`이 중복이고, 동시에 `_`·타 언어 문자가 전부 보존됩니다. → **허용 문자를 화이트리스트로 명시**했습니다.

**alias 치환은 `keyword` UPSERT보다 먼저입니다.** v1.0의 §8.4 [4]는 "정규화 → keyword UPSERT → alias 치환" 순서였는데, 그러면 alias가 독립 `keyword` 행으로 먼저 생성되고 그 행에 팩트가 붙은 뒤 나중에 치환됩니다. → 순서를 뒤집었습니다.

**alias 수동 병합 시 마이그레이션 절차** (v1.0에 없었습니다):

```
1. 병합 대상 keyword_id(from) → keyword_id(to) 확정
2. keyword_fact / keyword_score / listing_keyword 의 keyword_id 재지정
3. ★ uq_fact / uq_score 충돌 발생 시 지표를 SUM으로 합산 후 중복 행 삭제
4. keyword_alias 에 alias_norm 등록
5. from 키워드 행 삭제
   — 전체를 단일 트랜잭션으로 묶습니다.
```

**6번(공백 제거)이 한국어 이커머스에서 특히 중요합니다.** 검색어는 띄어쓰기가 제각각이고, 채널 리포트도 이를 그대로 실어 줍니다.

**토큰 집합**은 별도로 유지합니다(부분 일치 판정용, §F-07).

```
tokens(raw) = 형태소 분석 또는 n-gram 분해
  - 형태소 분석기 사용 시: mecab-ko / Kiwi (Python: kiwipiepy) 권장
  - 미도입 시 폴백: 공백 분리 + 2~5글자 슬라이딩 n-gram
```

> **초기 구현 권장**: 형태소 분석기 도입 전에는 n-gram 폴백으로 시작해도 됩니다. 다만 `keyword_alias` 수동 병합 UI를 반드시 함께 제공해, 셀러가 "이 둘은 같은 키워드"라고 알려줄 수 있게 하십시오. 실사용 데이터가 곧 사전이 됩니다.

**금칙어 사전**은 별도로 관리합니다. 최소 구성: 타사 브랜드명, 과대광고 표현(`최고`, `1위`, `정품보장` 등 채널 정책 위반어), 의약품·건강기능 관련 금지 표현.

**설계 의도**

- 채널이 컬럼명을 바꿔도 **JSON 배열에 한 항목 추가**로 끝납니다. 배포 없이 핫픽스 가능하도록 프로파일을 앱 데이터 디렉터리에서 로드하고, 원격 프로파일 업데이트 채널을 둡니다.
- `min_score`로 오탐을 막고, 실패 시 수동 매핑으로 폴백하므로 **파서가 모르는 파일이 와도 기능이 죽지 않습니다.**
- `row_filters`가 쿠팡 "검색 영역" 필터를 데이터로 표현합니다. 비검색영역(상세페이지 노출)이 섞이면 키워드 성과가 왜곡됩니다.

### 8.4 파이프라인 단계

```
[1] INGEST      파일 수신 · 해시 · 중복 차단
       │
[2] DETECT      프로파일 매칭 → (실패 시 → 수동 매핑 UI → 새 프로파일 저장)
       │
[3] PARSE       헤더 위치 결정 · 컬럼 매핑 · 타입 변환 · row_filters · validations
       │        └ 실패 행은 raw_row 보존 후 row_rejected 카운트
[4] NORMALIZE   키워드 정규화 → ★ alias 조회·치환 → keyword UPSERT
       │            (v1.0은 UPSERT가 먼저였습니다 — §8.2 참조)
[5] MATCH       채널 상품ID → product_channel_map 조회 (map_level 구분)
       │        └ 3단 폴백 (§F-04) → 미해결은 큐잉
[6] LOAD        ★ 기간 겹침 DELETE → keyword_fact / product_traffic_fact INSERT
       │
[7] SCORE       영향 범위만 재계산 (전체 재계산 아님)
       │        └ 대상: 이번 임포트에 등장한 keyword_id × product_channel_map_id
[8] ANALYZE     갭 분류(traffic_type 3차원) → keyword_suggestion UPSERT
       │        └ 신규 제안의 10~20%는 HELD_OUT 으로 보류 (§9.2)
[9] NOTIFY      업로드 결과 요약 UX
```

**[6] 기간 겹침 처리 — v1.0에서 빠져 있던 절차**

```sql
BEGIN;
  DELETE FROM keyword_fact
   WHERE channel_account_id = :acct
     AND stat_date BETWEEN :period_start AND :period_end
     AND grain = :grain AND traffic_type = :traffic_type;
  -- product_traffic_fact 도 동일
  INSERT INTO keyword_fact (...) VALUES ...;   -- 또는 ON CONFLICT (uq_fact) DO UPDATE
COMMIT;
```

`uq_fact`에서 `import_id`를 뺐기 때문에(§5.4-A) `ON CONFLICT`가 **다른 임포트의 행을 만날 수 있습니다.** v1.0의 유일키로는 이게 불가능해서 겹치는 기간이 2배로 합산됐습니다.

**[7] 증분 계산이 중요합니다.** 상품 수천 개 × 키워드 수만 개가 되면 전체 재계산은 수십 초가 걸립니다. 이번 임포트가 건드린 `(keyword_id, product_channel_map_id)` 쌍만 재계산하면 보통 1초 이내입니다.

**트랜잭션 경계** — 수만 행 UPSERT를 단일 트랜잭션으로 묶으면 장시간 락이 걸립니다. **1,000행 단위 배치 커밋**을 권장하고, 실패 시 `import_id` 기준 롤백(팩트 DELETE 후 재시도)으로 처리합니다.

**동시성** — 여러 파일을 동시에 드롭하면 `keyword` UPSERT가 같은 `norm_key`에서 경합합니다. `ON CONFLICT (norm_key) DO NOTHING` + 재조회, 또는 직렬 큐로 처리하십시오.

**재처리**: `import_id` 기준으로 팩트를 지우고 `raw_row`에서 다시 돌립니다. `ix_fact_import` 인덱스가 필요합니다(§5.4-G).

### 8.5 수집 어댑터 인터페이스 (미래 API 대비)

§2.3의 네이버 데이터솔루션 리뉴얼이나 채널의 신규 통계 API가 열렸을 때, **파이프라인 [4]~[9]는 그대로 두고 [1]~[3]만 교체**할 수 있어야 합니다.

```python

    def extract(self, payload: bytes | dict) -> Iterator[RawFactRow]:
        """정규화 이전의 표준 행 스트림"""
```

`FileSource`(프로파일 기반)와 `ApiSource`(네이버 검색광고 등)가 같은 프로토콜을 구현합니다. **네이버가 데이터솔루션을 스마트스토어까지 열면 `NaverBizDataSource` 클래스 하나를 추가하는 것으로 끝납니다.**

## 9. 키워드 스코어링 & 갭 분석 로직

### 9.1 VKS (Verified Keyword Score)

**문제**: 유입 3회에 전환 1회면 전환율 33%입니다. 유입 1,000회에 전환 200회면 20%입니다. 단순 전환율로 정렬하면 표본이 적은 노이즈가 1위를 차지합니다.

#### 베이지안 스무딩

```
CVR_smoothed(k, p) = (orders + α · CVR_prior) / (clicks + α)

  α         = 20        (사전 표본 크기. 카테고리별 튜닝)
  CVR_prior = (카테고리 × 채널 × traffic_type) 평균 전환율
```

**`CVR_prior`를 `traffic_type`으로 반드시 분리하십시오.** v1.0은 "카테고리·채널 전체 평균"이었는데, 광고 CVR과 오가닉 CVR은 규모가 다르므로 §2.2 결론②를 스무딩 단계에서 위반합니다.

`α = 20 > 0`이므로 `clicks = 0`에서도 분모 0이 발생하지 않고, 결과는 `CVR_prior`로 수렴합니다(의도된 동작).

**`orders > clicks` 방어**: 광고 리포트는 전환 기여 기간(`attribution_days`) 때문에 당일 클릭보다 전환이 많을 수 있습니다. 이 경우 `CVR_smoothed > 1`이 되어 백분위와 UI 전환율 표기가 깨집니다. → **기여 기간만큼 시프트해 정렬**하거나, 정렬이 불가능하면 `min(CVR, 1.0)`으로 클리핑하고 UI에 주석을 답니다.

#### 최신성 감쇠

```
Recency(k, p) = 0.5 ^ (days_since_last_click / H)
  H = 30                                    (반감기)
  days_since_last_click 이 NULL 이면 Recency = 0
```

**윈도우와 반감기를 함께 정하십시오.** 30일 윈도우로 자르면서 반감기 30일 감쇠를 또 곱하면 최신성이 이중 반영됩니다. → **윈도우 90일 + 반감기 30일**을 기본값으로 씁니다. 30일 윈도우 스코어는 감쇠 없이 계산합니다.

#### 최종 점수

```
VKS(k, p) = 100 × Recency × (
      w_v · P(clicks)
    + w_c · P(CVR_smoothed)
    + w_r · P(revenue)
)

  P(x) = 동일 (카테고리 × 채널 × traffic_type) 모집단 내 백분위 (0~1)
  w_v = 0.30   유입 규모
  w_c = 0.40   전환 효율   ← 위탁판매는 마진이 얇아 여기에 가중
  w_r = 0.30   매출 기여
```

**v1.0의 `log1p`를 제거했습니다.** `P(x)`가 백분위이면 P는 **단조 변환에 불변**이므로 `P(log1p(clicks)) ≡ P(clicks)`입니다. v1.0의 "설계 근거 1: log1p로 롱테일을 눌러야 한다"는 **min-max 정규화에서만 성립하는 논리**이고, 바로 다음 줄의 "설계 근거 2: 백분위 정규화(min-max 아님)"가 그것을 스스로 무효화하고 있었습니다. 계산 결과는 같지만(무해한 연산) 잘못된 근거가 문서에 남아 있으면 나중에 정규화 방식을 바꿀 때 오판합니다.

> **정규화 방식은 둘 중 하나만 택하십시오.**
> - (택1) **백분위** — `log1p` 불필요. 이상치에 강건. **본 문서의 채택안.**
> - (택2) `log1p` + robust min-max — 절대값 비교가 필요한 경우에만.

#### 필수 가드

| 가드 | 이유 |
|---|---|
| **모집단 `n < 30`이면 상위 스코프로 폴백** (카테고리 → 채널 전체 → 전체) | (카테고리 × 채널 × traffic_type) 조합에 키워드가 3개면 백분위가 `0 / 0.5 / 1`이 되어 VKS가 무의미해집니다. `keyword_score.population_n`에 실제 모집단 크기를 기록해 UI에서 신뢰도를 표기하십시오. |
| **`w_v`와 `w_r`의 공선성 인지** | `revenue ≈ clicks × cvr × 단가`이므로 `w_v + w_r = 0.60`이 사실상 유입 규모에 중복 가중됩니다. 튜닝 시 이 점을 감안하거나 `w_r`을 `revenue/click`(객단가)로 바꾸는 것을 검토하십시오. |
| **STORE grain의 `category_code`는 NULL** | 카테고리는 상품에서 옵니다. 스토어 레벨 스코어는 (채널 × traffic_type) 모집단으로 별도 계산하고, 상품별 화면에 섞지 않습니다. |

**STORE grain 처리**: ESM 키워드 분석처럼 상품 단위가 없는 데이터는 `product_channel_map_id = NULL`로 적재하고 **스토어 레벨 VKS만** 계산합니다. 상품별 진단 화면(S-3)에 절대 섞지 않고, 대시보드의 별도 섹션에만 `스토어 단위 · 주간 · 상위 5개` 배지와 함께 표시합니다.

### 9.2 기대 효과 추정 (`expected_gain`) — 홀드아웃 필수

제안을 정렬하려면 "이걸 하면 얼마나 나아지나"가 필요합니다.

```
DISCOVERED 키워드 k를 상품 p의 상품명에 추가할 때:

  expected_gain(k, p) = clicks(k, p, 30d) × uplift_factor × confidence

    uplift_factor = 0.3      -- 초기 상수. 근거 없음.
    confidence    = min(1.0, clicks(k,p,30d) / 20)
```

**⚠️ 상수만 미검증인 게 아니라 함수 형태도 미검증입니다.** 이 식은 "유입이 많은 DISCOVERED 키워드일수록 기대 이득이 크다"고 가정합니다. 그런데 유입이 이미 많다는 것은 **상품명에 없어도 이미 잘 매칭되고 있다**는 뜻이므로, 명시 삽입의 한계 이득은 오히려 작을 수 있습니다. **제안 정렬이 체계적으로 반대 방향일 가능성을 배제할 수 없습니다.** UI에 `(추정)`을 명기하고 산식을 툴팁에 공개하십시오.

#### 자가 보정 — 홀드아웃을 제품에 내장

v1.0은 "적용 후 4주 실측치로 `uplift_factor`를 보정"이라고 했는데, **대조군이 없습니다.** 계절성, 채널 전체 트래픽 변동, 그리고 특히 다음 두 가지가 전부 uplift로 잘못 귀속됩니다.

- **평균 회귀** — 제안은 최근 유입이 급증한 키워드에서 나오므로 다음 기간엔 자연 하락합니다.
- **선택 편향** — 셀러는 유망한 상품에 우선 적용합니다.

대조군 없이 보정하면 루프가 **편향을 학습해 시간이 갈수록 더 자신 있게 틀립니다.**

```
1. 제안 생성 시 무작위 10~20%를 status='HELD_OUT' 으로 보류 (사용자에게 미노출)
2. 4주 후 측정:
     Δ_applied  = 적용군의 유입 변화율
     Δ_heldout  = 홀드아웃군의 유입 변화율
     uplift_실측 = Δ_applied − Δ_heldout        ← 이것만이 인과 추정치
3. 카테고리별 uplift_factor 를 uplift_실측 으로 갱신 (월 1회)
```

**홀드아웃 비율은 사용자에게 고지하십시오.** "제안 정확도 개선을 위해 일부 제안을 대조군으로 보류합니다"를 설정 화면에 명시하고, 옵트아웃을 제공합니다.

### 9.3 제안 사유 코드

| `reason_code` | 조건 | UI 문구 |
|---|---|---|
| `DISCOVERED_HIGH_CVR` | DISCOVERED(ORGANIC) + CVR_smoothed 상위 25% | "안 넣었는데 전환이 나는 키워드입니다" |
| `DISCOVERED_HIGH_VOL` | DISCOVERED(ORGANIC) + clicks 상위 25% | "유입이 많은데 상품명에 없습니다" |
| `DEAD_LONG` | DEAD (유효 음성 관측 충족, §F-07) | "3주간 오가닉 전량 리포트에 한 번도 없었습니다" |
| `DEAD_BLOCKING` | DEAD + 글자수 ≥ 5 + 대기 중 DISCOVERED 존재 | "이걸 빼면 '{키워드}'를 넣을 수 있습니다" |
| `WATCH_NO_CONV` | WATCH + clicks ≥ 30 + orders = 0 | "유입은 오는데 전환이 없습니다. 키워드가 아니라 가격·썸네일을 점검하세요" |
| `PROPAGATE_CATEGORY` | 확산 자격 충족 + 미적용 상품 | "같은 카테고리 {n}개 상품에서 검증된 키워드입니다" |
| `AD_ONLY_ORGANIC_GAP` | traffic_type=AD 데이터만 존재 + 동일 키워드의 ORGANIC 데이터 0 | "광고로만 들어오는 키워드입니다. 상품명 반영으로 자연 유입을 노려보세요" |

`AD_ONLY_ORGANIC_GAP`이 실무적으로 가장 유용합니다. **광고비를 쓰고 있는데 오가닉으로는 안 들어오는 키워드**는 상품명 최적화 1순위이고, 성공하면 광고비가 줄어듭니다. 이 제안 하나로도 구독료를 정당화할 수 있습니다.

**단, 이 제안은 오가닉 전량 리포트가 있을 때만 유효합니다.** 오가닉 데이터 자체가 없으면 "오가닉 0"이 아니라 "모름"입니다(§5.4-C).

"차이 없음"을 정직하게 표기하는 것이 중요합니다(§7.4).

**`evaluate_at`(21일차) 이전에는 p값을 표시하지 않습니다.** 진행 중 화면에는 진행률과 Arm별 표본 수만 보여줍니다. 유의미가 나올 때까지 보다가 멈추면 실제 1종 오류율이 명목 α를 크게 넘습니다(§7.3). v1.0의 화면은 18일차에 p값을 노출하고 `[계속 관찰]`을 제공해 정확히 이 문제를 유발했습니다.

**평균이 아니라 중앙값 + IQR로 표기합니다.** 유입 분포는 소수 상품이 독식하는 극단적 롱테일이라 평균은 대표성이 없고, 순위 기반 검정과도 어긋납니다.

### 실측 × 이론 4분면 (P3-6) — Phase 3에서 이론 키워드의 자리

이론 키워드를 버리는 게 아니라 **실측과 교차**시킬 때 가장 강력해집니다.

```
              시장 검색량 많음
                    │
   ⚔ 격전지         │   💎 노다지
   시장 크고        │   시장 크고 나도 잘 됨
   나는 안 됨       │   → 지키고 광고 태우기
   → 순위 문제.     │
     상세·리뷰 보강 │
  ──────────────────┼──────────────────  내 실측 성과 좋음
                    │
   🗑 무시          │   🔒 숨은 금맥
   시장 작고        │   시장은 작은데 나는 잘 됨
   나도 안 됨       │   → 경쟁자가 모른다.
   → 버리기         │     조용히 확산.
                    │
              시장 검색량 적음
```

**🔒 숨은 금맥이 이 기능 전체의 최종 산출물입니다.** 아이템스카우트에서는 검색량이 낮아 필터에 걸려 사라지는 키워드인데, 내 실측 데이터에서는 확실히 전환이 나는 키워드. 경쟁자는 이 키워드의 존재 자체를 모릅니다. 이것이 "이론 키워드 대신 실측 키워드"라는 최초 아이디어가 도달하는 지점입니다.

**v1.0에서 고친 두 가지**

1. **제안 적용률의 분모에 `EXPIRED`를 포함했습니다.** v1.0은 `APPLIED/(APPLIED+DISMISSED)`였는데, 셀러가 무시하고 방치하면 30일 후 `EXPIRED`가 되어 지표에서 사라집니다. **실제보다 좋게 나옵니다.**
2. **효과 지표를 "적용군 − 홀드아웃군"으로 재정의했습니다.** v1.0의 "적용 상품의 4주 후 유입 변화 +15%"는 계절성·평균 회귀·선택 편향을 전부 uplift로 잘못 귀속합니다(§9.2).

> **가장 중요한 것은 아래에서 네 번째 줄입니다.** `listing_keyword.injected_by`로 "이론 키워드로 넣은 상품" vs "실측 검증 키워드로 넣은 상품"의 성과를 직접 비교할 수 있습니다. **이 숫자가 이 기능이 존재할 이유의 유일한 증명이며, 마케팅에도 그대로 쓸 수 있습니다.**
>
> 단, **P0-4 이후 등록된 상품에만 성립합니다.** 과거 상품은 투입 원장이 없어 비교 대상이 되지 않습니다.

**마지막 줄(`DEAD` 0건)은 목표가 아니라 하드 요구입니다.** 위반하면 셀러가 잘 팔리는 키워드를 지우게 됩니다. P1-11의 회귀 테스트로 고정하십시오.

### 법률 서술 보정

- **부정경쟁방지법 제2조 제1호 카목 4)** 는 "기술적 보호조치의 무력화를 **주된 목적으로 하는 기술·서비스·장치를 제공·배포**하는 행위"에 형사처벌이 적용됩니다. 따라서 "우회 로직을 넣는 순간"은 **그 프로그램을 셀러에게 배포하는 경우**에 정확합니다. 자사 서버 내부 실행만이라면 카목 1) 또는 정보통신망법 §48①이 문제됩니다. **배제라는 결론은 바뀌지 않지만, 배포 형태(C-0)에 따라 적용 법조가 달라지므로 C-18에서 확정하십시오.**
- **"접근권한 부여 주체는 서비스제공자"** 법리의 원 출처는 **대법원 2005도870(2005-11-25)** 이며, 2021도1533(여기어때)은 이를 인용·적용한 판결입니다. 두 사건번호를 함께 인용하십시오.
- **여기어때 무죄의 실제 이유**는 ① 서버에 별도 접근 보호조치가 없었고 회원 여부와 무관하게 자유 접근 가능 ② 수집 정보가 이미 공개된 것이어서 **DB의 통상적 이용과 충돌하지 않음**(저작권법) ③ 부정한 명령 입력 증거 부족(업무방해)입니다. §2.5 표의 "비회원이라 약관 적용 안 됨"은 ①의 일부를 다르게 표현한 것이며, **②가 §2.5 결정 3(타 스토어 데이터 미수집)의 직접 근거**이므로 함께 기억하십시오.
