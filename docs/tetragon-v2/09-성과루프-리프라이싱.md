## 0. 지금 무엇이 없는가 (코드 확인)

`Listing`([src/Tetragon.Domain/Listing/Listing.cs](../../src/Tetragon.Domain/Listing/Listing.cs), 63줄) 전체 필드입니다.

```csharp
TenantId, ProductId, MarketCode, Status, MarketItemId,
LastError, ListedPrice, CreatedAt, UpdatedAt, SyncLogs
```

**노출·클릭·주문·매출 필드가 하나도 없습니다.** `SyncLogs`는 우리가 마켓에 무엇을 했는지의 기록이지, 마켓에서 무슨 일이 일어났는지가 아닙니다.

`ListingStatus`는 `Pending | Registered | Failed | Suspended` 4종인데, `Suspended`로 가는 유일한 경로는 `StockChangedHandler`가 품절을 감지했을 때입니다([InventorySync.cs](../../src/Tetragon.Application/Pipeline/InventorySync.cs)). **마켓이 우리 상품을 판매중지·등록보류로 되돌린 것은 영원히 모릅니다.**

그래서 이 문서는 세 가지를 만듭니다.

1. **성과 원장** — 무엇이 팔렸는지 (§1~§3)
2. **리프라이싱 엔진** — 가격을 고치는 규칙 (§4)
3. **생존 확인** — 내 상품이 아직 살아 있는지 (§5, §6)

## 1. 데이터 모델

```sql
-- ── 일별 성과 원장 ──────────────────────────────────────────────
CREATE TABLE listing_perf (
  listing_id   TEXT    NOT NULL,
  date         TEXT    NOT NULL,          -- 'YYYY-MM-DD' (KST)
  source       TEXT    NOT NULL,          -- 'csv' | 'api'
  impressions  INTEGER NOT NULL DEFAULT 0,
  clicks       INTEGER NOT NULL DEFAULT 0,
  orders       INTEGER NOT NULL DEFAULT 0,
  units        INTEGER NOT NULL DEFAULT 0,
  gross_sales  REAL    NOT NULL DEFAULT 0,   -- ★ 취소·반품 반영 전. 이익 계산 금지 (§3.4)
  cancels      INTEGER NOT NULL DEFAULT 0,
  import_id    TEXT    NOT NULL,
  imported_at  INTEGER NOT NULL,
  PRIMARY KEY (listing_id, date, source)
);
CREATE INDEX ix_perf_date ON listing_perf(date);

-- ── 리스팅 티어 (v2 §4.3 A/B/C) ─────────────────────────────────
CREATE TABLE listing_tier (
  listing_id   TEXT PRIMARY KEY,
  tier         TEXT    NOT NULL,          -- 'A'|'B'|'C'
  reason       TEXT    NOT NULL,          -- 어떤 규칙으로 A가 됐는지 (사람이 읽는다)
  orders_30d   INTEGER NOT NULL DEFAULT 0,

CREATE INDEX ix_tier ON listing_tier(tier);

-- ── 위너 관측 (§5) ──────────────────────────────────────────────
CREATE TABLE listing_winner (
  id               TEXT PRIMARY KEY,
  listing_id       TEXT    NOT NULL,
  checked_at       INTEGER NOT NULL,
  method           TEXT    NOT NULL,      -- 'api'|'proxy-ctr'|'manual'
  is_winner        INTEGER,               -- NULL = 판정 불가

  winner_price     REAL,
  competitor_count INTEGER,
  note             TEXT
);
CREATE INDEX ix_winner_listing ON listing_winner(listing_id, checked_at DESC);

-- ── 리프라이싱 이력 (§4.5 롤백의 근거) ───────────────────────────
CREATE TABLE reprice_events (

  ceiling_price      REAL NOT NULL,
  reason             TEXT NOT NULL,
  state              TEXT NOT NULL,       -- 'proposed'|'applied'|'failed'|'reverted'

CREATE INDEX ix_reprice_listing ON reprice_events(listing_id, created_at DESC);

-- ── 임포트 배치 ────────────────────────────────────────────────
CREATE TABLE perf_imports (
  id           TEXT PRIMARY KEY,
  channel      TEXT NOT NULL,
  period_from  TEXT NOT NULL,
  period_to    TEXT NOT NULL,
  file_name    TEXT NOT NULL,
  profile_id   TEXT NOT NULL,
  row_count    INTEGER NOT NULL,

```

**보존 정책** (v2 §2.1이 "초판에는 보존 정책이 아예 없었다"고 지적한 것을 따릅니다):
`listing_perf` 25개월(전년 동월 비교용) · `listing_winner` 180일 · `reprice_events` 무기한(금액 이력) · `perf_imports` 무기한(메타만).

일 기준: 상품 1만 개 × 25개월 ≈ 750만 행. SQLite로 감당되지만 v2 §8 PostgreSQL 전환 트리거를 앞당길 수 있습니다.
→ **완화책**: 노출·클릭·주문이 모두 0인 날은 적재하지 않습니다. 위탁 카탈로그는 대부분이 0이므로 실제 행 수는 한 자릿수 퍼센트로 떨어집니다. 대신 "데이터 없음"과 "0"이 구분되지 않으므로 `perf_imports.period_from~to`로 커버리지를 판단합니다.

## 2. CSV 임포트

공용 프레임은 [08 §3](08-확장기능-개요.md)입니다. 여기서는 성과 고유 부분만.

### 2.1 매칭 — 마켓 상품번호 → 우리 Listing

```csharp
// IListingRepository에 이미 있는 메서드를 그대로 씁니다 (신규 포트 불필요)
Task<Listing?> FindByMarketItemAsync(string marketCode, string marketItemId, CancellationToken ct);
```

`Listings`에는 `(ProductId, MarketCode)` 유니크 인덱스만 있고 `MarketItemId` 인덱스가 없습니다
([TetragonDbContext.cs](../../src/Tetragon.Infrastructure/Persistence/TetragonDbContext.cs) `modelBuilder.Entity<Listing>`).
수천 행짜리 CSV를 한 줄씩 조회하면 전부 테이블 스캔입니다. **인덱스를 추가합니다.**

```csharp
b.HasIndex(l => new { l.MarketCode, l.MarketItemId });
```

임포트는 한 줄씩 조회하지 않고 **파일의 모든 marketItemId를 모아 한 번에 로드**해 사전을 만듭니다.

### 2.2 옵션 단위 vs 상품 단위

쿠팡 통계는 옵션(vendorItemId) 단위로 내려오고, 우리 `Listing`은 상품 단위입니다.
→ **옵션 행을 상품 단위로 합산**해 적재합니다. 옵션별 성과가 필요해지는 시점(어떤 색이 팔리는지)이 오면 `listing_perf_variant`를 추가하되, 지금은 만들지 않습니다.
트리거: 옵션이 5개 이상인 리스팅이 전체의 30%를 넘고, 옵션별 재고 조정을 하게 될 때.

### 2.3 미매칭 처리

미매칭 사유는 셋입니다. 사유별로 다르게 다룹니다.

| 사유 | 처리 |
|---|---|
| 우리가 등록하지 않은 상품 (수동 등록분) | `perf_imports.unmatched`에 세고 무시 |
| `MarketItemId`가 비어 있는 Listing (등록 실패 후 성공했는데 기록 누락) | attention `perf.unmatched` — 실제로 팔리고 있는데 시스템이 모르는 상태다 |
| 마켓이 상품번호를 재발급 | 위와 동일. 수동 연결 UI 제공 |

두 번째가 중요합니다 — **매출이 있는데 미매칭이면 impact_krw는 0이 아닙니다.** 그 CSV 행의 매출을 그대로 넣습니다.

### 2.4 `gross_sales`를 이익 계산에 쓰지 마십시오

마켓 통계 CSV의 '매출'은 **취소·반품 반영 전, 쿠폰 분담 반영 전** 숫자입니다.
이 값으로 이익을 계산하면 실제보다 낙관적인 숫자가 나오고, 그 숫자로 리프라이싱을 하면 역마진 상품을 "괜찮다"고 판정합니다.

> **규약**: `listing_perf.gross_sales`는 **수요 신호**로만 씁니다 (무엇이 팔리는가).
> **이익은 [10 정산 대사](10-정산대사-수익회계.md)의 `order_pnl`만이 답합니다.**
> 리프라이싱의 바닥가는 `order_pnl`(있으면) 또는 `MarginModel` 추정(없으면)에서 옵니다. `gross_sales`에서 오지 않습니다.

## 3. 롤업과 티어링

### 3.1 `perf.rollup` (일 1회 03:00 KST)

- 최근 7/30/90일 집계를 `listing_tier`에 캐시합니다. 매 조회마다 750만 행을 스캔하지 않기 위함입니다.
- 원가 변동을 감지합니다 — `RawProductRecord`(재수집분)와 현재 `Product.Variants[].SourcePrice` 비교 → 변동분을 `reprice.evaluate` 큐에 넣습니다.

### 3.2 티어 규칙 (v2 §4.3 표를 코드로)

```csharp
// src/Tetragon.Application/Services/Performance/TierPolicy.cs
public static ListingTier Compute(TierInput x) =>
    x.Orders30d > 0                     ? A("최근 30일 주문 있음")
  : x.IsWinner == true                  ? A("아이템위너 보유")
  : x.MinStock <= 5                     ? A("재고 5개 이하 — 품절 임박")
  : x.ListedWithinDays <= 90 && x.Clicks30d > 0 ? B("등록 90일 이내 + 클릭 있음")
  : C("나머지");
```

`reason`을 문자열로 남기는 것이 요점입니다. **"왜 이 상품이 4시간마다 동기화되는가"에 화면이 답할 수 있어야** 티어가 신뢰를 얻습니다.

### 3.3 티어의 실제 용도

v2 §4.3이 계산한 대로 전량 주기 동기화는 불가능합니다. 티어는 다음 셋을 나눕니다.

| | 티어 A | 티어 B | 티어 C |
|---|---|---|---|
| `operate.sync` (재고·원가) | 4~6시간 | 1일 | 주 1회 |
| `winner.check` | 일 1회 | — | — |
| `reprice.evaluate` | 일 1회 | 주 1회 | 원가 변동 시에만 |
| `operate.status_check` | 주 1회 | 주 1회 | 월 1회 |

## 4. 리프라이싱 엔진

### 4.1 왜 `PricingEngine`을 재사용할 수 없는가

기존 [PricingEngine.cs](../../src/Tetragon.Application/Services/PricingEngine.cs)(69줄)는 **전방 계산**입니다: 원가 → Rule 6개 순차 적용 → 판매가.
리프라이싱은 **제약 하의 목표가 선택**입니다: 현재가와 시장 상황이 주어졌을 때, 허용 구간 안에서 어디로 갈 것인가.

같은 `IPriceRule` 인터페이스에 욱여넣으면 `PriceContext`에 위너가·경쟁사수·재고·성과를 다 넣어야 하고, 그러면 기존 6개 Rule이 전부 그 컨텍스트를 알게 됩니다. **분리합니다.**

단, **바닥가는 반드시 `PricingEngine`과 같은 원가·환율·수수료를 씁니다.** 두 계산이 갈라지면 "정책상 15,900원인데 리프라이싱이 12,000원으로 내림" 같은 모순이 생깁니다.

### 4.2 구간 먼저, 목표 나중

```
바닥가 floor   = BreakEven × (1 + minMarginPct/100)
                 BreakEven = MarginModel의 손익분기 (10 §2의 정정된 산식)
천장가 ceiling = min( 현재가 × (1 + maxRaisePct/100),
                      정책가 × (1 + policyOverPct/100) )
쿨다운         = 마지막 적용으로부터 7일 (rule별 override 가능)
1회 변동폭     = |to − from| ≤ 현재가 × stepCapPct (기본 15%)
```

**모든 규칙은 `[floor, ceiling]` 안의 값만 제안할 수 있습니다.** 구간 밖을 원하면 제안이 아니라 `attention_item`입니다 — 사람이 정책을 고쳐야 하는 상황입니다.

### 4.3 규칙 4종

v2 §2.6이 `market_rules` 테이블 대신 `IListingValidator` **코드**를 택한 근거(개발자=운영자, 테이블판이 테스트하기 더 어렵다)를 그대로 적용합니다.

```csharp
// src/Tetragon.Application/Services/Repricing/IRepriceRule.cs
public interface IRepriceRule
{
    string RuleCode { get; }
    int Priority { get; }                       // 낮을수록 먼저 (충돌 시 §4.4)
    bool AppliesTo(RepriceContext ctx);
    RepriceProposal? Evaluate(RepriceContext ctx);
}

public sealed record RepriceContext
{
    public required Guid ListingId { get; init; }
    public required string Channel { get; init; }
    public required decimal CurrentPrice { get; init; }
    public required decimal FloorPrice { get; init; }
    public required decimal CeilingPrice { get; init; }
    public required decimal CostKrw { get; init; }          // 최신 공급가 (KRW 환산)
    public decimal? PreviousCostKrw { get; init; }
    public int MinStock { get; init; }
    public PerfWindow Perf30d { get; init; } = new();        // 노출·클릭·주문
    public WinnerObservation? Winner { get; init; }
    public DateTimeOffset? LastRepricedAt { get; init; }
    public int RepriceCount90d { get; init; }
}

public sealed record RepriceProposal(
    string RuleCode, decimal TargetPrice, string Reason, decimal Confidence);
```

| 규칙 | Priority | 조건 | 동작 | 위험 |
|---|---|---|---|---|
| **`CostChangeRule`** | 10 | 공급가가 올라 현재가가 `floor` 아래로 내려감 | `floor`까지 **인상** | 낮음 — 안 하면 확정 손실 |
| **`LowStockRule`** | 20 | 재고 ≤ 3 이고 티어 A | `min(현재가 × 1.10, ceiling)`으로 인상 | 낮음 — 품절 페널티 회피 |
| **`WinnerRecaptureRule`** | 30 | 쿠팡 · 위너 상실 · `winner_price − 10 ≥ floor` | `winner_price − 10`으로 인하 | **중간** — §5의 관측 신뢰도에 달림 |
| **`StaleNoSaleRule`** | 40 | 90일간 노출 ≥ 500 · 주문 0 · 인하 횟수 < 3 | 현재가 × 0.93 (단, ≥ floor) | 중간 — 수요가 아니라 노출 문제일 수 있음 |

**첫 배포에는 `CostChangeRule`만 켭니다** (08 §4 순서 4번). 나머지는 DryRun으로 몇 주 관찰한 뒤 하나씩.

### 4.4 충돌 해소 — 보수적 교집합

여러 규칙이 동시에 제안하면 **평균이나 최고 우선순위를 쓰지 않습니다.**

```
인상 제안들 → 가장 높은 하한 L = max(인상 제안가)
인하 제안들 → 가장 낮은 상한 U = min(인하 제안가)
L ≤ U  →  최종가 = L          (인상 요구를 우선 충족)
L > U  →  제안 없음 + attention_item("가격 요구가 서로 모순")
```

예: `CostChangeRule`이 "원가가 올라 12,000원 이상이어야 한다", `WinnerRecaptureRule`이 "위너 잡으려면 11,500원이어야 한다" → 모순. 이건 **가격으로 풀 문제가 아니라 이 상품을 계속 팔지 결정할 문제**입니다. 사람에게 보냅니다.

### 4.5 적용과 롤백

```
reprice.evaluate  (부작용 없음)
  → reprice_events(state='proposed', dry_run=policy.DryRun)
  → DryRun이면 여기서 끝. 화면에 "이렇게 바꿀 예정" 목록으로 표시
  → 아니면 reprice.apply 큐에 투입

reprice.apply     (마켓 쓰기)
  → external_calls INSERT (별도 트랜잭션 선커밋, v2 §2.3 규약 1)
       scope = "market.reprice.{channel}"
       key   = "{listingId}:{targetPriceKrw}:{yyyyMMdd_KST}"
  → IMarketplaceAdapter.UpdatePriceStockAsync(marketItemId, price, stock, cred, ct)
       ★ 기존 메서드. 새 어댑터 메서드를 만들지 않습니다
  → 성공: Listing.MarkPriceStockSynced(price, stock)  ★ 기존 메서드
          reprice_events(state='applied', applied_at)
  → 실패: state='failed' + last_error, work_item 백오프 (v2 §2.2)
```

`key`에 날짜를 넣은 이유: 같은 리스팅을 같은 가격으로 **다른 날** 다시 바꾸는 것은 정당합니다. 같은 날 두 번은 리스 만료 재실행입니다.

**롤백**: `POST /api/v1/reprice/revert` — 기간·규칙 코드로 묶어 `from_price`로 되돌립니다. 되돌리기도 `reprice.apply`를 타므로 같은 멱등 규약이 적용됩니다.

### 4.6 안전장치 (기존 `AutomationPolicy` 확장)

[AutomationPolicy.cs](../../src/Tetragon.Domain/Ordering/AutomationPolicy.cs)(146줄)는 이미 `Enabled`, `DryRun`, `IntervalMinutes`, 한도, `RecordFailure`/`HaltedReason`(연속 3회 실패 시 자가 정지)을 갖고 있습니다. **같은 패턴을 그대로 씁니다.**

```csharp
// AutomationPolicy에 추가
public bool     AutoReprice { get; private set; }          // 기본 false
public int      RepriceDailyCap { get; private set; }      // 기본 200
public decimal  RepriceStepCapPct { get; private set; }    // 기본 15
public int      RepriceCooldownDays { get; private set; }  // 기본 7
public decimal  RepriceMinMarginPct { get; private set; }  // 기본 10
```

- `RepriceDailyCap`은 쿠팡 일 5,000건 쿼터(v2 §2.5)와 **별개의 더 좁은 상한**입니다. 쿼터가 남아도 하루 200건만 바꿉니다 — 가격이 하루에 수천 개 흔들리면 되돌릴 수 없습니다.
- 실패가 연속 3회면 기존 `RecordFailure()`가 자동화를 멈춥니다. **이 동작을 리프라이싱에도 공유합니다.**

## 5. 위너 감시 — 공개 API가 없다는 사실을 정면으로

### 5.1 확인하지 못한 것

쿠팡 아이템위너(Buy Box) 보유 여부를 조회하는 **공개 셀러 API를 확인하지 못했습니다.** 현재 코드의 쿠팡 어댑터(partial 4파일, 약 1,750줄)에도 그런 호출은 없습니다.

이 상태에서 선택지는 셋입니다.

| 방법 | 신뢰도 | 문제 |
|---|---|---|
| (a) 셀러 API의 상품 조회 응답에 경쟁 정보가 있는지 확인 | 높음 | **미확인.** 먼저 실측해야 함 |
| (b) 쿠팡 상품 페이지 파싱 | 중간 | 마켓 ToS 위반 소지 + 차단 위험. **권하지 않음** |
| (c) 대리지표 — 우리 데이터만으로 추정 | 낮음~중간 | 오탐 가능 |

### 5.2 (c) 대리지표를 1차 수단으로

아이템위너를 잃으면 **노출은 유지되는데 클릭·주문이 절벽처럼 떨어집니다.** 우리는 `listing_perf`로 그것을 봅니다.

```
직전 14일 평균 CTR = clicks / impressions
최근 3일 평균 CTR
판정: 최근 3일 impressions ≥ 직전 평균의 70%   (노출은 살아 있다)
   AND 최근 3일 CTR ≤ 직전 평균 CTR × 0.35     (클릭만 죽었다)
   AND 직전 14일 orders ≥ 3                    (원래 팔리던 상품이다)
→ is_winner = 0, method='proxy-ctr', confidence = 0.5
```

`confidence`를 반드시 낮게 기록합니다. `WinnerRecaptureRule`은 **`confidence ≥ 0.8`일 때만 자동 인하**하고, 그 미만이면 제안만 하고 `attention_item(winner.lost)`으로 사람에게 보냅니다.

즉 **대리지표만으로는 가격이 자동으로 내려가지 않습니다.** (a)가 확인돼 `method='api'`, `confidence=1.0`이 들어오는 날 자동 인하가 켜집니다.

### 5.3 오탐의 대가를 계산해 두기

CTR 급락은 위너 상실 말고도 계절성·경쟁 신상품·검색 알고리즘 변경으로 일어납니다.
오탐으로 가격을 내리면 **마진만 잃고 위너는 못 잡습니다.** 그래서 위 조건에 `orders ≥ 3`을 넣었습니다 — 원래 안 팔리던 상품의 CTR 변동은 노이즈입니다.

## 6. 등록 생존 확인 (`operate.status_check`)

v2 §3.3이 지적한 공백입니다: **등록 성공 ≠ 판매 가능.**

```
주 1회 (티어 C는 월 1회)
  → IMarketplaceAdapter에 조회 메서드가 없다 ★
```

**여기서 계약을 하나 추가해야 합니다.** 기존 `IMarketplaceAdapter`(348줄 [Marketplace.cs](../../src/Tetragon.Plugin.Abstractions/Marketplace.cs))에는 `Register/Update/Delete/UpdatePriceStock/FetchOrders`만 있고 **조회가 없습니다.**

```csharp
// src/Tetragon.Plugin.Abstractions/Marketplace.cs — 신규 인터페이스 (IMarketplaceAdapter에 넣지 않음)
/// <summary>마켓에 등록된 우리 상품의 현재 상태를 되읽는 능력.
/// 등록 성공 이후 마켓이 판매중지·등록보류로 되돌린 것을 감지한다.
/// 조회 API가 있는 마켓만 구현한다 — 엑셀 경로 마켓(auction/gmarket)은 구현하지 않는다.</summary>
public interface IListingStatusSource
{
    Task<MarketListingStatus> FetchStatusAsync(
        string marketItemId, MarketCredential credential, CancellationToken ct);
}

public sealed record MarketListingStatus(
    bool Exists, string RawStatus, bool OnSale, decimal? Price, int? Stock, string? Reason);
```

`IShippingPlaceProvider`·`IOrderFulfillmentProvider`가 이미 "쿠팡만 구현하는 부가 인터페이스"로 존재하므로 **같은 패턴입니다** — 기존 어댑터를 하나도 수정하지 않습니다.

결과 처리:

| 관측 | 동작 |
|---|---|
| `Exists=false` | `Listing.Suspend("마켓에서 삭제됨")` + attention |
| `OnSale=false` | `Listing.Suspend(reason)` + attention `listing.halted` |
| `Price`가 우리 `ListedPrice`와 다름 | `MarkPriceStockSynced`로 동기화 + 로그 (마켓 쪽에서 바뀐 것) |

**`ListingStatus`에 `Halted`를 추가하지 않고 기존 `Suspended`를 재사용합니다.** 상태를 늘리면 `StatusBadge`([frontend/src/shared/ui.tsx](../../frontend/src/shared/ui.tsx))의 17종 매핑과 필터 UI를 모두 손봐야 하는데, 구분해서 얻는 것이 `SyncLogs` 한 줄뿐입니다.

## 10. 이 설계가 틀릴 수 있는 지점

1. **위너 대리지표(§5.2)의 임계값 0.70/0.35/3은 실측이 아니라 추측입니다.** 첫 4주는 판정만 기록하고 아무 동작도 시키지 마십시오. 그 기간의 오탐률을 보고 임계값을 고칩니다.
2. **`StaleNoSaleRule`은 인과를 거꾸로 볼 수 있습니다.** 안 팔리는 이유가 가격이 아니라 상세페이지 부재라면(12 참조) 인하는 마진만 깎습니다. 그래서 인하 횟수를 3회로 막았지만, 근본적으로는 **12(콘텐츠)를 먼저 적용한 상품에만 이 규칙을 켜는 것**이 맞습니다.
3. **CSV의 날짜가 KST인지 확인해야 합니다.** v2 §2.5가 쿼터에서 지적한 것과 같은 함정입니다 — UTC로 읽으면 하루가 밀립니다.
4. **`listing_perf` 행 수 추정(§1)이 낙관적일 수 있습니다.** 0행 스킵이 실제로 얼마나 줄여 주는지는 첫 임포트 후에야 압니다.
